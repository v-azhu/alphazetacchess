# AlphaZetaChess V0.4.4 — Pawn Structure (Connected Pawns)

## Status

**Implemented, tested, and cheap. `use_pawn_structure` defaults to
`False`** (same reasoning as every other V0.4.x term: disabled by
default until there's a playing-strength signal to justify flipping it,
per `docs/v0.4.1.md`'s established principle).

## Design

One well-defined Xiangqi-specific concept, kept intentionally small
(matching the scope discipline of V0.4.1/V0.4.2/V0.4.3): **Connected
Pawns (联兵)**. Two pawns on adjacent files at the same rank can
mutually support each other — once a pawn crosses the river it gains
sideways movement, so a same-rank neighbor on an adjacent file is a
real potential defender or recapture resource. An isolated pawn (no
same-rank neighbor on an adjacent file) has nothing nearby to rely on
if attacked — a well-known practical weakness in Xiangqi, especially
for advanced pawns that have already crossed the river.

```python
CONNECTED_PAWN_BONUS = 6
CONNECTED_PAWN_CROSSED_RIVER_BONUS = 10  # extra, on top of the base bonus
```

A pawn with an adjacent-file same-rank friendly pawn scores the base
bonus; if that pawn has ALSO crossed the river, it scores the extra
bonus too (checked per-pawn, not requiring both connected pawns to have
crossed — an advanced, supported pawn is valuable in its own right
regardless of exactly how advanced its neighbor is).

### Deliberately out of scope for this first version

- **Isolated pawn penalty** as a distinct, separately-tuned term (as
  opposed to simply not getting the connected bonus) — could be added
  later if the connected-only signal proves too weak.
- **Doubled pawns** — not really a meaningful Xiangqi concept the way it
  is in Western chess (pawns aren't tied to promotion), so intentionally
  not implemented.
- **Passed-pawn-equivalent concepts** — Xiangqi pawns don't promote, so
  there's no direct analogue; any future term here would need its own
  Xiangqi-specific justification, not a port from chess.

### API

`evaluate(board, perspective_color, ..., use_pawn_structure=False)` —
independent of `use_piece_square_tables`, `use_king_safety`, and
`use_mobility`; all four terms stack additively and can be toggled in
any combination. `SearchEngine` gained a matching `use_pawn_structure`
constructor flag, threaded through all four internal `evaluate()` call
sites, following the exact pattern established for
`use_mobility`/`use_king_safety`/`use_piece_square_tables`.

## Correctness gates (`tests/test_pawn_structure_v044.py`, 10 tests)

1. Isolated pawn (no neighbors at all) scores zero.
2. Two connected pawns each score the base bonus (both sides of the
   pair benefit).
3. Connected AND crossed the river scores the extra bonus too.
4. Same-file pawns (different ranks) are NOT connected — this term is
   specifically about side-by-side support, not "any nearby pawn".
5. Pawns two-or-more files apart are not connected.
6. An enemy pawn on an adjacent file does not count as a connection.
7. Symmetric position → `pawn_structure_balance(RED) ==
   -pawn_structure_balance(BLACK)`.
8. `use_pawn_structure=False` (explicit) exactly reproduces the V0.4.3
   baseline evaluation.
9. Toggling the term on changes the score by exactly the expected
   amount in a constructed position.
10. `SearchEngine`-level wiring check (direct `_quiescence` call,
    bypassing move search — same technique used for V0.4.1/V0.4.2's
    wiring tests, avoiding the "search picks a different move and hides
    the difference" trap those tests were designed around).

Full targeted suite (`test_mobility_v043.py`, `test_evaluation_v043.py`,
`test_search_v043_beta2.py`, `test_evaluation_v041.py`,
`test_evaluation_v042.py`, `test_pawn_structure_v044.py` together):
**35/35 green, 0.39s.**

No "kings on the same file" fixture pitfall this time (see
`docs/roadmap.md` V0.3.3/V0.3.4/V0.4.2 for the history of that recurring
bug) — every constructed test position in this file either uses a
single side's pawns with no king-adjacency logic involved, or places the
two kings on different files from the start.

## Benchmark

Quick depth-2 cost check on the initial position (same methodology as
V0.4.3's checkpoints):

| Pawn structure | Time | Nodes | Move |
|---|---|---|---|
| OFF | 5.57s | 1916 | (1,0)→(2,2) |
| ON | 5.43s | 1916 | (1,0)→(2,2) |

**Essentially free** — within normal run-to-run noise, identical node
count and chosen move. Unlike V0.4.3's mobility term (which needed a
pseudo-legal rewrite in beta-4 to become cheap), pawn structure was
cheap from the start: it's a simple O(pieces-on-board) scan checking
adjacent squares, no move generation involved at all.

No playing-strength benchmark attempted this checkpoint (consistent with
keeping each checkpoint small) — same honest-non-result situation
V0.4.1 documented: a real signal needs self-play or human-vs-engine
games, not a cost benchmark.
