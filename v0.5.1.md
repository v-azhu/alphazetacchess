# AlphaZetaChess V0.5.1 — Self-Play Game Recording

## Status

**Implemented, tested, smoke-tested end to end. No large-scale data
collection run yet** — see "Next step" below for why that's deliberately
left for a local run rather than attempted in this session.

## Context: why V0.5 exists, and what changed about its scope

`docs/roadmap.md`'s original V0.5 description was one line: "AI vs AI
games, data collection, automatic evaluation and training dataset
generation." When V0.4.5 completed V0.4's original five evaluation
terms, the open question was where Endgame Knowledge and Opening
Knowledge (also originally listed under V0.4) should go. **Decision:**
learn them from self-play data rather than hand-coding them, and fold
them into V0.5 rather than adding a V0.4.6/V0.4.7. This document is the
first concrete step toward that: before any opening book or endgame
heuristic can be learned from self-play, self-play games need to
actually be recorded in enough detail to mine later.

## Design

`src/alphazetacchess/selfplay/recorder.py`:

- `play_recorded_game(engine_red, engine_black, max_moves, red_config=None, black_config=None, board=None)`
  — plays one full game move by move (reusing the exact same
  `Rule.is_game_over` / `SearchEngine.choose_move` / `Board.move` calls
  `tools/benchmark.py`'s `play_game` already uses for win-rate
  benchmarking), but records every move instead of only the final
  winner. Returns one JSON-serializable dict per game (a "record").
- `append_record(path, record)` / `load_records(path)` — JSON-lines
  file I/O. Append-only by design: repeated runs accumulate data over
  time rather than overwriting, since self-play data collection is
  meant to happen across many sessions, not one big batch.

Record shape:
```json
{
  "red_config": {"depth": 2, "use_mobility": false, "use_pawn_structure": false, "use_piece_coordination": false},
  "black_config": {...},
  "result": "RED_WINS" | "BLACK_WINS" | "DRAW",
  "total_moves": 47,
  "moves": [{"color": "RED", "from": [1, 2], "to": [4, 2]}, ...],
  "recorded_at": 1735689600.0
}
```

`tools/self_play.py`: a CLI wrapper (`python tools/self_play.py --games
20 --depth 2 --output data/selfplay.jsonl`, plus `--use-mobility` /
`--use-pawn-structure` / `--use-piece-coordination` flags matching
`SearchEngine`'s own toggles) that runs N games with a given
configuration on both sides and appends each record to a file as it
finishes — so a long run's progress is never lost even if interrupted
partway through, unlike a design that only wrote output at the end.

`data/README.md` explains the directory; `data/*.jsonl` is gitignored
by default (regenerable, grows over time) with a note that a specific
corpus can always be committed deliberately if you want to preserve it.

### Why `board=None` was added to `play_recorded_game`

Not originally planned, but a genuinely useful test-support addition:
letting a test start from a pre-constructed position (e.g. a forced
mate one move away) makes decisive-game tests fast and fully
deterministic, instead of waiting on a real game to eventually produce
a decisive result. Used by
`test_a_decisive_forced_mate_game_records_the_correct_winner_and_moves`
below.

## Correctness gates (`tests/test_selfplay_recorder_v051.py`, 5 tests)

1. `max_moves=0` gives an immediate, fully deterministic `DRAW` record
   with zero moves — the fastest way to exercise the move-limit path.
2. Record shape: exact key set, config dicts stored correctly,
   `recorded_at` is a float timestamp.
3. **A decisive forced-mate game records the correct winner and exact
   move** — reused the same box-in-the-king fixture pattern from
   `tests/test_search_v033.py`, with `board=` letting the test start
   one ply from mate instead of playing a full game. Caught a genuine
   test-authoring mistake while writing this: `SearchEngine.choose_move()`
   returns a `SearchResult` (uniform across all engines, see
   `engine/base.py`), not a bare `Move` — `recorder.py`'s first draft
   tried to read `.from_pos` directly off the `SearchResult` and
   crashed immediately. `tools/benchmark.py`'s existing `play_game`
   already had this right (`result.best_move.from_pos`); fixed to
   match.
4. `append_record`/`load_records` round-trip two records correctly.
5. Three separate `append_record` calls accumulate to three records,
   confirming append-only behavior (not overwrite-on-each-call).

Combined with every other targeted V0.4.x/V0.5.x test file: **51/51
green, 0.39s.**

## Smoke test (this session, small and fast)

```
python tools/self_play.py --games 2 --depth 1 --max-moves 20 --output /tmp/selfplay_smoke.jsonl
  game    1/2: DRAW        ( 20 moves,   10.9s)
  game    2/2: DRAW        ( 20 moves,   11.1s)
Done in 22.0s.
```

Confirmed the output file has 2 well-formed records with the expected
keys, correctly recorded move sequences, and the correct configuration
dict. This was `depth=1` specifically to keep the smoke test fast and
deliberately not representative of real data-collection speed.

## Performance note (why no real data collection run happened this
session)

At `depth=2` (the default, and the more realistic choice for anything
meant to represent real playing strength), individual games have
historically taken 1-3+ minutes depending on how decisive they are (see
`docs/v0.3.4.md`, `docs/v0.4.3_beta3-results.md` for related per-move
timing data across this project). Collecting a data set large enough to
be useful for an opening book or endgame heuristic (dozens to hundreds
of games) is therefore squarely a **local, long-running task**, not
something to attempt inside a single interactive session — consistent
with how every other genuinely slow operation in this project (full
pytest suite, multi-position benchmark sweeps) has been handled: build
and verify the tool here, run the slow part locally.

## Next step

**Locally:** run a real batch, e.g.
```bash
python tools/self_play.py --games 20 --depth 2 --output data/selfplay.jsonl
```
This can be re-run repeatedly (records accumulate) and with different
`--use-*` flags to build up a mixed corpus, or a matched one if you want
data specific to a particular evaluation configuration. No need to
watch it — it appends progress as it goes, so even an interrupted run
leaves usable partial data.

**Here, once there's real data to work with:** V0.5.2 (a simple opening
book: analyze recorded move-1/move-2/... win rates and use the book for
early moves instead of searching) is the natural next increment, and
doesn't require a huge data set to prototype against — even a few dozen
games is enough to build and test the *mechanism*, with book quality
improving as more data accumulates over time.
