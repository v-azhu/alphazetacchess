# AlphaZetaChess V0.5.2 — Opening Book from Self-Play

## Status

**Implemented, tested, smoke-tested end to end (self-play → book →
book-driven move). No book built from a real, large self-play corpus
yet** — this session's self-play runs were small smoke tests; a real
book should be rebuilt once a meaningful `data/selfplay.jsonl` exists
(see V0.5.1's local-run instructions).

## Design

`src/alphazetacchess/selfplay/opening_book.py`:

- **Keyed by (Zobrist hash, color to move), not move sequence.**
  Transpositions (different move orders reaching the same position)
  share statistics instead of being tracked separately — `Board.
  zobrist_hash` already exists and is exactly the right key.
- `build_book_from_records(records, max_ply=20)` replays every
  recorded game's move list through a fresh `Board`, and for the first
  `max_ply` half-moves accumulates per-position, per-move
  `{wins, draws, losses, games}` counts.
- `select_book_move(book, board, color, min_games=3)` picks the move
  with the best score (`wins + 0.5*draws) / games`) among moves with
  at least `min_games` samples at that position, or `None` if there's
  no entry or nothing meets the threshold.
- `save_book`/`load_book`: plain JSON (position keys are strings —
  `f"{zobrist_hash}-{color.name}"` — since JSON object keys must be
  strings; a Python dict with tuple/int keys wouldn't round-trip).

**Deliberately simple move selection** (frequentist win-rate, no
confidence interval, no UCB-style exploration bonus): with a small
self-play corpus, extra statistical sophistication would mostly be
noise on noise. Worth revisiting once there's a genuinely large corpus
where the difference between "3 games, all wins" and "300 games, 80%
wins" actually matters for move selection confidence.

`tools/build_opening_book.py`: CLI (`--input`, `--output`, `--max-ply`)
that loads records via V0.5.1's `load_records`, builds the book, and
saves it — the glue between `tools/self_play.py`'s output and a usable
book file.

### SearchEngine integration

`SearchEngine(..., use_opening_book=False, opening_book=None,
opening_book_min_games=3)`. `opening_book` takes an already-loaded book
dict (via `selfplay.opening_book.load_book(path)`), not a file path —
`SearchEngine` doesn't do file I/O itself, so the same loaded book can
be reused across many `SearchEngine` instances (e.g. self-play games,
or repeated web UI games) without re-reading the file each time.

`choose_move()` checks the book FIRST, before generating legal moves
for the normal search path. If `select_book_move` returns a confident
move, it's validated against the position's actual current legal moves
(defensive — in case the book was built against a different rule-engine
version) and returned immediately as a `SearchResult` with
`from_book=True`, `score=None`, `nodes_evaluated=0` — search never
runs for that ply. If there's no confident book entry, execution falls
through to the exact same search path as before, unchanged.

`SearchResult` (in `engine/base.py`) gained a `from_book: bool = False`
field (defaulted, so every existing positional `SearchResult(...)`
construction across the codebase keeps working unchanged) so callers
(the web UI, `tools/benchmark.py`, etc.) can distinguish "this move
came from the book" from "this move came from search" without guessing
from `score is None`.

## Correctness gates (`tests/test_opening_book_v052.py`, 9 tests)

1. Building a book from records correctly counts games/outcomes per
   move at a position.
2. `max_ply` is respected — moves beyond it aren't recorded.
3. Move selection prefers the higher-win-rate candidate among moves
   that both meet `min_games`.
4. Returns `None` when the only candidate is below `min_games`.
5. Returns `None` for a position never seen in the book.
6. Save/load round-trips exactly.
7. `SearchEngine` uses the book move when confident (`from_book=True`,
   `nodes_evaluated=0` — search genuinely didn't run).
8. `SearchEngine` falls back to real search when the book isn't
   confident enough (`from_book=False`, a real move still comes back).
9. `SearchEngine` ignores the book entirely when `use_opening_book=False`.

Combined with every other targeted V0.4.x/V0.5.x test file: **60/60
green, 1.42s.**

## Smoke test (this session)

```
python tools/self_play.py --games 3 --depth 1 --max-moves 10 --output /tmp/smoke_selfplay.jsonl
python tools/build_opening_book.py --input /tmp/smoke_selfplay.jsonl --output /tmp/smoke_book.json --max-ply 4
```
Produced a 4-position book with correct per-move stats (3 games, 3
draws recorded against the one opening move a fully deterministic
depth-1 engine happened to play every time). Confirms the full
self-play → book pipeline works end to end; not meant to be a useful
book itself (too small, too deterministic to show real move variety).

## Known limitation

A `depth=1`, fully-deterministic `SearchEngine` playing itself always
makes the same moves, so a book built purely from that kind of data has
no real move diversity to choose between — every position it knows
about has exactly one candidate move. A useful book needs either (a)
higher search depth (still deterministic, but the position tree
naturally branches more as material trades happen and both sides start
diverging), (b) some intentional randomization in move selection during
data collection (e.g. sampling among near-equal top moves instead of
always taking the single best), or (c) simply more games at a depth
where results aren't always identical. Not implemented this checkpoint
— worth deciding once there's a real corpus and it's clear whether (a)
alone is enough or (b) is actually needed.
