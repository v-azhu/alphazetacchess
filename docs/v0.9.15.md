# V0.9.15 — Quiescence Search A/B Diagnostic

## Goal

V0.9.13/V0.9.14 showed that the engine's selected root moves are often stable while evaluation scores can change substantially between depths.

V0.9.15 does not modify the search algorithm. It isolates one possible source of that instability: Quiescence Search (QS).

The benchmark compares the current search with:

- use_quiescence=False
- use_quiescence=True

All other relevant SearchEngine defaults remain unchanged, and Null Move is explicitly disabled for this diagnostic.

## Files

- tools/benchmark_quiescence.py — A/B benchmark over the existing stability positions plus the three tactical regression fixtures.

No engine implementation is changed in V0.9.15.

## Positions

The benchmark covers:

1. initial
2. open_position
3. tactical_exchange
4. mate_in_one
5. free_capture
6. exchange_trap

The first three are reused from the V0.9.13 search-stability benchmark. The last three are the independently checkable tactical fixtures from V0.9.14.

## Run

From the repository root:

```powershell
python tools/benchmark_quiescence.py --depths 2 3 4
```

If the runtime is acceptable, extend the comparison:

```powershell
python tools/benchmark_quiescence.py --depths 3 4 5
```

## What to look for

The important signals are not simply whether QS is better.

### 1. Best-move difference

move_same=False means QS changes the selected root move at that depth.

This is a stronger diagnostic signal than a score difference alone because the engine actually makes a different decision.

### 2. Score difference

score_delta is:

```
QS ON score - QS OFF score
```

Large or repeatedly changing deltas indicate that the horizon extension is materially affecting the evaluation.

A large score delta with the same best move is not automatically a bug.

### 3. Tactical positions

The V0.9.14 objective properties remain useful:

- mate_in_one should select an immediate mate;
- free_capture should select the objectively safe capture;
- exchange_trap should avoid the immediately recapturable capture.

The V0.9.15 script is primarily an A/B diagnostic, so it does not replace those objective checks.

### 4. Node/time cost

QS ON will normally search more nodes because it continues tactical capture sequences beyond the nominal depth.

The useful comparison is therefore both tactical/score behavior and node/elapsed-time cost.

## Interpretation matrix

| Observation | Main layer to investigate |
| --- | --- |
| QS ON changes the move on tactical positions and improves the objective result | QS is materially involved; inspect its tactical extensions |
| QS ON changes the move but does not improve the objective result | QS may be amplifying an evaluation or move-ordering problem |
| QS ON/OFF produce the same unstable score pattern | Look beyond QS: evaluation, TT/PVS, or horizon behavior |
| QS ON changes scores but root moves remain stable | Score instability may be less important than it first appears; inspect score semantics before changing search |
| QS ON is much slower with little decision impact | QS implementation/performance becomes a candidate for optimization |

These are diagnostic hypotheses, not conclusions. The benchmark result should determine the next code change.

## Current implementation details relevant to the A/B

The current SearchEngine performs legal move generation before entering the depth-0 QS path. At depth zero, QS then generates legal moves again.

QS itself currently:

1. probes the transposition table at depth 0;
2. generates legal moves;
3. handles terminal positions;
4. stops at quiescence_max_ply;
5. if in check, searches all legal evasions;
6. otherwise evaluates the stand-pat position;
7. searches captures recursively;
8. stores a depth-0 TT result.

These details are recorded here because they are potential follow-up targets only after the A/B measurement identifies QS as relevant.

## Next checkpoint

Run the A/B benchmark at depths 2-4 first.

If the result clearly implicates QS, the next step should be a focused correctness review of:

- stand-pat behavior;
- capture-only continuation;
- check-evasion handling;
- q-ply termination;
- depth-0 TT bound semantics;
- duplicated legal-move generation around the depth-0 transition.

If QS does not explain the instability, do not modify QS merely for the sake of another version number. Move the investigation to evaluation/search-score semantics or TT/PVS behavior.
