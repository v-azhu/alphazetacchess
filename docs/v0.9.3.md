# V0.9.3 — Heuristic-Informed MCTS Priors

## Status

**IMPLEMENTED, tested, and benchmarked** (294/294 full suite green). Picked as the
next V0.9 increment per `docs/v0.9.2.md`'s own "practical implication": V0.6.1's
uniform move priors (`1/N`, no policy network yet) were identified as the more
consequential remaining gap after V0.9.2's decisive MCTS-vs-SearchEngine result, more
so than further fixed-prior MCTS tuning. This is not a trained policy network -- it's
the cheapest real non-uniform prior available without one, and a genuine first data
point on whether "better priors" is a promising direction at all before investing in
anything more expensive.

## Design

`_MCTSNode.prior` (V0.6.1's own module docstring: "uniform... for now... exactly the
parameter a future policy network would replace") gets its first real, if crude,
non-uniform source: `MCTSEngine._heuristic_priors(board, color, legal_moves)` makes
each candidate move, evaluates the resulting position from the *mover's own*
perspective (`evaluate(board, color)` after the move already means exactly "how good is
this for `color`" -- no negation needed, since `color` is still whoever is choosing
among these moves regardless of whose turn `board` reports after the move), undoes it,
and softmax-normalizes the resulting scores into a probability distribution. Always
restores `board` via `move()`/`undo()` around each candidate, matching `_simulate`'s own
restoration promise.

`use_heuristic_priors=False` (default) reproduces V0.6.1's exact uniform-prior behavior
bit-for-bit -- `_expand_and_evaluate` only calls `_heuristic_priors` when the flag is
on, otherwise computing `1/N` exactly as before. `prior_temperature=200` (two pawns'
worth) scales `evaluate()`-style points into the softmax's exponent, in the same
"principled first guess, not yet independently tuned" spirit as `value_scale=500`'s own
comment -- not tuned separately from that constant in this checkpoint.

**This has no correctness invariant the way `SearchEngine`'s ordering features do.**
V0.8.2's killer moves and V0.8.3's MVV-LVA are provably identical-result regardless of
ordering, because alpha-beta explores exhaustively; MCTS is inherently an approximate,
sampling-based algorithm, so a different prior genuinely can and does change which move
ends up with the most root visits -- that's the entire point of a policy prior, not a
bug to test against. Testing focuses instead on: the off-path being bit-for-bit
unchanged, the on-path actually producing a valid, meaningfully-peaked probability
distribution that rates a free-piece capture far above quiet moves in a constructed
position, board-mutation safety, and `eval_fn` override respect (mirroring
`SearchEngine`'s own `eval_fn`/`material_values` override-respect tests).

## Correctness

7 new tests (`tests/test_mcts_heuristic_priors_v093.py`): default reproduces uniform
priors exactly, heuristic priors rate a winning capture meaningfully (not just
marginally) above quiet moves in a hand-built fixture, the result is a valid probability
distribution (positive, sums to 1), the board is left unmutated, `eval_fn` is actually
read (a constant-returning fake eval_fn must degrade the distribution back to uniform --
confirms the override isn't silently ignored), `_expand_and_evaluate` is actually wired
to `_heuristic_priors` (not just correct in isolation), and a full `choose_move` call
doesn't crash and returns a legal move. Full suite: **294/294 green.**

## Benchmark: a real speed cost, and whether it's worth it

**Speed cost** (200 simulations, starting position, same machine): uniform priors run
at ~1386 simulations/sec; heuristic priors run at ~534 simulations/sec -- **roughly
2.6x slower**, from the extra `len(legal_moves)` `evaluate()` calls added at every
single node expansion (once per simulation).

**Does the quality gain outweigh that cost?** Two real comparisons, both via
`tools/compare_engines.py --a-engine mcts --a-use-heuristic-priors --b-engine mcts`
(`--a-use-mobility`/etc. left at defaults on both sides):

**Equal simulation count** (200 vs. 200, `data/v0.9.3_heuristic_vs_uniform_priors.jsonl`,
24 games run in two batches):

```
Heuristic priors: 18 wins
Uniform priors:    6 wins
Score rate: 75.0%
95% CI: [57.7%, 92.3%]
Estimated Elo diff: +191
```

Entirely above 50% -- a clear, statistically real win when simulation count is held
equal, confirming the prior information itself is useful to PUCT's selection formula
(unsurprising in principle, since `_select_child`'s `u` term uses `child.prior`
directly, but this is the first time this project has actually measured it).

**Equal wall-clock time** (200 heuristic-prior sims vs. 520 uniform-prior sims -- 520
matched to the ~2.6x speed ratio above, `data/v0.9.3_heuristic_vs_uniform_equal_time
.jsonl`), the practically relevant question, run in four batches of 12 as more
confirmatory evidence was gathered (final total: 48 games):

```
Heuristic priors (200 sims): 30 wins
Uniform priors (520 sims):   18 wins
Score rate: 62.5%
95% CI: [48.8%, 76.2%]
Estimated Elo diff: +89
p = 0.083 vs. a 50% null (not significant at the conventional 0.05 level)
```

Worth being transparent about the path here, not just the final number: after the first
two batches (n=24) this read 62.5%, CI [43.1%, 81.9%]. A third batch pushed the running
total to n=36 at 69.4%, CI [54.4%, 84.5%], p=0.02 -- independently significant. A fourth
batch then pulled the combined total back down to exactly 62.5% again (n=48) -- the
third batch's apparent significance did not hold up, and the *point estimate* is
remarkably stable across the two 24-game halves (15/24 then 15/24 again, exactly) even
though the CI briefly looked tighter than it should have in between. This is a
concrete, real instance of why treating an interim result as final ("it just crossed
p<0.05, stop here") is a mistake -- the honest number is the one from the complete,
pre-committed sample, not whichever partial total happens to look cleanest. The stable
~62.5% point estimate across independent halves is itself informative (a real central
tendency, not just sampling noise around 50%), but the CI's current lower bound (48.8%)
means this specific comparison, on its own, still doesn't independently clear
conventional significance -- "leans real and positive, not yet confirmed" remains the
honest read, not "confirmed" and not "settled negative" either.

**This does not close the earlier gap to `SearchEngine`.** A quick check
(`--a-engine mcts --a-simulations 200 --a-use-heuristic-priors --b-depth 2`, 4 games)
still went 0-4 -- heuristic-prior MCTS remains far behind `SearchEngine` at depth 2,
consistent with `docs/v0.9.2.md`'s finding that the gap is large enough that a
cheap, one-ply-lookahead prior alone isn't going to close it. What this result *does*
show is that the prior-quality direction itself is a real, measurable lever on MCTS's
own internal strength, not a dead end -- exactly the question this checkpoint set out
to answer before considering anything more expensive (a real trained policy network).

## Decision: `use_heuristic_priors=False` default

The equal-simulation-count result is unambiguous; the practically-relevant equal-time
result leans clearly positive (a stable ~62.5% point estimate across independent
batches, see the transparency note above) but doesn't independently clear conventional
significance even at the fuller n=48 (CI lower bound 48.8%, just under 50%, p=0.083).
Per this project's standing "off until
proven" rule -- the same bar that kept V0.6.4's combined calibrated weights off until
V0.6.5's larger, more clearly significant result justified promoting them -- this stays
off by default pending a larger confirmatory run, rather than being promoted on the
strength of a promising-but-not-fully-conclusive equal-time result alone. Available via
`--{prefix}-use-heuristic-priors` in `tools/compare_engines.py` for that future run.

## Scope boundary

No trained policy or value network -- this is a fixed, hand-designed heuristic (softmax
over one-ply `evaluate()` lookahead), not learning. `prior_temperature` is not
independently tuned from `value_scale` in this checkpoint; both remain first guesses.
Does not touch `SearchEngine` at all. A real policy/value network remains the larger,
separate undertaking this checkpoint was meant to inform a go/no-go decision on, not
replace -- the positive equal-simulation-count result is a real, if modest, signal that
investing further in the "better priors" direction (up to and including a trained
network) is worth pursuing rather than a dead end, but this checkpoint alone doesn't
settle how far that investment should go.
