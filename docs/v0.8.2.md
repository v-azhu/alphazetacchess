# V0.8.2 — Killer Move Ordering

## Status

**IMPLEMENTED, tested, and benchmarked in this session** (266/266 full suite green).
No doc existed for this sub-version prior to the V0.7/V0.8 merge review — the code,
tests, and `tools/benchmark_killer_moves.py` had all landed on
`dev/v0.8.1-attack-detector`, but the benchmark itself had never actually been run, and
no design/acceptance doc had been written. This doc closes that gap retroactively,
following the project's own documented convention (`docs/roadmap.md`'s "Progress
Tracking / Handoff" section) that every sub-version gets a doc with real measured
evidence before being considered complete.

## Goal

Reduce Alpha-Beta node counts by trying moves that previously caused a beta cutoff at
the same search ply before other quiet moves, on the well-established heuristic that a
move which refuted a sibling position is disproportionately likely to also be strong in
the current one.

## Design

`engine/killer_moves.py`: `KillerMoves`, a two-slot table keyed by ply. `record(ply,
move)` stores a *quiet* move that caused a beta cutoff (captures are deliberately never
stored — see below); `get(ply)` returns the stored killer keys, most recent first.
`SearchEngine` owns one `KillerMoves` instance, clears it at the start of every
`choose_move()` (same lifecycle as `nodes_evaluated`/TT stats — a search-local
structure, not one that should leak moves from an unrelated position), and records a
killer whenever `_negamax` finds `alpha >= beta` from a quiet move. Controlled by
`use_killer_moves` (default `True` — justified below), independent of every other
`use_*` toggle.

### Why captures are excluded

Captures already have their own ordering signal (recapture value at the node itself);
a killer table entry that happens to share a from/to square with a *now-different*
capture on this move) is not "the same tactical idea" and must not be trusted just
because the coordinates match. `_order_moves` enforces this explicitly: a stored killer
key only promotes a candidate move if that candidate is currently non-capturing,
regardless of what the move was when the killer was recorded. This is the exact
scenario `tests/test_killer_moves.py::test_stale_capture_matching_a_killer_is_not_prioritized`
targets.

## Correctness

6 new tests (`tests/test_killer_moves.py`), covering: two-slot capacity + most-recent-first
promotion, captures never recorded, quiet killers ordered before other quiet moves, a
stale killer whose coordinates now match a capture is *not* prioritized, and that
`SearchEngine` returns the identical score/best-move with `use_killer_moves` on vs off
(move ordering must never change the *result*, only the path taken to it — the same
invariant every prior ordering/pruning feature in this project has been held to). Full
suite: **266/266 green.**

## Benchmark: the packaged tool's fixture is misleading; the reference positions are not

`tools/benchmark_killer_moves.py` ships with one hand-built 8-piece "midgame" fixture.
Run in this session (`--depth 3 --runs 3` and `--depth 4 --runs 3`, Killer OFF vs ON,
identical score/move confirmed both times — correctness holds):

| Depth | Killer OFF nodes | Killer ON nodes | Node change |
|---|---|---|---|
| 3 | 1169 | 1724 | **+47.5%** (worse) |
| 4 | 3469 | 4998 | **+44.1%** (worse) |

Taken at face value, this looks like a real regression, and the tool's own
`--depth 3 --runs 5` default would report it as one. Rather than trusting a single
fixture (the project's established practice — see `docs/v0.4.3_beta3-results.md`'s
mobility cost investigation and `docs/v0.6.2.md`'s repeated "don't trust one number"
pattern), the same on/off comparison was run against `tools/benchmark_search.py`'s three
existing reference positions (`initial`, `early_development`, `central_development`,
depths 2-3, the same positions every prior search-layer feature in this project has been
benchmarked against since V0.3.1):

| Position | Depth | OFF nodes | ON nodes | Node change | Same score/move |
|---|---|---|---|---|---|
| initial | 2 | 1921 | 1099 | **-42.8%** | yes |
| initial | 3 | 6955 | 5842 | **-16.0%** | yes |
| early_development | 2 | 816 | 845 | +3.6% | yes |
| early_development | 3 | 6300 | 4364 | **-30.7%** | yes |
| central_development | 2 | 425 | 460 | +8.2% | yes |
| central_development | 3 | 4918 | 2124 | **-56.8%** | yes |

**Conclusion**: on real, previously-established reference positions, killer-move
ordering gives a genuine, sometimes large (16-57%) node reduction at depth 3, with a
small (under 10%) overhead at depth 2 — consistent with the same "needs enough
remaining tree depth to pay back its own probing cost" pattern `docs/v0.3.3.md` already
documented for PVS. Best move and score are identical in every case tested.
`docs/v0.8.2-benchmark.md`-style raw output is not being added as a separate file since
the table above already carries the full data; see git history of this doc for the
session that produced it if the raw run output is needed later.

The packaged fixture's apparent regression is explained, not contradicted, by this: it
is a tiny 8-piece position with very few quiet moves per node, so the killer table's
own bookkeeping cost is paid on almost every node while rarely being amortized by a
cutoff it enables — a real, reproducible property of *that specific fixture*, not of the
feature in general. **The fixture is not being changed in this doc** (that is a
`tools/benchmark_killer_moves.py`-owned decision), but future readers of that tool's
output should cross-check against the reference-position table above before concluding
killer moves hurts performance.

## Decision: `use_killer_moves=True` default is justified

Unlike V0.4.3-4.5/V0.5.x/V0.6.x's evaluation-layer toggles (which default `False` until
a *playing-strength* benchmark justifies flipping them), killer-move ordering is a
move-ordering-only change with a strict, tested correctness invariant (identical
score/best-move on/off, enforced by `test_killer_moves_preserve_search_result`) — the
same class of feature as the transposition table (V0.3.2) and PVS (V0.3.3), both of
which also default on. The reference-position benchmark above gives this the same kind
of measured evidence those features had before defaulting on. Defaulting `True` is
therefore consistent with, not an exception to, the project's "measure before trusting a
default" rule — it is being held to the ordering-feature bar, not the
evaluation-feature bar.

## Scope boundary

V0.8.2 does not introduce history heuristic, SEE/MVV-LVA capture ordering, or any
change to evaluation. Those remain open items for a later V0.8.x step per
`docs/v0.8.1.md`'s own scope boundary.
