## Goal

Provide one registered, replay-validated match path for in-process `SearchEngine` instances
and external UCI/UCCI processes. Strength decisions use the V0.11.0 §6.2 SPRT gates, not
depth or node counts. Opening pairs start from a shared Red-to-move position and swap engine
colors across the two games.

## Design

### SPRT

`src/alphazetacchess/selfplay/sprt.py` is a pure-Python module. Pair scores are
`{0, 0.5, 1, 1.5, 2}`; game W/D/L probabilities are derived from the standard Elo logistic
expected score and a fixed draw-rate nuisance parameter, then convolved into the pentanomial
pair distribution. The sequential log-likelihood ratio uses Wald bounds with alpha = beta = 0.05.

Named presets are G1 (-10 vs 0 Elo, 8,000-game cap), G2 (0 vs +10 Elo, 8,000-game cap), and
G3 (+50 vs +150 Elo, 1,000-game cap). Reaching a gate cap or exhausting the configured opening
set without crossing a bound is INCONCLUSIVE, never a pass. A constant stream of 20 identical
pair outcomes is marked INCONCLUSIVE with a zero-observed-variance reason rather than treated
as calibrated evidence.

The test suite includes an independent direct LLR calculation and two fixed-seed Monte Carlo
operating-characteristic tests with 10,000 simulated tests each. The calibration tests use a
16,000-game cap to measure the nominal boundary behavior; production gates retain the exact
V0.11.0 caps.

### Runner

`tools/match.py` records a registration before the first game, writes JSONL game records,
replays every completed game for legality/result validation, and writes a manifest containing
opening and config hashes, engine/binary hashes where available, revision, machine metadata,
CPU affinity, a reference-NPS calibration, per-game load samples, and SPRT outcome. A JSONL
registration ledger prevents rerunning the same registration under a new output filename after
INCONCLUSIVE or ACCEPT_H0 unless the code revision changes.

The runner accepts the paired-opening format `{initial_fen, opening_prefix}`. Python engines use
the existing `SearchEngine`; UCI engines reuse the existing `PikafishClient` transport, and UCCI
uses the same runner-facing adapter interface. Move history since the paired starting position
is sent on each process-engine search so the engine can replay the current game position.

### Fixed-sample workers

For `--fixed-pairs N --workers W`, the runner partitions the selected opening pairs deterministically
across up to W isolated worker processes. Each worker owns its own engine instances, records its CPU
affinity and machine/load metadata, and closes its external engines when its chunk finishes. Results
are written as JSONL as worker chunks complete; pair scores in the manifest are sorted by opening
index. Partial game records and worker errors are retained when a chunk fails.

Parallel execution is intentionally restricted to fixed-sample mode. A conventional sequential SPRT
must update its likelihood ratio and stop at the first boundary crossing; scheduling several opening
pairs ahead can change the stopping behavior or create unaccounted post-boundary games. Therefore
SPRT runs still require `--workers 1`. The worker path is implemented but remains **unverified until
the focused and full test suites and a real multi-worker smoke test pass**.

Current implementation limitations (not acceptance passes):
- The worker path is fixed-sample only; sequential SPRT remains serial to preserve exact Wald stopping
  semantics. Physical-core enforcement fails closed to one worker when physical-core detection is
  unavailable (for example, when optional `psutil` is not installed).
- The six legacy comparison entry points delegate to `tools/match.py` and are safe to import
  without parsing CLI arguments. Their experiment-specific legacy CLI flags have been retired;
  use the unified options. `compare_null_move_paired.py` retains its `TimedSearch` helper for
  existing regression tests and callers.
- Node limits are available to UCI processes only; the current UCCI protocol does not accept
  `go nodes`, and in-process Python node limits are intentionally rejected.
- The UCI adapter reuses the existing client's startup/handshake and then uses its process
  transport through private attributes; a public search API would be preferable.
- Search-response waits use a queue with a timeout, but the reused PikafishClient startup handshake
  itself has no timeout yet.

## Commands

Install development dependencies and run the focused tests:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q tests/test_sprt_v0111.py tests/test_match_v0111.py
```

Run the complete regression suite before every commit:

```powershell
python -m pytest -q
```

To enable physical-core detection for parallel runs, install the optional dependency:

```powershell
python -m pip install psutil
```

A parallel fixed-sample plumbing smoke test, using two short games per opening pair, is: 

```powershell
python tools/match.py --test-id smoke-parallel --fixed-pairs 2 --opening-count 2 --opening-plies 8 --workers 2 --limit-kind depth --limit-value 1 --a-depth 1 --b-depth 1 --max-moves 2 --output data/smoke-parallel.jsonl
```

This verifies worker startup, CPU affinity where supported, per-game evidence metadata, pair aggregation, and clean engine shutdown; it is not a strength test. The parallel path must be exercised on Windows as well as Linux.

A small serial SPRT-runner plumbing smoke test, using a prepared opening file, is:

```powershell
python tools/match.py --test-id smoke-g2 --gate G2 --openings data/suites/openings_8ply_v1.json --opening-count 1 --limit-kind depth --limit-value 1 --a-depth 1 --b-depth 1 --output data/smoke-g2.jsonl
```

This command is a plumbing smoke test only; one opening cannot calibrate a gate and its result must not be cited as a strength claim. Full acceptance controls and Pikafish calibration remain PENDING OWNER RUN until the runner is validated and the required external binary/network are available.

## Reproducible control commands

The commands below are exact procedures, not results. They remain **PENDING OWNER RUN** until
executed on the owner machine with the prepared opening suite and, for AC1, Pikafish plus its
network. Use a fresh output filename for each run. Each command registers its revision, gate,
engine/config hashes, opening set and seed before the first game.

### AC1 — V0.10/Pikafish reproduction (fixed sample, 20 opening pairs)

```powershell
python tools/match.py --test-id ac1-pikafish-repro --fixed-pairs 20 --opening-count 20 --openings data/suites/openings_8ply_v1.json --seed 11001 --a-kind process --a-protocol uci --a-command "C:\tools\pikafish\pikafish.exe" --a-network-path "C:\tools\pikafish\pikafish.nnue" --b-kind python --a-limit-kind movetime --a-limit-value 500 --b-limit-kind movetime --b-limit-value 500 --output data/ac1-pikafish-repro.jsonl
```

Fixed-sample mode intentionally makes no SPRT acceptance claim; inspect
`candidate_score_rate` and require Pikafish (engine A) to score at least 90% over all 40 games.

### AC2 — Ten independent null-control runs (200 games each)

```powershell
1..10 | ForEach-Object {
  $seed = 12000 + $_
  $id = "ac2-null-{0:D2}" -f $_
  python tools/match.py --test-id $id --gate G2 --opening-count 100 --openings data/suites/openings_8ply_v1.json --seed $seed --a-kind python --b-kind python --a-depth 5 --b-depth 5 --a-limit-kind movetime --a-limit-value 500 --b-limit-kind movetime --b-limit-value 500 --output "data/$id.jsonl"
}
```

The null control uses time-based limits deliberately: identical deterministic engines can produce
identical games at fixed depth, whereas timer scheduling and OS execution timing determine where
each 500 ms search is interrupted, introducing the required run-to-run variation. After all ten
manifests exist, confirm G2 accepted H1 in no more than one run and pool all 2,000 games; the pooled
score must be in 47–53%. Different seeds select different opening samples but do not guarantee
disjointness, so inspect the recorded opening hashes before pooling.

### AC3 — Positive control (500 ms candidate vs 250 ms base)


Expected: `ACCEPT_H1` within 2,000 games. If it does not, preserve the manifest and records as
a negative control result; do not rerun with unchanged registration.

### AC5 — Pikafish node ladder

```powershell
python tools/calibrate_ladder.py --pikafish-path "C:\tools\pikafish\pikafish.exe" --network-path "C:\tools\pikafish\pikafish.nnue" --openings data/suites/openings_8ply_v1.json --output-dir data/ladder-v0111 --adjacent-pairs 100 --baseline-pairs 20 --seed 15001
```

The script tests all ten rungs `{1, 3, 10, 30, 100, 300, 1k, 3k, 10k, 30k}`; each adjacent rung
gets 200 games by default. It also measures V0.10 against every rung at 500 ms and 2,500 ms and
records the first rung scoring below 50%. Expected runtime is **several hours and potentially
overnight**: the baseline probes alone are about 2,000 games, and the 2,500 ms probes dominate
wall time; high-node adjacent-rung games can add substantial time. This is an estimate, not a
measured runtime. Preserve the complete output directory and `ladder-report.json`.
