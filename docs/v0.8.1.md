# V0.8.1 — Specialized Attack Detector

## Purpose

V0.8.1 replaces the search-critical attack query used by `Rule.is_in_check()` with a
specialized position-level detector. The detector answers one narrow question:

> Is square `(x, y)` attacked by `by_color` in the current position?

It must do this without generating `Move` objects and without applying/undoing moves.

The purpose is performance-oriented infrastructure, not a change to search strategy.
The detector must remain behaviorally compatible with the existing move generator for
attack queries used by check detection.

## Existing hot path

The current `Rule.is_square_attacked()` asks `MoveGenerator.generate_moves()` for every
piece of the attacking side and scans the resulting moves for the target square.
`Rule.is_in_check()` calls this for the king square, and `Rule.generate_legal_moves()`
may call `is_in_check()` after every candidate move. Consequently, attack detection is
inside a large legality-filtering hot path.

The existing move generator is deliberately a pseudo-legal move generator; final king
safety is handled by `Rule`.

## Design

`core/attack.py` introduces `AttackDetector` with direct source-square and ray checks:

- rook: scan each orthogonal ray until the first occupied square;
- cannon: scan each orthogonal ray with an explicit one-screen state;
- horse: test the eight possible source squares and their horse-leg squares;
- elephant: test diagonal source squares, elephant-eye occupancy, and river boundary;
- advisor: test the four diagonal source squares and palace boundary;
- king: test the four adjacent source squares;
- pawn: test the forward source square and, after crossing the river, the two horizontal
  source squares.

The detector intentionally does **not** implement the flying-general rule. `Rule` keeps
that position-level check separately through `board.kings_facing()`.

## Correctness strategy

V0.8.1 uses two layers of validation:

1. targeted tests for each piece's attack geometry and blockers;
2. deterministic differential testing against `MoveGenerator` on occupied target squares.

The differential test compares only captures onto an occupied opposing square. This is
intentional: a specialized attack detector defines an actual attack, while a pseudo-legal
move generator also emits non-capturing movement to empty squares.

## Important Xiangqi details

### Cannon

A cannon does not attack a target merely because it has an unobstructed orthogonal ray.
It requires exactly one screen between the cannon and the target. This is handled directly
by the ray state machine rather than by move generation.

### Elephant

An elephant's target must remain on its own side of the river, and its eye must be empty.

### Horse

A horse attack is invalid when its orthogonally adjacent leg square is occupied.

### Pawn

A pawn attacks forward before and after crossing the river. After crossing, it also
attacks horizontally, but never backward.

### Flying general

Flying general is not a piece attack in this detector. It remains an explicit board-level
condition in `Rule.is_in_check()`.

## Scope boundary

V0.8.1 does not introduce:

- killer moves;
- history heuristic;
- SEE/capture ordering;
- aspiration windows;
- LMR or null-move pruning;
- evaluation changes.

Those belong to later V0.8 steps and should not be mixed into this correctness/performance
checkpoint.

## Acceptance gate

The local acceptance sequence is:

```text
pytest tests/test_attack_detector.py -q
pytest tests/test_rule.py -q
pytest -q
```

After correctness is established, compare a fixed search benchmark against the V0.7.4
baseline. Record at minimum depth, best move, score, nodes, elapsed time, and NPS.
A speedup is useful only if the best move/score and regression suite remain stable.
