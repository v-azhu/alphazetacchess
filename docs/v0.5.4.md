# AlphaZetaChess V0.5.4 — Automated Strength Comparison

## Status

**Implemented, tested, smoke-tested end to end.** Answers the exact
question `tools/self_play.py`'s own docstring flagged when it was
written ("V0.5.4's planned strength comparison between
configurations") and that `docs/roadmap.md`'s V0.5.3 hand-off named as
the next increment: given two `SearchEngine` configurations, which one
is actually stronger, and by roughly how much?

## Design

### `src/alphazetacchess/selfplay/strength_comparison.py`

`run_comparison_match(engine_a_factory, engine_b_factory, games,
max_moves, ...)`: plays `games` games between two engine
configurations, alternating which color each plays every game so
neither has a systematic first-move advantage — the same convention
`tools/benchmark.py`'s `run_match` already established for
SearchEngine-vs-RandomEngine. The key design decision is *how* each
game is played: rather than re-implementing a play loop (as
`tools/benchmark.py` does), this reuses V0.5.1's
`recorder.play_recorded_game` directly. Two consequences fall out of
that for free:

1. Every comparison-match game is automatically a valid, complete
   V0.5.1 self-play record — no separate "comparison result" format to
   maintain, and no risk of the two code paths (self-play recording,
   strength comparison) silently diverging over time.
2. `--output` can point at the exact same `data/selfplay.jsonl` corpus
   `tools/self_play.py` writes to, and `tools/build_opening_book.py` /
   `tools/analyze_endgame.py` already consume. A strength-comparison
   run and a self-play data-collection run are not two different
   activities competing for the same limited local compute time — they
   can be the same run.

`estimate_elo_diff(win_rate)`: the same standard log-odds Elo estimate
`tools/benchmark.py` already uses, duplicated rather than imported —
`tools/*.py` scripts are thin CLI wrappers by convention in this
project (see `build_opening_book.py`, `analyze_endgame.py`), never
import targets for `src/` modules, so importing `tools/benchmark.py`
from `src/alphazetacchess/selfplay/` would invert that dependency
direction. `tools/benchmark.py` itself is untouched by this checkpoint
— it already does its one job (a quick SearchEngine-vs-RandomEngine
sanity check) well, and doesn't need generalizing since RandomEngine
has no configuration to compare in the first place.

### `tools/compare_engines.py`

CLI wrapper exposing two independently configurable sides via
`--a-*`/`--b-*` flags (`--a-depth`, `--a-use-mobility`,
`--a-use-pawn-structure`, `--a-use-piece-coordination`,
`--a-use-endgame-heuristics`, mirrored for `--b-*`), plus the shared
`--games`, `--max-moves`, `--output`, and opening-randomization flags
`tools/self_play.py` already established. Prints per-game progress and
a final win/draw/loss + Elo-difference summary, identical in spirit to
`tools/benchmark.py`'s own output.

## Correctness gates (`tests/test_strength_comparison_v054.py`, 8 tests)

1. `estimate_elo_diff` is exactly 0 at a 50% win rate.
2. `estimate_elo_diff` is positive above 50%.
3. `estimate_elo_diff` is `None` at the 0%/100% extremes.
4. `max_moves=0` gives every game an immediate draw (fast,
   fully-deterministic exercise of the aggregate-counting logic,
   reusing the same "zero move limit" trick
   `test_selfplay_recorder_v051.py` established for `play_recorded_game`
   directly).
5. Colors alternate correctly across games, and each side's config is
   stored under the correct `red_config`/`black_config` key in every
   written record — not just "A is always Red."
6. **The one most worth calling out**: a decisive win is credited to
   the correct *configuration*, not just to whoever happened to play
   Red that game. Both games in this test start from the same
   forced-mate fixture (Red mates in one, deterministically); game 0
   has A playing Red (A should win) and game 1 has B playing Red (B
   should win). A naive "winner is whoever played Red" bug — an easy
   mistake to make when generalizing `tools/benchmark.py`'s
   `a_is_red`-tracking logic — would get game 1 backwards and this
   test would catch it immediately.
7. `on_game_complete` fires exactly once per game with the correct
   `(index, a_is_red)` pairs.
8. Omitting `output_path` runs cleanly with no file written (no crash
   from an unguarded `None` path).

Combined with every other targeted V0.4.x/V0.5.x test file: **130/130
green.**

## Smoke test (this session)

```
python tools/compare_engines.py --a-depth 1 --b-depth 1 --a-use-mobility --games 4 --max-moves 30
  → 4/4 draws (move limit), A score rate 50%, Elo diff +0

python tools/compare_engines.py --a-depth 1 --b-depth 1 --games 2 --max-moves 10 --output /tmp/smoke_compare.jsonl
  → records written; tools/analyze_endgame.py --input /tmp/smoke_compare.jsonl
    loaded both records cleanly (0/2 reached endgame, as expected at
    10 moves) -- confirms the cross-tool compatibility claim above
    isn't just theoretical.
```

Both runs used shallow depth/short move limits to keep the smoke test
itself fast; the all-draws outcome is expected at this
depth/move-limit combination (consistent with every other shallow
smoke test in this project, e.g. V0.5.3's own smoke test) and isn't
evidence about either configuration's actual strength — see Known
limitation.

## Known limitation

**No comparison has been run yet at a depth/game-count that would
actually be statistically meaningful.** This checkpoint's job was
building and correctness-testing the *mechanism*; every run above was
deliberately small and shallow (depth=1, ≤30 moves, ≤4 games) purely
to confirm the pipeline works end to end without spending this
session's time budget on a slow real comparison. Real answers to
questions like "does `use_endgame_heuristics` actually help?" or "is
depth=3 meaningfully stronger than depth=2?" require a real local run
— see Next step.

## Next step

**Locally, whenever convenient:**
```bash
# Does V0.5.3's endgame heuristic help?
python tools/compare_engines.py --a-depth 2 --a-use-endgame-heuristics --b-depth 2 --games 20 --output data/selfplay.jsonl

# Is depth=3 meaningfully stronger than depth=2?
python tools/compare_engines.py --a-depth 3 --b-depth 2 --games 20 --output data/selfplay.jsonl
```
Both commands feed `data/selfplay.jsonl`, the same corpus
`tools/build_opening_book.py` and `tools/analyze_endgame.py` already
consume — one real local session covers V0.5.2, V0.5.3, and V0.5.4's
open validation questions at once.

**Here:** with V0.5.1 (recording) through V0.5.4 (strength comparison)
now all in place as mechanisms, the V0.5 line's remaining work is
almost entirely "run real data through the tools that already exist"
rather than new code — a good natural checkpoint to pause new feature
work and let real local runs catch up, or, if continuing here anyway,
`docs/roadmap.md`'s V0.6+ section (neural evaluation / MCTS) is the
next planned major line.

## Addendum (2026-09-05): `--use-opening-book` support added

`docs/v0.5-real-data-checkpoint-2.md` (a real 63-game local batch)
made the opening book substantial enough (1057 positions) to actually
be worth comparing against — but `tools/compare_engines.py` had no way
to enable it on one side. Added `--a-use-opening-book`/
`--b-use-opening-book` plus shared `--opening-book`/
`--opening-book-min-games` flags, wired straight through to
`SearchEngine`'s existing (V0.5.2) `use_opening_book`/`opening_book`/
`opening_book_min_games` parameters — no new mechanism, just exposing
one that already existed but had no CLI path into this tool.

Documented and smoke-tested one real interaction worth knowing about:
opening randomization (on by default) and the opening book aren't
mutually exclusive, but `RandomizedOpeningEngine` wraps the book-aware
engine and can override its book move with a uniformly random one
(default 30% chance per ply, first 10 plies) — fine for general data
diversity, but a comparison specifically meant to isolate the book's
effect should pass `--random-opening-prob 0`. Smoke-tested both the
happy path (book loads, `from_book=True` moves are instant since no
search runs) and the missing-file fallback (clear message, continues
without a book rather than crashing).

No new `pytest` tests added for this addendum specifically — the
underlying `use_opening_book` mechanism is already covered by
`SearchEngine`'s own V0.5.2 test suite; `tools/compare_engines.py`'s
own flags are, like every other `tools/*.py` CLI wrapper in this
project (`build_opening_book.py`, `analyze_endgame.py`,
`self_play.py`), validated by documented manual smoke tests rather
than direct pytest coverage of the script itself.
