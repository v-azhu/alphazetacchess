# V0.8.3 — MVV-LVA Capture Ordering

## Status

**IMPLEMENTED, tested, and benchmarked** (274/274 full suite green). Picked as the
V0.8 continuation per `docs/roadmap.md`'s own hand-off note and `docs/v0.8.1.md`'s
explicit scope boundary ("SEE/capture ordering... belong to later V0.8 steps").

## Goal

V0.8.2 gave quiet moves a way to reuse a sibling's cutoff (killer moves), but captures
still had no explicit ordering beyond whatever order `MoveGenerator` happens to produce
them in. MVV-LVA (Most Valuable Victim - Least Valuable Attacker) is the standard,
cheap-to-compute first pass at capture ordering: try the capture of the most valuable
piece first, and among equally valuable victims, prefer the cheapest attacker (a Pawn
taking a Rook risks less if the capture turns out to be refuted than a Rook taking a
Rook does).

## Design

`SearchEngine._mvv_lva_score(move)` returns `victim_value * 1000 - attacker_value`
using `self.material_values or MATERIAL_VALUES` -- the same override already threaded
through `_evaluate` (e.g. `CALIBRATED_MATERIAL_VALUES` from V0.6.3), so capture ordering
stays consistent with whatever material scale the rest of the engine is using rather
than silently using a different one. `_order_captures_by_mvv_lva` partitions a move
list into captures (sorted by that score, descending) and quiets (left in place), then
returns captures followed by quiets. Controlled by `use_mvv_lva` (default **False** --
see the benchmark section for why this differs from V0.8.2's `use_killer_moves=True`
default).

### Interaction with killer moves (V0.8.2) — ordering, not a rewrite

The desired combined priority when both features are on is the standard
`hash move > captures > killers > other quiets`. V0.8.2's `_promote_killer_moves`
already existed and pulls any matching quiet move to the front of *whatever list it is
given* -- it was never capture-aware because there was nothing to be aware of yet.
Rather than modifying that function (which would have silently changed V0.8.2's
already-shipped, already-tested behavior even when `use_mvv_lva=False`), `_order_moves`
runs killer promotion **first**, unchanged, and then MVV-LVA **second** on top of that
result. Two consequences, both intentional:

- `use_mvv_lva=False` reproduces V0.8.2's exact prior ordering, bit-for-bit -- no
  regression risk for anyone who never turns V0.8.3 on.
- `use_mvv_lva=True` pulls captures ahead of an already-promoted killer, giving the
  standard priority described above, exercised end-to-end by
  `tests/test_move_ordering.py::test_full_priority_order_is_tt_move_then_captures_then_killers_then_other_quiets`.

## Correctness

7 new tests (`tests/test_mvv_lva.py`) plus 1 combined-ordering test
(`tests/test_move_ordering.py`), covering: captures ranked before quiets, higher-value
victim ranked before lower-value victim, equal victim prefers the cheaper attacker, the
TT/preferred move still overrides everything, `material_values` override is actually
read (not silently defaulted), `use_mvv_lva=False` reproduces the untouched prior
order, and -- the same invariant every ordering feature in this project is held to --
identical score/best-move with `use_mvv_lva` on vs off
(`test_mvv_lva_preserves_search_result`). Two pre-existing V0.8.2 tests
(`test_killer_ordering_puts_quiet_killers_before_other_quiet_moves`,
`test_stale_capture_matching_a_killer_is_not_prioritized`) now pin `use_mvv_lva=False`
explicitly, since `SearchEngine`'s default changed and those tests exist to isolate
killer-move behavior specifically, not the combination. Full suite: **274/274 green.**

## Benchmark: a genuinely mixed, position-dependent result

Same methodology as V0.8.2 (`docs/v0.8.2.md`): compare nodes-evaluated with the feature
on vs off, same score/best-move required both times. First, on top of killer moves
(already default on) across the project's established reference positions
(`tools/benchmark_search.py`'s `initial`/`early_development`/`central_development`):

| Position | Depth | Killer-only nodes | Killer+MVV-LVA nodes | Node change | Same score/move |
|---|---|---|---|---|---|
| initial | 2 | 1099 | 1189 | -8.2% (worse) | yes |
| initial | 3 | 4978 | 5412 | -8.7% (worse) | yes |
| early_development | 2 | 845 | 891 | -5.4% (worse) | yes |
| early_development | 3 | 4728 | 5215 | -10.3% (worse) | yes |
| central_development | 2 | 460 | 466 | -1.3% (worse) | yes |
| central_development | 3 | 3478 | 3525 | -1.4% (worse) | yes |

MVV-LVA alone (killer moves off, to isolate) shows the same pattern -- mostly a small
regression, one roughly-flat case:

| Position | Depth | OFF nodes | ON nodes | Node change |
|---|---|---|---|---|
| initial | 2 | 1921 | 1974 | -2.8% |
| initial | 3 | 6955 | 7872 | -13.2% |
| early_development | 2 | 816 | 871 | -6.7% |
| early_development | 3 | 6300 | 6606 | -4.9% |
| central_development | 2 | 425 | 425 | +0.0% |
| central_development | 3 | 4918 | 4762 | +3.2% |

This looked, at first, like a straightforward "doesn't help" result -- and would have
been reported as one, following the same "trust the established reference positions
over a single fixture" reasoning V0.8.2 used. But those three reference positions are
all opening-phase (few or zero captures available near the root; `initial` literally
has none for the first several plies), so before concluding the feature has no value,
the same capture-dense midgame fixture `tools/benchmark_killer_moves.py` uses (the one
V0.8.2 found *misleading* for killer moves, precisely because it's atypically
capture-poor for a killer-move test) was tried here specifically because it is
capture-*rich*:

| Depth | OFF nodes | ON nodes | Node change | Same score/move |
|---|---|---|---|---|
| 3 | 1169 | 741 | **+36.6%** | yes |
| 4 | 3469 | 2181 | **+37.1%** | yes |

**Conclusion**: MVV-LVA's node-ordering overhead (a partition + sort on every node with
at least one capture) is not repaid on quiet opening positions where captures are rare,
but gives a large, real reduction once captures are actually common -- exactly the
condition the technique is designed for, and exactly the condition real middlegame play
spends most of its time in. This is the mirror image of V0.8.2's finding: there, the
packaged fixture *understated* the feature's value because it was unrepresentative in
the other direction (too few *quiet* moves per node to amortize the killer table's
bookkeeping). Both cases are the same underlying lesson --
`docs/v0.4.3_beta3-results.md`'s and `docs/v0.6.2.md`'s "don't trust one number" applies
equally to "don't trust one *kind* of position."

## Decision: `use_mvv_lva=False` default

Unlike V0.8.2's `use_killer_moves=True` (a broad win across every reference position
tested), V0.8.3's evidence is genuinely mixed: a real cost on quiet positions, a real
benefit on tactical ones, and no full-game benchmark yet to say which effect dominates
over an actual game's node budget. Per this project's standing rule --
`docs/roadmap.md`'s Engine Benchmark methodology and every prior "off until proven"
evaluation-layer toggle (V0.4.3 mobility through V0.6.2 neural eval) -- a mixed result
defaults off, not on. This is not a correctness concern (the score/best-move invariant
holds in every benchmark run above); it is purely about whether flipping it on helps or
hurts typical games, which is exactly what is still unresolved.

## Open item for a future step

A `--a-use-mvv-lva`/`--b-use-mvv-lva` flag pair was added to `tools/compare_engines.py`
in this session (alongside a `--{prefix}-no-killer-moves` flag that was missing for
V0.8.2 as well) so that the actual question -- does MVV-LVA help or hurt real games,
net of the opening-phase cost and midgame benefit -- can be settled the same way V0.6.3
settled the material-calibration question: a real `compare_engines.py` run, not a node
count on a handful of fixed positions. Not attempted in this session (no compute budget
for a multi-game self-play run here); this is a clean next step alongside the still-open
V0.6.1 MCTSEngine-strength question and the larger V0.6.3 material-calibration
comparison, all three of which share the same blocker (a real multi-game benchmark
run).
