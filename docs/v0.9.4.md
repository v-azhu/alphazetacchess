# V0.9.4 — Policy Network Infrastructure (Mechanism, Not Yet Trained)

## Status

**IMPLEMENTED and tested** (313/313 full suite green). No real training has happened --
this is deliberately the same "mechanism first" order V0.6.2's `NeuralEvaluator`/
`eval_fn` followed before any real Pikafish-labeled training existed. Picked as the
next V0.9 step because V0.9.3's positive (if not fully conclusive) result made a real
trained policy network a better-justified investment than it was before that
checkpoint, and because a genuinely trained network needs the user's local Pikafish
setup regardless of what infrastructure exists to consume it -- exactly the same
dependency `docs/v0.6.2.md`'s own value network had.

## What this builds

Four new pieces, mirroring the exact shape V0.6.2's value-network pipeline already
established (features -> network -> evaluator -> engine wiring), applied to the policy
side instead:

**`neural/policy_encoding.py`** -- `move_to_policy_index(move, color)`/
`policy_index_to_squares(index, color)`, encoding a move as one of
`POLICY_DIM = 90 * 90 = 8100` (from-square, to-square) indices. Uses the *exact same*
perspective-relative vertical-flip convention `features.py`'s `board_to_features`
already uses for its input planes -- "my" home rank always at the same edge regardless
of color -- so a single canonical policy network only has to learn one orientation,
not two mirror-image ones. `tests/test_policy_encoding_v094.py`'s
`test_mirrored_move_from_black_encodes_to_the_same_index_as_the_red_move` is the direct
analogue of `test_network_v062.py`'s own board-symmetry test, checking the same
easy-to-get-backwards property (flip the coordinate but forget which side "mine" is)
in the move-encoding direction instead of the board-encoding one.

**`neural/policy_network.py`** -- `PolicyMLP`, a small 2-hidden-layer MLP predicting
`POLICY_DIM` logits. Deliberately a **separate** network from `SmallMLP` (the value
network), not a shared trunk with two heads -- zero changes to `SmallMLP`'s
extensively-tested existing code, lower risk for a first checkpoint with no real
training data yet to validate a shared-trunk design against anyway. Trains via ordinary
(unmasked) softmax cross-entropy -- a training example is "Pikafish's actual move was
index K," an ordinary single-target-class classification problem, so illegal-move
logits get pushed down over training the same way any never-correct class does in a
normal classifier, without the loss needing to know the legal-move set for each
training example. Masking only happens at **inference**
(`predict_masked_probs(features, legal_indices)`): softmax computed only over the
legal indices for whatever specific position is being evaluated right now, which is
different for every position and isn't known (or needed) at training time. Verified
this distinction concretely, not just asserted: `test_predict_masked_probs_ignores_
illegal_indices_entirely` sets one "illegal" logit to an artificially enormous value
and confirms it doesn't distort the legal distribution -- illegal logits never enter
the softmax normalization, not just zeroed out afterward.

**`neural/policy_evaluator.py`** -- `NeuralPolicyEvaluator`, wrapping a trained
`PolicyMLP` to match `engine/mcts.py`'s `policy_fn(board, color, legal_moves) ->
{move: probability}` calling convention exactly, mirroring `evaluator.py`'s
`NeuralEvaluator` doing the same for `eval_fn`. Same "fail loudly and clearly at
construction, not with an opaque numpy shape error at first use" guard `NeuralEvaluator`
has for `FEATURE_DIM` mismatches, extended to also check `POLICY_DIM` (a network saved
before a future move-encoding change would otherwise fail confusingly deep inside
`predict_masked_probs` instead).

**`engine/mcts.py`**: `MCTSEngine` gains a `policy_fn=None` parameter, matching
`eval_fn`'s existing pattern. When set, it **takes priority over
`use_heuristic_priors`** (V0.9.3's cheap stand-in) -- a real trained policy is the
whole point that stand-in existed to justify investing in, not something to average
with once one exists. Verified directly, not assumed:
`test_policy_fn_takes_priority_over_use_heuristic_priors` constructs an engine with
*both* set to deliberately conflicting distributions and confirms `policy_fn`'s wins.

## A real, concrete gap found and fixed along the way

`PikafishClient.evaluate_fen` (V0.6.2) has *always* returned `best_move` alongside the
evaluation score -- but `tools/label_positions_with_pikafish.py` was only ever
recording `{fen, score_cp}`, silently discarding it. This wasn't a bug exactly (nothing
needed `best_move` before this checkpoint), but it's exactly the kind of latent gap that
only becomes visible once you go looking for it with a real purpose in mind -- real
policy-network training needs "what move did Pikafish actually play here," and that
data was never being kept. Fixed: the tool now records `{fen, score_cp, best_move}`.
**Existing `data/pikafish_labels.jsonl` records predate this fix and don't have a
`best_move` field** -- they would need relabeling (re-running Pikafish on the same
positions) to become usable for policy training, since the move choice isn't
derivable from the score alone.

## Scope boundary -- what this is not

**No training has happened.** `PolicyMLP` instances in every test are randomly
initialized, never trained on real data -- this checkpoint validates the *mechanism*
(encoding is correct and symmetric, backprop is mathematically correct, masking is
sound, the wiring into `MCTSEngine` actually takes priority when it should), not
playing strength. There is no `tools/train_policy_network.py` yet (the natural next
step, mirroring `tools/train_neural_eval.py`, once relabeled `best_move`-including data
exists) and no real strength comparison, because there is nothing trained yet to
compare. `SmallMLP` and `PolicyMLP` remain two separate networks rather than a shared
value+policy trunk -- a reasonable follow-up once there's an actual trained result to
weigh a bigger architecture change against, not attempted here.

## Concrete next steps, in dependency order

1. **Relabel a real corpus with `--output` pointed at a fresh file** (or accept that
   pre-V0.9.4 `data/pikafish_labels.jsonl` records can't be reused for this) --
   needs the user's local Pikafish, the same one-time dependency V0.6.2's value network
   already had.
2. **Write `tools/train_policy_network.py`**: parse each labeled position's FEN back
   into a `Board`, generate legal moves, convert `best_move` (the UCI/ICCS move string
   `PikafishClient` returns) to a `policy_encoding` index via the position's side to
   move, and train `PolicyMLP` on `(features, target_index)` pairs -- straightforward
   given everything else in this checkpoint, not attempted here since it has no data to
   run against yet.
3. **A real strength comparison** (`NeuralPolicyEvaluator` as `policy_fn`, the same
   `tools/compare_engines.py` methodology V0.9.3 used for `use_heuristic_priors`) is
   the actual test of whether this whole direction was worth it -- can't happen before
   steps 1-2.
