# V0.9.4 — Policy Network Infrastructure (Mechanism, Not Yet Trained)

## Status

**IMPLEMENTED, tested, and given a first real training run** (313/313 full suite
green). The mechanism (encoding/network/evaluator/`MCTSEngine` wiring) was built in the
same "mechanism first" order V0.6.2's `NeuralEvaluator`/`eval_fn` followed before any
real Pikafish-labeled training existed; later in this same session the user provided a
real (if modest, 4,106-example) relabeled corpus, which was used to train a real
network, find and fix a second real gap (this tool's own default hyperparameters), and
run real strength comparisons -- see "A second real gap found" and "Real strength
results" below for what came of that. Picked as the next V0.9 step because V0.9.3's
positive (if not fully conclusive) result made a real trained policy network a
better-justified investment than it was before that checkpoint.

## What this builds

Four new pieces, mirroring the exact shape V0.6.2's value-network pipeline already
established (features -> network -> evaluator -> engine wiring), applied to the policy
side instead:

**`neural/policy_encoding.py`** -- `move_to_policy_index(move, color)`/
`policy_index_to_squares(index, color)`, encoding a move as one of
`POLICY_DIM = 90 * 90 = 8100` (from-square, to-square) indices. Uses the *exact same*
perspective-relative vertical-flip convention `features.py`'s `board_to_features`
already uses for its input planes -- "my" home rank always at the same edge regardless
of color -- so a single canonical policy network only has to learn one orientation,
not two mirror-image ones. `tests/test_policy_encoding_v094.py`'s
`test_mirrored_move_from_black_encodes_to_the_same_index_as_the_red_move` is the direct
analogue of `test_network_v062.py`'s own board-symmetry test, checking the same
easy-to-get-backwards property (flip the coordinate but forget which side "mine" is)
in the move-encoding direction instead of the board-encoding one.

**`neural/policy_network.py`** -- `PolicyMLP`, a small 2-hidden-layer MLP predicting
`POLICY_DIM` logits. Deliberately a **separate** network from `SmallMLP` (the value
network), not a shared trunk with two heads -- zero changes to `SmallMLP`'s
extensively-tested existing code, lower risk for a first checkpoint with no real
training data yet to validate a shared-trunk design against anyway. Trains via ordinary
(unmasked) softmax cross-entropy -- a training example is "Pikafish's actual move was
index K," an ordinary single-target-class classification problem, so illegal-move
logits get pushed down over training the same way any never-correct class does in a
normal classifier, without the loss needing to know the legal-move set for each
training example. Masking only happens at **inference**
(`predict_masked_probs(features, legal_indices)`): softmax computed only over the
legal indices for whatever specific position is being evaluated right now, which is
different for every position and isn't known (or needed) at training time. Verified
this distinction concretely, not just asserted: `test_predict_masked_probs_ignores_
illegal_indices_entirely` sets one "illegal" logit to an artificially enormous value
and confirms it doesn't distort the legal distribution -- illegal logits never enter
the softmax normalization, not just zeroed out afterward.

**`neural/policy_evaluator.py`** -- `NeuralPolicyEvaluator`, wrapping a trained
`PolicyMLP` to match `engine/mcts.py`'s `policy_fn(board, color, legal_moves) ->
{move: probability}` calling convention exactly, mirroring `evaluator.py`'s
`NeuralEvaluator` doing the same for `eval_fn`. Same "fail loudly and clearly at
construction, not with an opaque numpy shape error at first use" guard `NeuralEvaluator`
has for `FEATURE_DIM` mismatches, extended to also check `POLICY_DIM` (a network saved
before a future move-encoding change would otherwise fail confusingly deep inside
`predict_masked_probs` instead).

**`engine/mcts.py`**: `MCTSEngine` gains a `policy_fn=None` parameter, matching
`eval_fn`'s existing pattern. When set, it **takes priority over
`use_heuristic_priors`** (V0.9.3's cheap stand-in) -- a real trained policy is the
whole point that stand-in existed to justify investing in, not something to average
with once one exists. Verified directly, not assumed:
`test_policy_fn_takes_priority_over_use_heuristic_priors` constructs an engine with
*both* set to deliberately conflicting distributions and confirms `policy_fn`'s wins.

## A real, concrete gap found and fixed along the way

`PikafishClient.evaluate_fen` (V0.6.2) has *always* returned `best_move` alongside the
evaluation score -- but `tools/label_positions_with_pikafish.py` was only ever
recording `{fen, score_cp}`, silently discarding it. This wasn't a bug exactly (nothing
needed `best_move` before this checkpoint), but it's exactly the kind of latent gap that
only becomes visible once you go looking for it with a real purpose in mind -- real
policy-network training needs "what move did Pikafish actually play here," and that
data was never being kept. Fixed: the tool now records `{fen, score_cp, best_move}`.
**Existing `data/pikafish_labels.jsonl` records predate this fix and don't have a
`best_move` field** -- they would need relabeling (re-running Pikafish on the same
positions) to become usable for policy training, since the move choice isn't
derivable from the score alone.

## Scope boundary -- what the original checkpoint's tests do and don't cover

**No training happens in the automated test suite.** `PolicyMLP` instances in every
test are randomly initialized, never trained on real data -- these tests validate the
*mechanism* (encoding is correct and symmetric, backprop is mathematically correct,
masking is sound, the wiring into `MCTSEngine` actually takes priority when it should),
not playing strength. (A real training run *did* happen in this same session, after
this original checkpoint -- see "A second real gap found" and "Real strength results"
below.) `SmallMLP` and `PolicyMLP` remain two separate networks rather than a shared
value+policy trunk -- a reasonable follow-up now that there's an actual trained result
to weigh a bigger architecture change against, not attempted here.

## `tools/train_policy_network.py`

Mirrors `tools/train_neural_eval.py`'s exact shape (same CLI flags, same
val-split/early-stopping-on-a-patience-counter structure), adapted for a classification
target instead of a regression one: validation top-1 accuracy instead of RMSE,
ordinary softmax cross-entropy instead of standardized-target MSE (no `y_mean`/`y_std`
needed -- targets are class indices, not unbounded centipawn scores, so
`train_neural_eval.py`'s own target-standardization concern doesn't apply here).

`load_dataset` converts `best_move` (already in the same ICCS/UCCI coordinate notation
`GameRecord.move_to_iccs`/`move_from_iccs` use elsewhere in this project, so no new
parsing code was needed) to a policy index via the labeled position's own side to move.
Two kinds of malformed records are skipped with a reported count rather than silently
dropped -- records with no `best_move` field (pre-V0.9.4 labels) and records whose
`best_move` isn't actually legal in the labeled position (a malformed FEN/move pairing,
or an engine reporting a move for the wrong side, which would otherwise silently train
toward nonsense with no visible symptom until real play).

**Initially smoke-tested** with a small synthetic dataset (60 real, legal
(FEN, best_move) pairs generated by playing random legal moves from the starting
position -- not real Pikafish labels, just real board mechanics, since no relabeled
corpus existed yet at that point): confirmed the full label -> train -> save -> load ->
use pipeline wires together correctly. Superseded a session later by a real run -- see
below.

## A second real gap found: the original `--lr`/`--patience` defaults silently failed

The user ran a real (if modest -- 8,000-position-capped) relabeling pass:
`tools/label_positions_with_pikafish.py --max-positions 8000`, yielding 4,115 real
`(FEN, score_cp, best_move)` records (`data/pikafish_labels.jsonl`, 9 later dropped by
`load_dataset`'s legal-move sanity check -- 4,106 usable). Training against this real
data with the tool's *original* defaults (`--lr 1e-3`, `--patience 40`, inherited
verbatim from `tools/train_neural_eval.py`'s regression setting) produced a network that
looked completely untrained: **validation top-1 accuracy stuck at exactly 0.0% for
every epoch, early-stopping fired at epoch 41, and the "best" checkpoint restored was
epoch 1** -- indistinguishable from a real bug (backprop broken, learning rate zero,
data pipeline broken) from the output alone.

**It was not a bug.** Reproducing training with instrumentation `train_policy_network
.py` doesn't print by default (train accuracy, not just validation accuracy, at a fixed
short interval rather than a fraction of `--epochs`) showed loss *was* decreasing and
train accuracy *was* climbing -- just at a rate of roughly +0.01 percentage points every
few epochs at `lr=1e-3`, far too slow for a 40-epoch patience window (or even a
few-hundred-epoch one) to ever register a single validation improvement. The original
`--patience 40` default is a reasonable value for `train_neural_eval.py`'s smoothly
receding RMSE; it is not a reasonable value for an 8100-way classifier's validation
accuracy, which can plausibly sit at literal 0% for dozens of epochs before the network
has learned enough to get *any* example exactly right, then move in **noisy,
multi-decade-epoch stretches** rather than a smooth curve once it does start moving.

**With `lr=0.01` (the new default) and `patience=150` (the new default)**, the exact
same 4,106-example dataset reaches **47.1% validation top-1 accuracy** (best checkpoint
at epoch 280, training stopped at epoch 430) -- correctly predicting Pikafish's *exact*
chosen move, unmasked over the full 8100-index output space, for very nearly half of a
held-out validation set the network never trained on. Also fixed the print-interval
issue that made the original failure hard to read at a glance: printing was tied to
`args.epochs // 10`, so a run that (as this one did) stopped in the first few percent of
its epoch budget printed almost nothing; now fixed at every 20 epochs regardless of the
total budget.

**This is a concrete instance of the same lesson `docs/v0.6.2.md`'s own 4th addendum
already drew for the value network** (a fixed epoch count without early stopping caused
overfitting there) -- appearing here in the opposite direction: a *default learning
rate carried over from a different problem shape* silently starved training of any
chance to show real progress within a *reasonable* patience window, and the fix wasn't
"add more data" or "debug the math," it was recognizing that a classifier with an
8100-way output space needs a substantially different learning-rate/patience regime
than a scalar regression target does, even though both share the same training-loop
skeleton.

## Real strength results: promising accuracy, not yet promising play

`--{prefix}-policy-network PATH` was added to `tools/compare_engines.py` (loads a
trained `PolicyMLP` via `NeuralPolicyEvaluator`, takes priority over
`--{prefix}-use-heuristic-priors` the same way `MCTSEngine`'s own `policy_fn` parameter
does) so the retrained network (47.1% val accuracy, above) could actually be tested in
real games, the same `tools/compare_engines.py` methodology V0.9.3 used.

**Trained policy vs. uniform priors** (200 sims each, `data/v0.9.4_trained_policy_vs_
uniform.jsonl`, 40 games):

```
Trained policy: 20 wins
Uniform:        20 wins
Score rate: 50.0%
95% CI: [34.5%, 65.5%]
```

Dead even -- no measurable effect either way at this dataset size.

**Trained policy vs. V0.9.3's heuristic priors** (200 sims each, `data/v0.9.4_trained_
policy_vs_heuristic_priors.jsonl`, 25 games):

```
Trained policy:   6 wins
Heuristic priors: 19 wins
Score rate: 24.0%
95% CI: [7.3%, 40.7%]
Estimated Elo diff: -200
```

Clear, statistically real loss -- the cheap one-ply-lookahead heuristic from V0.9.3
currently beats the trained network outright.

**Honest read: 47% top-1 accuracy on held-out validation data is a genuinely
encouraging number for a from-scratch classifier trained on ~4,100 examples, but it
has not yet translated into better MCTS play** -- indistinguishable from uniform, and
clearly worse than the cheap heuristic. The most likely explanation, not confirmed
here, echoes `docs/v0.6.3.md`'s own material-calibration lesson from a different angle:
a signal that is measurably good on its own terms (predicting Pikafish's move choice)
doesn't automatically transfer into being a good PUCT exploration prior for *this*
specific, weak, shallow-leaf-evaluation MCTS -- 4,106 examples covering only 819
distinct target squares-pairs is also very likely just not enough data yet for the
network to have learned anything that generalizes reliably to genuinely new positions
in real games, as opposed to the specific validation split it was measured against.
Both explanations point the same direction: **more, and more varied, real labeled
data is the natural next experiment**, not a sign this direction is a dead end after
one modest-sized try.

## Concrete next steps, in dependency order

1. **A substantially larger relabeled corpus.** 4,106 examples (819 distinct target
   classes) is almost certainly too little for an 8100-way classifier to generalize
   well; the original, much larger corpus this project's `data/pikafish_labels_pre_
   v094.jsonl` reached (94,872 positions, before it lacked `best_move`) is a more
   realistic scale to aim for. Needs the user's local Pikafish, the same one-time
   dependency V0.6.2's value network already had.
2. **Retrain and re-run both comparisons above** once step 1 lands, to see whether
   more data actually closes the gap to (and ideally past) V0.9.3's heuristic priors,
   or whether the gap persists even with much more data (which would point toward the
   "doesn't transfer to a good PUCT prior" explanation over the "just needs more data"
   one instead).
