# V0.9.5 — Promote `use_heuristic_priors` to `MCTSEngine`'s Default

## Status

**IMPLEMENTED and tested** (313/313 full suite green). Acts on a real, now-decisive
result: `docs/v0.9.3.md`'s equal-wall-clock-time comparison (V0.9.3's cheap one-ply
lookahead prior vs. uniform priors, accounting for the ~2.6x per-simulation speed cost)
was expanded from n=48 to n=96 games in this session, and this time the result held up
under scrutiny rather than reverting the way an earlier n=36 checkpoint did.

## Why now, and not when V0.9.3 first measured this

`docs/v0.9.3.md`'s original write-up was explicit that n=48 (62.5%, 95% CI
[48.8%, 76.2%], p=0.083) leaned positive but didn't independently clear conventional
significance, and specifically flagged that an *interim* n=36 checkpoint had briefly
looked significant (69.4%, p=0.02) before a further batch pulled the full total back
down -- exactly the "don't stop at a lucky interim result" lesson that write-up drew
explicitly. This checkpoint is the deliberate follow-through on that lesson: rather
than treating n=48's "leans positive, not confirmed" as the final word, four more
12-game batches were run, and the result was checked for stability at each step before
trusting it:

| n | score rate | 95% CI | p |
|---|---|---|---|
| 48 (previous) | 62.5% | [48.8%, 76.2%] | 0.083 |
| 72 | 65.3% | [54.3%, 76.3%] | -- |
| 84 | 65.5% | [55.3%, 75.6%] | 0.0046 |
| 96 (final) | 65.6% | [56.1%, 75.1%] | **0.0022** |

The last three checkpoints (65.3% -> 65.5% -> 65.6%) are remarkably stable -- unlike the
n=36 checkpoint that inspired the original caution, this result did not move when more
data was added, it settled. That stability, not just the final p-value on its own, is
what makes this a decisive result rather than another maybe-lucky checkpoint: the same
"treat a single interim number with suspicion, trust a result that survives more data"
standard `docs/v0.9.3.md` itself was built around was applied here and passed.

## What changed

`MCTSEngine.__init__`'s `use_heuristic_priors` default moves from `False` to `True` --
exactly the configuration the 96-game result above measured, not a new untested one.
This is a default-value change only, following the same precedent `SearchEngine`'s
V0.6.5 promotion of `CALIBRATED_MATERIAL_VALUES`/`CALIBRATED_PST_WEIGHT`/
`CALIBRATED_KING_SAFETY_WEIGHT` already set for this project: promote a real,
now-well-evidenced default rather than leaving it as an available-but-off flag
indefinitely once the evidence bar is actually cleared.

Every default-constructed `MCTSEngine()` now uses heuristic priors automatically.

## Why `tools/compare_engines.py`'s existing comparisons are unaffected

`build_engine`'s `MCTSEngine(...)` call always passes `use_heuristic_priors=
config["use_heuristic_priors"]` explicitly -- `config["use_heuristic_priors"]` comes
from argparse's `action="store_true"` (default `False` unless `--{prefix}-use-
heuristic-priors` is actually passed), so every existing and future
`compare_engines.py` invocation continues to mean exactly what it always meant: the
"B" side of a comparison with no flags still gets the pre-V0.9.5 uniform-prior
baseline, not silently upgraded to the new default. Verified by reading the call site,
not assumed -- the same check `docs/v0.6.5.md` did for `SearchEngine`'s equivalent
promotion.

## Correctness

One existing test broke immediately: `tests/test_pluggable_eval_v062
.py::test_mcts_uses_provided_eval_fn_instead_of_heuristic` asserted `eval_fn` was
called exactly once (for the leaf value) -- with heuristic priors now on by default,
`_heuristic_priors` also calls `eval_fn` once per candidate move at the starting
position (44 calls), breaking the single-call assertion for a reason orthogonal to
what the test actually checks (whether `eval_fn` overrides the *leaf-value* heuristic,
a naming coincidence with "heuristic priors" unrelated to V0.9.3's feature). Fixed by
pinning `use_heuristic_priors=False` explicitly, the same "pin what you're not
testing" pattern used throughout V0.6.5's equivalent fixes. Full suite: **313/313
green.**

## Scope boundary

Does not touch `policy_fn` (V0.9.4) at all -- that still takes priority over
`use_heuristic_priors` when both are set, unaffected by which one is the "off" default.
Does not touch `SearchEngine`, `UCCIEngine`'s default engine choice, or anything about
which *engine* (`SearchEngine` vs. `MCTSEngine`) gets used where -- `MCTSEngine` still
loses decisively to `SearchEngine` at equal settings (V0.9.2's own -570-Elo-scale
result), so this promotion does not change the standing recommendation to prefer
`SearchEngine` for actual play; it only makes `MCTSEngine` itself measurably better
than it was before, for anyone who does use it (e.g. the V0.9.4 policy-network
comparisons this session ran, which used `MCTSEngine` on both sides).
