# V0.7.2 — UCCI asynchronous search worker

## Status

**IMPLEMENTED** — UCCI `go` now starts an asynchronous search worker and `stop` requests cooperative cancellation through the V0.7.1 search API.

## Goal

V0.7.1 made search cancellation safe, but the original UCCI adapter still called `choose_move()` synchronously. A synchronous `go` blocks the protocol loop, so a later `stop` command cannot be received until search has already finished.

V0.7.2 closes that protocol-layer gap without moving UCCI concerns into the search engine.

## Design

### `go`

1. Validate the requested depth and current position.
2. Snapshot the current board as FEN.
3. Create one `threading.Event` for this search.
4. Start a daemon worker thread.
5. Return immediately to the protocol loop.

The worker reconstructs its own board from the FEN snapshot and calls:

```python
search_engine.choose_move(board, color, stop_event=stop_event)
```

The live UCCI board is therefore never mutated by the search worker.

### `stop`

When a search is active:

1. `stop` sets the search event.
2. The command waits for the worker to unwind naturally.
3. The worker publishes exactly one final `bestmove` or `nobestmove`.
4. The pending response is returned to the protocol loop.

This is cooperative cancellation, not forced thread termination.

## Position safety

While a worker is active, commands that would change the searched position are rejected:

- `position`
- `setoption name newgame`
- another `go`

The protocol client must send `stop` first. `quit` and `bye` stop an active search before setting the quit flag.

## Response ownership

Search results are placed into a small pending-response queue protected by a lock. The worker is responsible for publishing the final result; the protocol loop is responsible for writing it to the output stream.

This separation avoids concurrent writes to UCCI output and prevents duplicate final responses.

## Scope boundary

This version intentionally supports only the existing `go depth N` search limit. Time-based UCCI controls such as `usemillisec`, `time`, `opptime`, and `movetime` are not implemented yet.

`usemillisec` remains accepted for protocol compatibility, but it does not currently alter search behavior.

## Tests

The UCCI test suite now covers:

- asynchronous `go`
- worker-produced `bestmove`
- `stop` cancellation
- exactly one final response
- rejection of position changes during search
- existing handshake, position, and depth-zero behavior

Tests have been added but have not been executed in the current environment. The next local handoff step is to run the complete test suite with `pytest` before merging this branch.

## Next step

After the worker is verified, the next protocol increment should add real UCCI time controls while keeping the same per-search event ownership model. The search engine should remain protocol-agnostic.
