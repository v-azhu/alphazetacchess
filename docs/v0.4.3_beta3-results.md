## Benchmark data (initial position, `SearchEngine` with iterative
deepening + TT + PVS + quiescence all ON, only `use_mobility` toggled)

| Depth | Mobility | Time | Nodes | Score | Best move |
|---|---|---|---|---|---|
| 1 | OFF | 0.50s | 161 | 10 | (1,0)→(2,2) |
| 1 | ON | 1.32s | 184 | 10 | (1,2)→(1,5) |
| 2 | OFF | 5.43s | 1916 | 0 | (1,0)→(2,2) |
| 2 | ON | 17.60s | 2582 | 0 | (1,2)→(2,2) |

**Cost:** mobility adds roughly 2.6x (depth 1) to 3.2x (depth 2) wall-clock
time, with a smaller node-count increase (1.14x at depth 1, 1.35x at depth
2) — meaning most of the slowdown is **per-leaf evaluation cost**, not a
bigger search tree. This is exactly what you'd expect from
`mobility.py`'s implementation: `mobility_balance()` calls
`Rule.generate_legal_moves()` for BOTH colors at every leaf it's asked to
evaluate, and full legal-move generation is the same expensive
check-simulation-per-candidate-move operation that has been the
established bottleneck since the V0.2 review (and the reason Quiescence
Search's own cost is so position-dependent — see `docs/v0.3.4.md`).

**Move changed at both depths, score did not.** Per your own note in
`docs/PROGRESS_v043_beta3.md` ("do not interpret a changed move as an
automatic strength improvement"), this is very likely the same
tie-breaking-by-encounter-order effect documented back in
`docs/roadmap.md`'s V0.3.4 section for a different feature — not evidence
of a strength change either way. A real strength signal would need either
decisive self-play results or a hand-picked tactical position where
mobility clearly should matter, neither of which was attempted this
session.

## Why depth-3 (and the other two reference positions) wasn't attempted

Extrapolating from the ~3.2x depth-2 multiplier, and knowing from
`docs/v0.3.4.md` that depth-3 Quiescence Search alone already ranges from
~6.6s (initial) to ~29s (central_development) *without* mobility, a
mobility-ON depth-3 run could plausibly take anywhere from ~20s to several
minutes per position depending on which one. Given the current session
priority is **avoiding a long-running command that could eat into a
free-tier usage window**, this was deliberately not attempted. This is a
recommendation to run locally (not a technical blocker) — see "Suggested
next step" below for the exact command.

## Recommendation: don't tune mobility yet — consider a cheaper mobility
first

The real lever here isn't the weight (`mobility_weight`), it's the
**cost of computing mobility at all**. `mobility_balance()` uses
`Rule.generate_legal_moves()` (fully legal moves, expensive) for both
colors. The project's *original* V0.2 mobility term (still visible in
`evaluate()`'s `use_piece_square_tables=False` fallback path, and in the
very first mobility formulation from the V0.2 review) deliberately used
**pseudo-legal** move counts via `MoveGenerator` directly instead —
cheap, no check-simulation, and "good enough" as a mobility proxy since
it doesn't need to be exact to be a useful positional signal. Recreating
`mobility.py`'s per-piece-type weighting on top of pseudo-legal counts
instead of `Rule.generate_legal_moves()` would very likely eliminate most
of the 2.6-3.2x cost measured here, for a component whose entire point is
to be a cheap, approximate signal — not a source of exact legal-move
counts, which the search doesn't need for evaluation purposes.

**Suggested next step (not done this session):** benchmark a
pseudo-legal version of `mobility_balance()` against the current
fully-legal one, same A/B methodology as above. If it's meaningfully
cheaper with a similar-shaped score signal, that becomes the real V0.4.3,
and the expensive fully-legal version can be dropped rather than tuned.
