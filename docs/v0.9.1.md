# V0.9.1 — MCTS Cooperative Cancellation & UCCI Wiring

## Status

**IMPLEMENTED and tested** (281/281 full suite green). First step of V0.9 (Hybrid
Engine, see `docs/roadmap.md`'s V0.9 section) -- picked because it's the concrete
prerequisite both `MCTSEngine` (V0.6.1) and `NeuralEvaluator` (V0.6.2) need before
either can actually be used for real play: `UCCIEngine` is the only way this project
currently plays a full game against a GUI or another engine, and until this step,
`MCTSEngine` simply could not be plugged into it.

## Problem

`UCCIEngine._search_worker` calls `self.search_engine.choose_move(board, color,
stop_event=stop_event)` unconditionally -- every engine handed to `UCCIEngine` must
support that exact signature. `SearchEngine` has since V0.7.1/V0.7.2. `MCTSEngine`
(built in V0.6.1, before V0.7's cancellation work existed) only had
`choose_move(self, board, color)` -- no way to interrupt a run in progress at all.
Trying to construct `UCCIEngine(MCTSEngine())` and run a real `go`/`stop` cycle
surfaced two separate gaps, both fixed here:

1. `MCTSEngine.choose_move` had no `stop_event` parameter and no way to stop early.
2. `UCCIEngine._parse_go`/`_handle_go` unconditionally read and wrote
   `self.search_engine.depth` -- `MCTSEngine` has no `depth` attribute (it measures
   effort in `simulations` instead), so simply constructing a `go` command against an
   MCTS-backed `UCCIEngine` raised `AttributeError` before any of #1 even mattered.

## Design

### MCTSEngine cooperative cancellation

`MCTSEngine.choose_move(self, board, color, stop_event=None)` now mirrors
`SearchEngine`'s exact `stop_event=None -> internal Event` convention
(`request_stop()`/`clear_stop()` included), so it's drop-in usable wherever
`SearchEngine` was. The cancellation *strategy* is deliberately different from
`SearchEngine`'s, though, for a real reason rather than just copying the pattern:

- **SearchEngine (alpha-beta)**: a partially-searched fixed-depth iteration is
  unsound -- alpha-beta's pruning and bounds are only valid once every root move at
  that depth has been explored -- so V0.7.1 discards a cancelled iteration entirely and
  falls back to the last *fully completed* shallower depth.
- **MCTSEngine (PUCT)**: the root's visit-count distribution is meaningful after *any*
  number of completed simulations; more simulations only refine it, they never
  invalidate it (this is the same "anytime algorithm" property real AlphaZero-style
  engines rely on for exactly this reason). So cancellation here just stops the
  simulation loop early and reports on whatever tree already exists -- no discarding
  needed. The one edge case that does need a fallback, for the same reason V0.7.1
  needed one: if cancelled before even the *first* simulation could expand the root,
  there is no tree at all to report on, so this falls back to the first legal move,
  exactly mirroring `SearchEngine`'s pre-depth-1 fallback.

`SearchResult.depth` continues to be repurposed as the simulation count (V0.6.1's own
convention), now specifically `completed_simulations` rather than the requested
`self.simulations` -- identical value when a search isn't cancelled, the honest lower
number when it is.

### UCCIEngine: engine-agnostic depth handling

`_parse_go`'s `values.get("depth", self.search_engine.depth)` evaluated
`self.search_engine.depth` unconditionally (Python evaluates `.get()`'s default
argument eagerly regardless of whether the key is present) -- crashing immediately on
any `go` command for an engine without a `.depth` attribute, whether or not `depth` was
actually requested. Changed to `getattr(self.search_engine, "depth", None)`.
`_handle_go`'s corresponding `self.search_engine.depth = limits.depth` write is now
guarded by `hasattr(self.search_engine, "depth")` too, so it's simply a no-op for an
effort-model that doesn't have a depth concept, rather than quietly creating an unused
attribute. Net effect: `go depth N` is accepted (never raises) for any engine, and
actually constrains search only for engines that have a `.depth` to set; `go movetime`/
`go time` continue to work identically for every engine, since both honor `stop_event`
the same way regardless of what "one unit of search effort" means internally.

## Correctness

`tests/test_mcts_cancellation.py` (5 tests): cancelled before the first simulation
falls back to the first legal move, cancelled mid-run uses the partial tree and reports
the honest completed-simulation count, board state is restored after cancellation
(trivially true given `_simulate`'s own move/undo restoration promise, tested anyway as
a regression guard), omitting `stop_event` entirely still runs the full configured
budget, and `request_stop()`/`clear_stop()` target `self._stop_event` specifically (a
pending `request_stop()` does not cancel a later call that doesn't share that same
Event object -- documented explicitly since it's an easy behavior to assume works the
other way).

`tests/test_mcts_ucci_integration.py` (2 tests) -- deliberately uses a **real**
`MCTSEngine`, not a fake double like `tests/test_ucci.py`'s own tests, specifically
because a fake would have silently satisfied the `choose_move(..., stop_event=...)`
signature without ever exercising the `self.search_engine.depth` access that was
actually broken: a full `go`/(wait)/bestmove cycle produces a well-formed ICCS move,
and `go`/`stop` actually interrupts a long-running MCTS search (`simulations=1_000_000`,
so the search is still running when `stop` arrives) rather than hanging until the full
budget completes.

Full suite: **281/281 green.**

## Scope boundary

V0.9.1 does not touch `MCTSEngine`'s tree-search logic, evaluation, or priors at all --
purely the cancellation/protocol-wiring gap. It does not yet make `UCCIEngine` (or
`tools/compare_engines.py`, `tools/self_play.py`, etc.) actually *configurable* to use
`MCTSEngine` instead of `SearchEngine` -- that wiring (a `--engine mcts` style choice,
or similar) is a natural, separate next V0.9 step, now that the underlying interface
mismatch this doc fixes is out of the way. Also not addressed here: `NeuralEvaluator`
(V0.6.2) already plugs into `MCTSEngine.eval_fn` and `SearchEngine.eval_fn` identically,
so no further wiring work is needed there -- only the cancellation/protocol gap was
MCTS-specific.
