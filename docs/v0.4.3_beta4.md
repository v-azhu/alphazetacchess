# AlphaZetaChess V0.4.3-beta-4 — Pseudo-Legal Mobility

## Status

**Implemented and benchmarked. `use_mobility` stays `False` by default**
(no change in default behavior — this is a cost fix for when mobility is
enabled, not yet a recommendation to enable it).

## What changed

`engine/mobility.py`'s `mobility_score`/`mobility_balance` switched from
`Rule.generate_legal_moves()` (fully legal — simulates every candidate
move to check it doesn't leave the mover's own king in check) to
`MoveGenerator.generate_moves()` (pseudo-legal — piece movement patterns
and blocking only, no check-simulation). The old fully-legal
implementation is kept as `_mobility_score_legal_reference` /
`_mobility_balance_legal_reference` purely for comparison, not called by
`evaluate()`/`SearchEngine`.

No changes to `evaluation.py` or `search.py` — both call
`mobility_balance()` by name and are unaware of the internal
implementation swap. No API change.

## Why this is a reasonable trade

Mobility is meant to be a cheap, approximate "how much room to move does
each side have" signal, not an exact legal-move count — the search
doesn't need mobility to be perfectly precise to be useful, unlike (say)
checkmate detection, which genuinely does need exact legality. Beta-3's
benchmark (`docs/v0.4.3_beta3-results.md`) identified the fully-legal
version's check-simulation cost as the dominant expense; this removes it.

## Benchmark: beta-3 (fully-legal) vs beta-4 (pseudo-legal)

Same methodology as beta-3: initial position, `SearchEngine` with
iterative deepening + TT + PVS + quiescence all ON, only `use_mobility`
toggled.

| Depth | Mobility | beta-3 (legal) time | beta-4 (pseudo) time | Cost multiplier (beta-3 → beta-4) |
|---|---|---|---|---|
| 1 | OFF | 0.50s | 0.52s | — |
| 1 | ON | 1.32s (2.6x) | 0.59s (**1.13x**) | 2.24x faster |
| 2 | OFF | 5.43s | 5.26s | — |
| 2 | ON | 17.60s (3.2x) | 7.52s (**1.43x**) | 2.34x faster |

Node counts and chosen moves are **identical** between beta-3 and beta-4
at both depths (184/2582 nodes, same best move each time) — confirming
the pseudo-legal signal didn't change search behavior on this position,
only its cost. This is exactly the outcome hoped for: same signal
quality, much less overhead.

## What this doesn't answer yet

This benchmark is still cost-only, on one position, at shallow depth —
it says nothing about whether mobility actually improves playing
strength, only that turning it on is now much cheaper if/when that gets
tested. Per the project's established principle (see
`docs/v0.4.1.md`'s benchmark section), a real strength signal needs
either decisive self-play results or human-vs-engine games — and now
that the web UI's core gameplay loop is confirmed working, playing a few
games with `use_mobility=True` vs the current default is a realistic way
to get a qualitative read, if useful, before deciding whether to flip
the default.

## Next step

Two independent options, not mutually exclusive:

1. **Try it in the UI:** temporarily set `use_mobility=True` in
   `web/server.py`'s `new_game()` (or expose it as a checkbox next to
   the depth selector, matching the existing dropdown pattern) and play
   a few games to get a qualitative read on whether mobility-aware play
   feels different/better. Now affordable at depth 2 (~1.4x instead of
   ~3.2x) and even depth 3 is worth a try given the multiplier dropped
   this much.
2. **Move to the next V0.4 item** (pawn structure or piece coordination)
   and leave mobility as an available-but-off feature to revisit later —
   it's fully implemented and tested either way.
