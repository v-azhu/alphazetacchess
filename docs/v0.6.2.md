# AlphaZetaChess V0.6.2 — Neural Evaluation via Pikafish Distillation

## Status

**Full pipeline implemented and tested end to end against a fake
engine.** Not yet run against the real Pikafish (needs the user's
local machine -- this development environment can't run it), and no
network has actually been trained on real labels yet. Not wired into
`SearchEngine`/`MCTSEngine` yet (see Next step).

## Why distillation, not porting Pikafish's own NNUE weights

The original plan discussed was "borrow Pikafish's trained network
directly." Investigated before writing any code, and found two real
blockers:

1. **Licensing**: Pikafish's own `pikafish.nnue` weights carry a
   custom NNUE-License ("no commercial use without permission," and
   the license explicitly follows "weights further derived from
   them") -- usable for personal/non-commercial purposes, but murky
   enough that embedding it (or a derivative) in this public repo
   isn't a clean call. A CC0 (public-domain) alternative network
   exists for Fairy-Stockfish's xiangqi variant, but locating and
   verifying it wasn't worth the effort given blocker 2.
2. **Reimplementation complexity**: Pikafish's NNUE uses a specific
   feature encoding (HalfKAv2_xq: king-bucketed, per-piece-position
   features) and quantized int8/int16 inference. Correctly
   reimplementing that in this project's pure-Python `Board`
   representation is a substantial reverse-engineering project on its
   own -- get the feature indexing or quantization even slightly wrong
   and the network's output is meaningless, not just "a bit off."

**Distillation sidesteps both.** Running Pikafish locally to generate
evaluation *labels* for positions, then training an entirely new,
small network from scratch on those labels:
- Never redistributes Pikafish's weights or code -- only uses its
  output (a centipawn number) as training signal, the same way
  virtually every NNUE-family network's own training pipeline
  bootstraps from a stronger reference engine's evaluations. The
  trained network this project ends up with is fully our own.
- Needs only NNUE-level *inference* speed from Pikafish (fast, by
  design, on ordinary CPUs) to generate labels, and training a small
  MLP on the resulting dataset is itself cheap (plain numpy, no GPU) --
  both comfortably within reach of modest, non-GPU hardware.

## Pipeline (four independently-testable pieces)

### 1. `core/fen.py` — Xiangqi FEN encode/decode

Needed because the only way to hand an external UCI engine a specific
position is `position fen <FEN>`. The one detail worth calling out:
Xiangqi has **two competing piece-letter conventions** (see
`fen.py`'s own module docstring) -- this project's own `PieceType.value`
happens to use one (`H`orse, `E`lephant), but Pikafish/UCCI engines
use the other (`N`night, `B`ishop). Using `piece.type.value` directly
would silently mislabel every Horse and Elephant sent to Pikafish.
`_FEN_LETTERS` is the explicit translation table for exactly this
reason.

Correctness gates (`tests/test_fen_v062.py`, 7 tests): starting
position matches the well-known standard Xiangqi FEN exactly; a
dedicated test that the UCCI letters (not this project's own) are
used; round-trip tests (encode then decode reproduces the original);
and — the strongest evidence, same "cross-validate rather than
hand-verify" principle `docs/v0.6.1.md`'s mate-in-one test used — a
real-world FEN pulled from an external source parses to exactly the
expected pieces at exactly the expected squares.

### 2. `neural/features.py` — board -> feature vector

Encodes "my pieces" vs "opponent pieces" (not "Red" vs "Black"
directly), vertically flipping the board when encoding from Black's
perspective so "my" home rank is always at the same edge regardless of
color -- standard practice for chess/Xiangqi neural evaluators, and it
means the network only has to learn one canonical orientation instead
of two mirror-image ones, mattering a lot for a small, laptop-scale
training set. 1260-dimensional (90 squares x 7 piece types x 2
"mine/theirs" planes), one-hot per occupied square.

Correctness gates (`tests/test_network_v062.py`'s feature tests, 3
tests): expected shape/sparsity on the starting position; and the
central symmetry property -- a position and its vertical-flip-plus-
color-swap mirror produce **identical** feature vectors when each is
encoded from its own side's perspective (the easiest thing to get
backwards here: flipping the board but forgetting to also swap which
side counts as "mine").

### 3. `neural/network.py` — `SmallMLP`

A hand-derived 2-hidden-layer MLP (numpy only, no torch/sklearn),
matching this project's practice of implementing its own engine
components rather than reaching for an off-the-shelf library (the
same reasoning `engine/search.py`'s own hand-written Negamax follows).

The one thing most worth testing directly, and tested directly:
hand-derived backpropagation is exactly the kind of code that *runs*
but trains subtly wrong when a sign or transpose is off -- the same
bug category as `engine/mcts.py`'s value-sign convention.
`test_backward_matches_numerical_gradient` perturbs individual weights
and confirms the measured loss change matches the analytical gradient,
which is much stronger evidence of correctness than "training loss
went down" alone (also tested, separately, as a sanity check that the
network can actually fit a simple synthetic target).

### 4. `neural/pikafish_client.py` + `tools/label_positions_with_pikafish.py`

A minimal UCI client (handshake, `position fen`, `go movetime`, parse
`info ... score cp/mate ...` up to `bestmove`) and a CLI that replays
real V0.5.1 self-play games, samples a position every N plies (default
4, to avoid over-representing near-duplicate consecutive positions),
and asks a running Pikafish process to label each one.

**Tested against a fake engine, not real Pikafish** (see
`pikafish_client.py`'s own docstring for why this project's test suite
can't depend on a real Pikafish binary): `tests/fixtures/
fake_uci_engine.py` is a tiny, self-contained script that speaks just
enough UCI to be useful, launched as a *real subprocess* (not mocked)
so the actual stdin/stdout plumbing gets exercised end to end. 8 tests
cover the handshake, cp-score parsing, mate-score parsing (both signs),
context-manager usage, and process reuse across multiple evaluate
calls.

### 5. `tools/train_neural_eval.py`

Loads (FEN, score_cp) labels, encodes features via `board_to_features
(board, board.current_player)` -- lining up with the label's own
"from the side-to-move's perspective" UCI convention with no sign flip
needed -- and trains `SmallMLP` via mini-batch gradient descent,
reporting train/validation RMSE in centipawns every few epochs.

### `neural/evaluator.py` — `NeuralEvaluator`

A thin wrapper so a trained network can be called exactly like
`evaluate(board, color)` -- a drop-in replacement anywhere that
function is currently used. 2 tests confirm it matches direct
`SmallMLP.predict` output and returns a plain Python float (not a
numpy scalar, which could behave subtly differently in comparisons
elsewhere in the codebase).

## Smoke test (this session, against a fake engine)

```
python tools/label_positions_with_pikafish.py --pikafish-path /tmp/fake_pikafish.sh \
    --input <3 real self-play games> --sample-every 20
  -> 24 labeled positions, real FENs sampled from real games, e.g.:
     {"fen": "rnbakabnr/9/1c5c1/.../RNBAKABNR w - - 0 1", "score_cp": 42}

python tools/train_neural_eval.py --input <above> --epochs 20 --batch-size 8
  -> train/val RMSE converges toward 0 (expected: the fake engine
     always returns the same score, so this only confirms the
     pipeline's mechanics -- data loads, features extract, network
     trains and saves -- not anything about real learning capacity)
```

Confirms every piece of the pipeline actually works together end to
end. What it does NOT confirm: whether a network trained on **real**
Pikafish evaluations (which vary meaningfully position to position,
unlike the fake engine's constant output) can learn anything useful --
that's next, and needs the user's local Pikafish.

## Known limitations

- **No real training has happened yet.** Everything above is verified
  against fakes/synthetic data; the actual value of this pipeline is
  unproven until real Pikafish-labeled data trains a network that
  measurably improves on the existing heuristic `evaluate()`.
- **Not wired into `SearchEngine`/`MCTSEngine`.** Both still call the
  heuristic `evaluate()` directly. Deliberately deferred until there's
  a real trained network worth plugging in and testing against actual
  search behavior (see Next step) -- wiring the mechanism up ahead of
  having anything real to verify it with would just be more surface
  area for an undetected bug to hide in.
- **`--movetime-ms` and `--sample-every` defaults are unvalidated
  guesses**, same "principled first guess, not yet data-validated"
  category as every other constant in this project. 200ms/position and
  every 4th ply are reasonable starting points, not measured optima.

## Addendum (2026-09-05): `--network-path` fix

First real-world run on the user's machine hit exactly the failure
mode you'd expect Pikafish's own error messages to describe: it
accepted `uci`/`isready` fine, then failed and exited (without ever
sending `bestmove`) the moment `go` was actually requested, because it
couldn't find its `.nnue` network file next to the executable (common
on Windows when the network file isn't sitting in the expected default
location). Added a `network_path` parameter to `PikafishClient` (sends
`setoption name EvalFile value <path>` during the handshake, before
`isready`) and a matching `--network-path` CLI flag on
`tools/label_positions_with_pikafish.py`. Also made
`PikafishClient`'s error message actionable in this specific case
(detects "EvalFile"/"network file" in the engine's output before it
exited and prints a hint pointing at `--network-path` and where to
download a network) rather than just dumping the raw engine output.

2 new tests (fake engine extended to optionally simulate this exact
failure, and to echo `setoption` commands so a test can confirm one
was actually sent) -- combined total **167/167 green**.

```bash
python tools/label_positions_with_pikafish.py \
    --pikafish-path "path\to\pikafish-avx2.exe" \
    --network-path "path\to\pikafish.nnue" \
    --sample-every 4
```

## Addendum (2026-09-06): first real training run diverged — fixed

The first real run (real Pikafish labels from the user's machine)
produced a **broken** network: every prediction was the same absurd
constant (~-3.9e10) regardless of position. Diagnosed by loading the
saved weights directly and checking their magnitude — every weight
matrix had entries around **1e24 to 1e27**, i.e. training diverged,
not "learned a bad function." Root cause: Pikafish's raw `score_cp`
labels range up to +/-9000 (mate scores, via `mate_score_to_cp`), and
plain mean-squared-error gradient descent against targets that large,
at a learning rate tuned for roughly unit-scale targets, blows the
weights up within the first few steps rather than converging — a
well-understood regression-training failure mode, independently
confirmed to NOT be a backprop-correctness bug (the numerical gradient
check added in the original checkpoint already ruled that out).

**Fixed two ways, together**: `SmallMLP` gained `y_mean`/`y_std`
attributes — `predict()` always returns real-scale (centipawn) values,
while `train_step` is fed pre-standardized (roughly unit-scale)
targets by the caller. `tools/train_neural_eval.py` now sets these
from the training set's own mean/std before training, and warns
explicitly if the post-training weight magnitude still looks like
divergence (>1e6). `train_step` also gained gradient-norm clipping
(`max_grad_norm=10.0` default) as defense-in-depth, independent of
standardization.

5 new tests in `test_network_v062.py`, most importantly one that
**reproduces the actual failure** (large-scale synthetic targets,
same order of magnitude as real Pikafish labels) and confirms
standardized training now stays bounded (max weight < 1000, vs. the
~1e24 seen in the real divergence), plus one confirming gradient
clipping alone bounds a single step even without standardization.
Verified the fix directly against a synthetic large-scale dataset
built from real self-play positions: max weight magnitude after
training was **0.73** (vs. 1e24+ before the fix). Combined test total:
**172/172 green**.

**`data/neural_eval.npz` currently committed in this repo is from the
diverged run and should not be used or trusted** — it will be
overwritten once the user reruns `tools/train_neural_eval.py` with
this fix (no need to re-run Pikafish labeling; the existing labels
file works fine, only the training step itself was unstable).
