# V0.6.5 — Promote Calibrated Weights to `SearchEngine`'s Actual Defaults

## Status

**IMPLEMENTED and tested** (287/287 full suite green). Acts on the recommendation
`docs/v0.6.4.md`'s real-game addendum explicitly flagged but deliberately didn't do
unilaterally, given how consequential changing every default-constructed
`SearchEngine`'s behavior is.

## What changed

`SearchEngine.__init__`'s actual parameter defaults:

| Parameter | Old default | New default |
|---|---|---|
| `material_values` | `None` (→ `MATERIAL_VALUES` inside `evaluate()`) | `CALIBRATED_MATERIAL_VALUES` |
| `pst_weight` | `1` | `CALIBRATED_PST_WEIGHT` (10) |
| `king_safety_weight` | `1` | `CALIBRATED_KING_SAFETY_WEIGHT` (8) |

This is exactly the configuration `docs/v0.6.4.md`'s real-game comparison tested (200
games total: +49 Elo at depth 2, +81 Elo and statistically significant at depth 3,
Fisher-combined p≈0.023) -- not a new, untested configuration. Every default-constructed
`SearchEngine()` (including `UCCIEngine`'s own default: `search_engine or
SearchEngine(depth=3)`) now uses it automatically.

**`evaluate()`'s own defaults are deliberately unchanged** (`material_values=None` still
resolves to `MATERIAL_VALUES` inside `evaluate()` itself, `pst_weight`/
`king_safety_weight` still default to `1`). Only `SearchEngine`'s constructor defaults
moved -- `evaluate()` is the shared, lower-level function both `SearchEngine` and direct
callers (tests, `evaluate_components()`) use, and changing its own defaults would have a
much larger, harder-to-reason-about blast radius than changing one call site's choice of
arguments.

## Why this doesn't break `tools/compare_engines.py`'s existing A/B comparisons

`build_engine`'s `SearchEngine(...)` call always passes `material_values`/`pst_weight`/
`king_safety_weight` *explicitly*, one way or the other
(`CALIBRATED_MATERIAL_VALUES if use_calibrated_material else None`, `CALIBRATED_PST_
WEIGHT if use_calibrated_weights else 1`, etc.) -- it never omits these arguments and
relies on `SearchEngine`'s own default. So every existing and future
`compare_engines.py` invocation continues to mean exactly what it always meant,
regardless of what `SearchEngine`'s bare default now is. This was verified, not assumed
-- see Correctness below.

## A real bug found and fixed along the way: two vacuous tests

Changing `SearchEngine`'s defaults broke 6 existing tests immediately (full suite run
before any fixes: 6 failed, 281 passed) -- all of them constructed a bare `SearchEngine()`
and compared its score against a bare `evaluate()` call (which still defaults to the old
baseline), so the two sides silently stopped matching. Straightforward fix: pin
`material_values=MATERIAL_VALUES, pst_weight=1, king_safety_weight=1` explicitly on
those `SearchEngine` constructions, since those tests are about whether a specific
constructor flag (`use_piece_square_tables`, `use_king_safety`, `use_pawn_structure`,
`use_piece_coordination`, `use_endgame_heuristics`) reaches `evaluate()` -- not about
which material/weight defaults happen to be in effect -- so pinning decouples them from
`SearchEngine`'s current defaults entirely, the same fix already applied to two V0.8.2
tests when V0.8.3 changed `SearchEngine`'s `use_mvv_lva` situation similarly. One more,
`tests/test_mvv_lva.py::test_material_values_override_is_used_for_scoring`, compared a
bare-default engine against an explicitly-`CALIBRATED_MATERIAL_VALUES` engine -- now
identical by construction -- fixed by comparing against an explicitly-pinned baseline
engine instead.

**A second, more interesting problem surfaced while fixing those 6**: two of
`tests/test_pst_king_safety_weights_v064.py`'s own tests (written in the *previous*
session, before this promotion) turned out to already be passing *vacuously* on their
original fixture, for a reason unrelated to this default change. That fixture (`Board()`
minus one Black Rook) happened to produce `pst_balance == 0` and `king_safety_balance ==
0` on this project's actual tables -- so `weighted - baseline == (weight - 1) *
components[...]` was trivially `0 == 0` regardless of whether the weight scaling
actually worked. `test_search_engine_threads_weights_to_evaluate` additionally went from
"passing meaningfully" to "passing vacuously" specifically *because* of this session's
default change (both its `default_engine` and `calibrated_engine` sides became
identical configurations). Root-caused and fixed: the fixture was rebuilt from scratch
(King + off-file Horses + a Rook + a Cannon on the King's open file, not blocked by the
Horse) to give `material_rook`, `pst_balance`, and `king_safety_balance` all
simultaneously nonzero, verified directly rather than assumed. A related bug in
`test_weights_combine_independently_with_material_values`'s own expected-delta formula
was caught by this fixture change too: it only accounted for the Rook term of
`CALIBRATED_MATERIAL_VALUES`'s change, silently ignoring that Cannon and Horse also
differ by 300 each -- invisible on the old fixture (no Cannon-count asymmetry existed),
surfaced immediately once the new fixture's real Cannon asymmetry made the sum actually
wrong. Fixed by summing over every piece type `CALIBRATED_MATERIAL_VALUES` actually
changes, not just Rook. All 6 tests in that file now pass with genuinely nonzero
deltas throughout, verified by manual computation before trusting the assertions again,
not just by the test going green.

## Correctness

Full suite: **287/287 green** (0 new tests -- this checkpoint is a default-value change
plus test repairs, not new functionality). Manually verified (not just asserted in a
test) that `tools/compare_engines.py`'s existing config-building logic is unaffected:
every `SearchEngine(...)` call site there passes these three parameters explicitly, so
`SearchEngine`'s new defaults are never silently substituted into an existing
comparison.

## Why no new confirmatory real-game run

`docs/v0.6.4.md`'s addendum said promoting these defaults "would need its own... real-game
confirmation that nothing regressed." That confirmation already exists: `SearchEngine()`
with the new defaults is, by construction, the *identical* configuration
`tools/compare_engines.py --a-use-calibrated-weights` already tested for 200 real games
in `docs/v0.6.4.md` (same constants, same `evaluate()` code path, same
`SearchEngine._evaluate()` call) -- not a new, untested configuration that merely
resembles it. Re-running the same comparison again would reproduce the same result
rather than test something new. What *would* be worth running, as a genuinely separate
question: whether `SearchEngine()`'s new default beats the *old* default head-to-head
directly (`--a-depth 2 --b-depth 2` with no other flags, now that "no other flags" on
each side means "new calibrated defaults" vs... nothing, since there's no flag left to
ask for the *old* baseline on the "B" side specifically -- see Follow-up below).

## Correction (checked in the next session): the "Follow-up" below was wrong

This doc originally claimed `tools/compare_engines.py`'s "no flags" case changed
meaning after this checkpoint (from "old baseline" to "new calibrated defaults") and
flagged a missing `--use-baseline-weights` flag as a result. **That claim was checked
and is incorrect.** `build_engine`'s `SearchEngine(...)` call always passes
`material_values`/`pst_weight`/`king_safety_weight` *explicitly* -- `material_values=
CALIBRATED_MATERIAL_VALUES if use_calibrated_material else None`,
`pst_weight=CALIBRATED_PST_WEIGHT if config["use_calibrated_weights"] else 1`, and so
on -- never omitting them and relying on `SearchEngine`'s own default. This was already
correctly stated earlier in this same doc ("Why this doesn't break `tools/
compare_engines.py`'s existing A/B comparisons"), which makes the "Follow-up" section
below directly self-contradictory: it can't simultaneously be true that every call site
passes these explicitly (so V0.6.5 doesn't affect `compare_engines.py`'s behavior at
all) *and* that "no flags" changed meaning because of V0.6.5. Verified directly (not
just re-reasoned): calling `build_engine` with no calibration flags before *and* after
this checkpoint's `SearchEngine` default change produces identical, explicit
`material_values=None, pst_weight=1, king_safety_weight=1` in both cases --
`compare_engines.py`'s "no flags" has always meant, and still means, the pre-V0.6.5
hand-guessed baseline. No new flag is needed; none was added. The "Follow-up" section
below is left in place (rather than deleted) as a record of the mistake, per this
project's own practice of not silently erasing a wrong conclusion once corrected.

## Follow-up (incorrect, see correction above): `tools/compare_engines.py` has no way left to request the old baseline

A side effect worth flagging: before this change, "no flags" meant "old hand-guessed
baseline" on both sides. Now, "no flags" means "new calibrated defaults" on both sides,
and there is no `--{prefix}-use-baseline-weights`-style flag to explicitly ask for the
pre-V0.6.5 hand-guessed table if someone wants to reproduce it in a future comparison
(e.g. against a real V0.9 hybrid-engine candidate) without hand-constructing a
`SearchEngine` in a script. Not fixed in this checkpoint -- flagging it as a small,
easy follow-up rather than doing it here, since it wasn't needed for anything in this
session and the existing `--{prefix}-use-calibrated-material`/`--{prefix}-use-
calibrated-weights` flags remain fully meaningful and correct either way (they say
"turn calibration on", which is still true regardless of what the engine's own
un-flagged default now is).
