# V0.7.1 — Cooperative Search Cancellation

## Status

**IMPLEMENTED** on `dev/v0.7-ucci-control`.

The focused regression tests have been added but have not been executed in this environment. The next handoff should begin by running the full `pytest` suite locally.

## Goal

Make `SearchEngine` safely interruptible so the UCCI layer can later implement a real asynchronous `go` / `stop` cycle without forcibly killing a Python thread.

This version deliberately changes the search layer only. UCCI worker-thread integration and time controls remain the next step.

## Design

### 1. Cooperative cancellation

`SearchEngine` uses a `threading.Event` as the cancellation signal.

- `request_stop()` sets the engine-owned stop event.
- `clear_stop()` clears it before a new engine-owned search.
- `choose_move(..., stop_event=...)` accepts an externally owned event for protocol workers or other callers that need explicit lifetime control.
- The external event is never cleared by `choose_move()`; its owner is responsible for that lifecycle.

Cancellation is checked at search-node boundaries and before each root move. The search raises the internal `SearchCancelled` signal to unwind the current recursion immediately.

No thread is force-killed. This is intentional: Python does not provide a safe general mechanism for asynchronously terminating arbitrary code while it may be mutating a board.

### 2. Board-state safety

Every search-side `board.move()` is now paired with `board.undo()` inside `try/finally` blocks in:

- root search;
- Negamax recursion;
- Quiescence Search.

Therefore a cancellation exception cannot leave the caller's board one ply deeper than it was when the search started.

### 3. Iterative-deepening boundary

An interrupted iteration is never promoted to the current result.

For example:

```text
depth 1 complete  -> keep result
 depth 2 started   -> cancelled
return depth 1 result
```

`SearchResult.depth` therefore reports the last **fully completed** iteration, not the requested depth.

If cancellation arrives before depth 1 completes, the first legal move is returned as a safe fallback with `depth=0`.

### 4. Transposition-table safety

A node writes its TT result only after its child searches have completed. If cancellation propagates through that node, execution leaves before the store is reached.

This avoids storing a score produced from an incomplete search subtree.

## Validation

`tests/test_search_cancellation.py` covers two critical invariants:

1. cancellation after a root move has already been made restores the exact original FEN, Zobrist hash, side to move, and position history;
2. iterative deepening keeps the result from the last completed depth when the next iteration is cancelled.

The tests use deterministic test doubles rather than wall-clock sleeps, so they do not depend on machine speed or thread scheduling.

## Scope Boundary

V0.7.1 does **not** implement:

- asynchronous UCCI search workers;
- UCCI `stop` command integration with a running worker;
- `go movetime`;
- `go time/inc` time management;
- periodic `info` reporting;
- hard search deadlines.

Those belong to the next protocol-layer step.

## Handoff Notes

The next implementation should build directly on this API rather than introducing another cancellation mechanism:

1. UCCI creates an event for each `go` search.
2. A worker thread calls `SearchEngine.choose_move(..., stop_event=event)`.
3. `stop` sets that event.
4. The worker waits for the search function to return naturally.
5. The worker emits exactly one final `bestmove` or `nobestmove`.

The worker must not mutate `UCCIEngine.board` while the main protocol loop is simultaneously processing `position`, `ucinewgame`-equivalent reset behavior, or another `go`. Protocol-state synchronization should be designed explicitly in the next step rather than relying on incidental GIL behavior.
