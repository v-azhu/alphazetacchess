# V0.9.2 — `--engine mcts` Wiring in `tools/compare_engines.py`

## Status

**IMPLEMENTED and smoke-tested** (281/281 full suite unaffected -- see Scope note on
why this has no dedicated unit tests). Second step of V0.9, picked because it directly
unblocks two still-open items at once: V0.9.1's own scope boundary ("make
`tools/compare_engines.py` actually configurable to use `MCTSEngine`") and V0.6.1's
long-standing open question ("V0.6.1's `MCTSEngine` still has no real strength benchmark
against `SearchEngine` at any depth" -- flagged in `docs/roadmap.md`'s hand-off trail
since the V0.6.3 addendum).

## Design

`--{a,b}-engine {search,mcts}` (default `search`, so every existing invocation of
`compare_engines.py` is unaffected) chooses which `ChessEngine` implementation that side
plays as. `--{a,b}-simulations` (default 200, `MCTSEngine`'s own default) controls MCTS
effort, playing the same role `--{a,b}-depth` plays for `SearchEngine`.

`build_engine` branches on `config["engine"]`: `MCTSEngine` gets
`use_mobility`/`use_pawn_structure`/`use_piece_coordination`/`use_endgame_heuristics`/
`eval_fn` -- every flag it actually has a constructor parameter for -- and nothing else;
`SearchEngine`'s construction is completely unchanged. `RandomizedOpeningEngine` (V0.5.2)
wraps either one identically, since it's already engine-agnostic by design (wraps any
`ChessEngine`, calls `choose_move(board, color)` with no engine-specific assumptions).

**Flags that don't apply to MCTS** (`--{prefix}-no-killer-moves`, `--{prefix}-use-mvv-lva`,
`--{prefix}-use-opening-book`, `--{prefix}-use-calibrated-material` -- none of these are
meaningful concepts for a PUCT tree search: no killer table, no capture-ordering pass,
and `MCTSEngine` has no `material_values` constructor parameter at all) are silently
*accepted* by argparse (so a typo'd combination doesn't crash), but `build_engine`
never reads them for the MCTS branch, and `main()` prints an explicit warning listing
exactly which non-default flags will be ignored for that side --
`_mcts_ignored_flag_warnings` only flags ones actually toggled away from their default,
so a plain `--{prefix}-engine mcts` with nothing else set stays quiet. This mirrors the
project's existing convention for `--use-neural-eval`'s similar "ignores the mobility/
pawn-structure/etc flags" documented behavior, made an explicit runtime warning instead
of only a docstring note, since combining an unsupported flag with `--engine mcts` is an
easier mistake to make silently than the neural-eval case (that one's ignored flags are
at least all evaluation-related; MCTS's span ordering, opening selection, *and*
material valuation).

`--{prefix}-depth` is simply unused when `--{prefix}-engine mcts` -- not warned about,
unlike the four flags above, since its default (2) doesn't represent an explicit,
easy-to-misread user intent the way toggling a boolean flag does.

## Verification

Smoke-tested with a real 2-game run (`--a-engine mcts --a-simulations 150
--a-use-mvv-lva`, confirming both the mechanism works end-to-end and the ignored-flag
warning fires correctly for the deliberately-mismatched `--a-use-mvv-lva`). Full suite
281/281 unaffected (no `SearchEngine`/`MCTSEngine`/protocol code touched, only
`tools/compare_engines.py`).

## Scope note: no dedicated unit tests

Consistent with this project's existing convention --
`strength_comparison.py`'s own docstring: *"`tools/` scripts are thin CLI wrappers by
convention in this project... shouldn't be import targets for `src/` modules"* -- and
the precedent already set by V0.6.3's `--use-calibrated-material` and V0.8.3's
`--use-mvv-lva` additions to this same file, neither of which got dedicated unit tests
either. Verification is the real, executed comparison run below instead, the same way
those two were verified.

## First real data: MCTSEngine vs. SearchEngine — decisive, MCTS loses badly

Two batches run immediately after wiring this up, settling V0.6.1's open strength
question with a much clearer signal than V0.8.3's or V0.6.3's near-50% results needed
(no large sample was needed here -- the effect is large and consistent from the start).
Both sides otherwise at default config (no mobility/pawn-structure/etc. on either side).

**28 games, MCTSEngine (200 simulations, V0.6.1's own default) vs. SearchEngine (depth
2)**, `data/v0.6.1_mcts_vs_search.jsonl`:

```
MCTS wins:   1
Search wins: 27
Draws:       0
MCTS score rate: 3.6%
95% CI: [0.0%, 10.4%]
Estimated Elo diff (MCTS - Search): ~-570 (see caveat below)
```

**10 more games at 5x the simulation budget, MCTSEngine (1000 simulations) vs.
SearchEngine (depth 2)**, `data/v0.6.1_mcts1000_vs_search.jsonl`:

```
MCTS wins:   0
Search wins: 10
Draws:       0
```

**Conclusion: this is a clear, decisive result, not noise.** Unlike V0.8.3's and
V0.6.3's near-50% findings (which genuinely needed 25-120+ games to distinguish from
chance), a 1-27-0 record has a 95% CI that doesn't come close to touching 50% even at
n=28 -- no larger sample is needed to be confident `MCTSEngine`, as it exists today,
loses badly to `SearchEngine` at depth 2. The 1000-simulation follow-up (0/10, still a
clean sweep) rules out "just needs more simulations" as the explanation -- 5x the
budget didn't produce a single win.

*Caveat on the -570 Elo figure*: `estimate_elo_diff`'s log-odds formula is numerically
unstable near the 0%/100% extremes (a single additional win or loss would swing this
estimate substantially, and it returns `None` outright at an exact 0% or 100% score
rate, which the 10-game follow-up hit). Treat "~-570" as "very large and decisively
negative," not as a precise figure -- the win/loss/draw counts above are the real
result, this number is a rough illustration of scale.

**This is not surprising in retrospect, and does not mean MCTS is a bad direction --
it means the *current, deliberately minimal skeleton* is weak, exactly as
`docs/roadmap.md`'s own V0.6.1 description flags**: uniform move priors (no policy
network), no history/killer-move-style learning across simulations, and `evaluate()`
(the same leaf-value function `SearchEngine` already uses, tuned for use inside years of
accumulated alpha-beta optimizations, not for MCTS's very different search shape) as the
only signal at every leaf. This is the same well-known pattern behind why AlphaZero-style
engines need a trained policy/value network before their MCTS search becomes competitive
with strong classical engines at all -- V0.6.1 built the tree-search skeleton
deliberately without one yet ("search skeleton first, evaluation second," the same split
`docs/roadmap.md`'s V0.6.1 section already frames it as), and this result is the concrete
confirmation of exactly the gap that skeleton was always going to have until a real
policy network fills it in.

**Practical implication for V0.9**: this makes V0.9's neural-network step (wiring
`NeuralEvaluator`, and eventually a real policy head, into `MCTSEngine`) the more
consequential remaining item compared to further MCTS-vs-SearchEngine tuning at fixed
priors -- the uniform-prior ceiling this result demonstrates is unlikely to move much
without one.
