## Goal

Continuing V0.4's Advanced Evaluation scope. V0.4.1 added Piece-Square
Tables for Horse/Cannon/Rook/Pawn; King/Advisor/Elephant were
explicitly left out of that scope, with King Safety called out as its

step"). V0.4.2 implements that term.

## Design

Two independent, additive scoring terms in `engine/evaluation.py`,
computed once per side per evaluation call (not per-piece, since King
Safety is a whole-board property):

### 1. Guard Integrity

A flat bonus for every Advisor and Elephant of a king's own color
still on the board:

```python
ADVISOR_ALIVE_BONUS = 20
ELEPHANT_ALIVE_BONUS = 12
```

Advisors score higher than Elephants because Advisors are confined to
(and therefore always guard) the palace itself, immediately adjacent
to the king; Elephants are more general-purpose blockers on the
friendly half of the board and can never enter the palace at all.

This term deliberately does **not** check which exact square each
guard occupies — V0.4.1's PST already exists for "is this piece well
placed"; Guard Integrity answers a different, simpler, and arguably
more decisive question in Xiangqi: **is the king's escort still
alive**. A king that has lost both advisors is dramatically more
exposed to certain mating patterns regardless of exactly where the
remaining pieces stand, which is what this term is meant to capture
cheaply.

### 2. Open-File Exposure

Scans straight out from the king along its own file (column), toward
the opponent's side of the board:

```python
OPEN_FILE_ROOK_PENALTY = -40
OPEN_FILE_CANNON_PENALTY = -25
```

The scan stops at the first piece encountered. If that piece is an
enemy Rook, the file is a serious, direct threat (a Rook can reach the
king's file in one clean move with nothing in the way) — a real
penalty. If it is an enemy Cannon, the position is still dangerous but
less immediately so (a Cannon needs a screen piece to actually
capture, so an empty file alone isn't a capture threat yet, only a
setup for one) — a smaller penalty. Any other piece — friendly or
enemy, including a Cannon's own future screen if one already exists
further down the file — fully blocks the line and this term
contributes nothing.

This is deliberately a *positional* danger signal, not a check
detector: the classic Xiangqi principle it encodes is that a fully
open file toward the king is dangerous even before any piece is
actually delivering check, because the king's own mobility is already
severely restricted to the 3x3 palace and cannot easily create its own
escape route once a real attack starts.

**Important interaction with Quiescence Search (found while writing
the wiring test, see below):** if the "open file" scenario also
happens to have *nothing at all* between the king and an enemy Rook —
i.e. it is not just a positional risk but an actual, immediate check —
then `Rule.is_in_check` is already true for that position. Quiescence
Search's own "no stand-pat while in check, must resolve" rule (V0.3.4)
then takes over at the leaf and searches evasions instead of returning
a static score. This is correct, expected behavior (an immediate check
should never be scored as if it were just a quiet positional
disadvantage) — but it means Open-File Exposure's *positional* penalty
and quiescence's *tactical* check-resolution can both apply to the
same underlying danger via different mechanisms depending on whether
something happens to be blocking the file. Worth being aware of when
reasoning about a position's score, not a bug to fix.

### Combining with perspective

```python
score += _king_safety_score(board, perspective_color)
score -= _king_safety_score(board, opponent_color)
```

so the term reflects the *relative* difference in king safety, not
just an absolute measure of one side.

### Scope boundaries (deliberately not included here)

- **Rank-based exposure** (an open row toward the king, as opposed to
  a file) — the file case is the more classically significant one in
  Xiangqi and was implemented first to keep this sub-version focused;
  rank exposure is a natural, structurally similar follow-up.
- **Attacker proximity / piece count near the palace** — a more
  holistic "how many enemy pieces threaten the palace area" metric,
  more complex to compute cheaply and left for a later refinement.
- **King mobility as danger** (inverting the usual "more moves is
  better" logic specifically for the king) — conceptually appealing
  but overlaps significantly with what checkmate/stalemate detection
  in `Rule`/`SearchEngine` already resolves exactly at the terminal
  level; a heuristic approximation of it during normal (non-terminal)
  search nodes is left for later if it proves useful in practice.

### API

`evaluate(board, perspective_color, use_piece_square_tables=True,
use_king_safety=True)` — `use_king_safety=False` omits this term
entirely, independent of `use_piece_square_tables`, so each V0.4.x
evaluation layer stays separately A/B-comparable (verified directly by
`test_pst_and_king_safety_toggles_are_independent`). `SearchEngine`
gained a matching `use_king_safety` constructor flag, threaded through
all four internal `evaluate()` call sites, the same way
`use_piece_square_tables` was in V0.4.1.

## Correctness gates (`tests/test_evaluation_v042.py`, 10 tests)

1. `test_king_safety_is_color_symmetric_on_initial_position` — reaffirms
   V0.4.1's symmetry invariant still holds with King Safety included.
2. `test_advisor_worth_more_than_elephant_in_guard_integrity` — direct
   constant check documenting design intent.
3. `test_open_file_rook_penalty_is_larger_than_cannon_penalty` — same,
   for the other term.
4. `test_guard_integrity_rewards_surviving_advisors_and_elephants` —
   exact expected delta (`2 * ADVISOR_ALIVE_BONUS + 2 *
   ELEPHANT_ALIVE_BONUS`) for a fully-intact guard.
5. `test_open_file_exposure_penalizes_enemy_rook_on_open_file` — exact
   delta equals `OPEN_FILE_ROOK_PENALTY`.
6. `test_open_file_exposure_penalizes_enemy_cannon_on_open_file` — same
   for Cannon.
7. `test_open_file_exposure_is_zero_when_file_is_blocked` — a blocking
   piece fully cancels the term.
8. `test_king_safety_reflects_the_difference_between_both_sides` — the
   term is relative (Red's guard minus Black's), and symmetry
   (`evaluate(RED) == -evaluate(BLACK)`) holds even in an asymmetric
   position.
9. `test_pst_and_king_safety_toggles_are_independent` — the two V0.4.x
   evaluation terms don't interact; turning both on sums their
   individual deltas exactly.
10. `test_search_engine_use_king_safety_toggle_reaches_evaluation` —
    proves the constructor flag reaches all the way through
    `SearchEngine` to evaluation. **This test went through one fix
    during writing**: the first draft used an enemy Rook (not Cannon)
    on the open file, which made the fixture an actual check (not just
    a positional risk), causing `_quiescence` to diverge from a plain
    `evaluate()` call for the correct reason described above under
    "Important interaction with Quiescence Search". Switched to a
    Cannon, which is a real King Safety threat without being an
    immediate check, resolving the mismatch without changing any
    production code.
