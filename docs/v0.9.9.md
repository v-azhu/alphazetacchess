# V0.9.9 — Attacking the Real Weakness: Search Speed, and Raising the Default Depth

## Status

**IMPLEMENTED and tested** (319/319 full suite green, suite runtime itself dropped
from ~32s to ~19s as a side effect). Driven by direct user feedback rather than an
internal metric: a 天天象棋 专业1-1 club player reported beating the engine **while
giving a horse handicap AND three free moves**. That is not a tuning-level weakness,
so this checkpoint went looking for a structural cause instead of adjusting evaluation
terms.

## Diagnosis: the engine was searching 2 ply because it could not afford more

The web UI defaulted to depth 2 and its dropdown capped at 3; the CLI defaulted to 2.
In xiangqi, depth 2 is roughly one move of lookahead -- it can see its own move and the
reply, and essentially nothing else. Any club-level human out-calculates that trivially.
So the question wasn't "why is the evaluation bad", it was **"why is the depth so
low"**, and the answer was raw speed:

```
depth=1:  0.12s     162 nodes   1396 nps
depth=2:  0.57s     988 nodes   1731 nps
depth=3:  2.41s    4464 nodes   1850 nps
depth=4:  9.42s   18137 nodes   1926 nps
```

**~1,900 nodes/second.** The effective branching factor (162 -> 988 -> 4464 -> 18137,
about 4.3) shows alpha-beta, PVS, the TT and move ordering were all doing their job --
the tree was being pruned well. The engine was simply executing nodes about an order of
magnitude slower than a Python engine of this design should.

Profiling a depth-3 search made the cause specific: **`generate_legal_moves` was 95% of
total runtime** (7.64s of 8.02s), because it does make-move -> `is_in_check` -> unmake
for every pseudo-legal move -- 156,554 legality probes to evaluate just 4,464 nodes.
Three costs inside that dominated, and all three were fixable without touching search
logic or changing a single result.

## Three fixes

**1. `Board.find_king` was a full board scan, called 470,284 times.** Every
`is_in_check` and `kings_facing` call re-scanned up to 90 squares to locate a king.
Now cached as a `Piece` reference. The subtlety that makes this safe: the cache stores
the *object*, not coordinates, and `move()` mutates `piece.x`/`piece.y` in place, so a
cached king stays correct across moves with no invalidation on the hot path. A
`self.board[y][x] is cached` guard makes it self-healing -- it re-scans whenever the
cached piece isn't where it thinks it is, which covers a captured king, an `undo()`
restoring one, and boards rebuilt or hand-edited in place (several tests do exactly
that). A cache keyed on coordinates, or one invalidated only inside `move()`, would
have silently returned a stale king in those cases.

**2. Legality probing used the full `move()`/`undo()` pair.** Those maintain four
Zobrist `PIECE_KEYS` lookups (each hashing a 4-tuple containing two enums), the
side-to-move flip, and appends to both `history` and `position_history` -- all of it
discarded microseconds later when the probe is undone, 156,554 times per search. Added
`Board.probe_move`/`undo_probe`, which touch only what the attack detector actually
reads: the board array and the moved piece's coordinates. These are deliberately *not*
exposed as a general faster `move()` -- they leave the board in an incoherent
post-move state (no valid hash, no history), so anything reading the TT, repetition
history, or calling `undo()` would be silently wrong. Both docstrings say so
explicitly.

**3. `in_bounds` and `get` were called 6.37M and 5.40M times.** One-line functions, but
at that volume Python's per-call overhead dominates their actual work. Inlined
throughout `core/attack.py`'s hot paths, with the board grid bound to a local.

## Result: ~2x faster

```
              before      after
depth=3:   1850 nps    3842 nps     2.41s -> 1.16s
depth=4:   1926 nps    3865 nps     9.42s -> 4.69s
depth=5:        --     4536 nps            25.5s
```

Every one of the 319 tests passes unchanged -- these are pure performance changes, no
search or evaluation behavior was altered. (The suite's own runtime dropping from ~32s
to ~19s is independent corroboration that the speedup is real and broad, not specific
to the benchmark position.)

## Then: raise the default depth

Speed only matters here because it buys depth. With depth 4 now costing about what
depth 3 used to:

- **Web UI**: default 2 -> 4, dropdown extended from 1-3 to 1-5.
- **CLI** (`src/main.py`): `AI_SEARCH_DEPTH` 2 -> 4. The comment block above it, which
  said depth 4 was ">55s from the opening position, not yet practical", is now stale
  by an order of magnitude and has been corrected in place rather than deleted.

Depth 2 -> 4 is two extra ply. In practical terms that is the difference between
seeing one move ahead and seeing a short tactical sequence -- it should matter far more
to real playing strength than any evaluation-term change measured in this project so
far (all of which have been worth tens of Elo at most; V0.6.4's combined calibration,
this project's best previous evaluation result, was ~+49/+81 Elo).

**Honest caveat on that claim**: I did *not* verify depth 4 > depth 2 with a real
multi-game match in this session. Depth-4 games run ~10 minutes each here, so a
meaningful sample wasn't reachable within the session's limits, and a 1-game result
(which is all I got) is not evidence -- I deliberately discarded it rather than
commit a data file implying more than it shows. The depth/strength relationship is
about as well-established as anything in computer chess, and the speed measurements
above are directly measured and reproducible, but the specific end-to-end strength
claim rests on that general knowledge rather than on this project's own numbers. **This
is the natural thing for the user to confirm by simply playing it.**

## What this does not address

Speed and depth were the dominant, structural problem, but they are unlikely to be the
*only* one. Specifically still open, and better attacked once depth 4-5 is the baseline
rather than depth 2:

- **`docs/v0.9.8.md`'s conversion finding.** Uniform-prior MCTS could not convert a
  single win against a random mover in 10 games, hitting the move limit every time.
  That smelled like an endgame/conversion weakness distinct from move-selection
  quality. `SearchEngine` went 6-0 in the same test so it is clearly less affected --
  but "clearly less affected at depth 2 against random" is a low bar, and it is worth
  re-checking whether the deeper search still struggles to finish won positions.
- **No endgame tablebase or mating-net knowledge.** The evaluation has an optional
  endgame-heuristics term (V0.5.3, off by default) but nothing that actually
  understands how to deliver mate with limited material.
- **Opening play.** A real 1330-entry book exists and is now reachable from the web UI
  (V0.9.7), but it is off by default and built from this engine's own weak self-play,
  so its move choices are only as good as the engine that generated them.

## Further speed headroom, if depth 5-6 becomes the goal

Profiling after these fixes shows the remaining time is spread across the attack
detector's per-piece-type checks rather than concentrated in one place, so the next
meaningful gain is architectural, not another micro-optimization. The realistic options,
roughly in order of payoff-to-risk: incremental attack/legality updates instead of
re-probing every move; a bitboard or flat-array board representation to replace the
list-of-lists and `Piece` objects; or `PyPy`/native extension for the hot path. None
attempted here -- this checkpoint deliberately stopped at the point where the fixes
were still provably behavior-preserving.
