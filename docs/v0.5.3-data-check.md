# Self-Play Data Check & Opening Randomization Fix

## What happened

You ran `tools/self_play.py` locally (before the randomization fix
below existed) and shared `data/selfplay.jsonl`: 10 games, `depth=2`,
all V0.4.x evaluation terms off on both sides.

**Finding: all 10 games were byte-for-byte identical** — same result
(`BLACK_WINS`), same length (82 moves), and every single move matched
exactly across all 10 records. Verified directly:

```python
first_moves = records[0]["moves"]
all(r["moves"] == first_moves for r in records)  # True
```

## Why

`SearchEngine` is fully deterministic (same position → same move,
every time — no randomness anywhere in Negamax/Alpha-Beta/PVS/
Quiescence/TT lookups). Self-play with identical configurations on both
sides, from the fixed starting position, therefore always plays out the
exact same game. This was exactly the concern flagged in
`docs/v0.5.2.md`'s "Known limitation" section, now confirmed with real
data rather than just predicted.

**Consequence:** this data isn't usable for V0.5.2's opening book (it
would produce one "10/10 confident" line and zero information about
anything else) or for V0.5.3's endgame heuristics — there's no
diversity to learn from. Not wasted effort, though: it's exactly the
diagnostic signal needed to confirm the fix below was actually
necessary before spending real time collecting more data.

## Fix: opening randomization

`src/alphazetacchess/selfplay/opening_randomization.py`:
`RandomizedOpeningEngine` wraps any `ChessEngine`. For the first
`random_plies` plies, each call to `choose_move()` has `random_prob`
probability of returning a uniformly random legal move instead of
deferring to the wrapped engine — a standard "epsilon-greedy
exploration" technique for injecting diversity into self-play data
collection. Deliberately kept as an external wrapper rather than built
into `SearchEngine` itself: this is a data-collection concern, not a
playing-strength one, and a "real" (non-randomized) game against the
engine should stay completely unaffected.

`tools/self_play.py` now uses this **by default**
(`--random-opening-plies 10 --random-opening-prob 0.3`, both
overridable; pass `--random-opening-prob 0` to fully disable and get
old-style pure deterministic self-play, e.g. for reproducing/debugging
one specific line).

## Verification

4 new tests (`tests/test_opening_randomization_v052b.py`): `prob=0`
exactly reproduces the wrapped engine's own choice; `prob=1` always
picks a legal move (not necessarily the engine's choice); randomization
only applies within `random_plies` (a later ply exactly matches the
wrapped engine again regardless of `rng`); **and, directly reproducing
the actual issue found** — two self-play games with randomization and
different seeds produce genuinely different move sequences, unlike the
uploaded batch.

Combined with every other targeted V0.4.x/V0.5.x test file: **64/64
green.**

Real CLI smoke test (`--games 4 --depth 1 --max-moves 16`, default
randomization now on): confirmed the 4 games are no longer identical —
each has a different opening. (Depth 1 for smoke-test speed only; real
data collection should still use `--depth 2` as before.)

## What this means for your uploaded data

The 10 games you shared are still useful as exactly what they are: a
confirmed, reproduced diagnosis of the diversity problem. They're not
being used to build a real opening book or endgame heuristics, since
statistically there's nothing to extract from one repeated line.
