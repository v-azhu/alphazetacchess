# V0.9.14 — Tactical Regression Framework

## Goal

Turn the search-stability observations from V0.9.13 into repeatable tactical
checks without pretending that the engine's current answer is ground truth.

The first framework uses small positions whose tactical property can be checked
independently from the search result:

1. **mate in one** — enumerate legal moves and verify which moves produce
   checkmate;
2. **free capture** — enumerate captures and verify that the captured piece
   cannot be immediately recaptured;
3. **exchange trap** — preserve a known capture/recapture fixture used by the
   Static Exchange Evaluator tests.

The framework deliberately reports engine hits rather than turning every
position into a hard-coded "best move" assertion. A search failure is useful
diagnostic information and should not be hidden by a test that simply encodes
the current engine's preferred move.

## Files

- `tests/test_tactical_positions.py` — fixture sanity checks and objective
  tactical-property helpers.
- `tools/benchmark_tactics.py` — runs the engine at multiple depths and reports
  whether the selected move satisfies the independently computed tactical
  property.

## Run

From the repository root:

```powershell
pytest tests/test_tactical_positions.py
```

Benchmark the baseline search:

```powershell
python tools/benchmark_tactics.py --depths 2 3 4
```

For comparison with the experimental Null Move pruning:

```powershell
python tools/benchmark_tactics.py --depths 2 3 4 --null-move
```

## Interpretation

`mate_hit=True` means the engine selected one of the legal immediate mating
moves found independently by the fixture checker. `free_hit=True` means it
selected one of the captures that the checker found to be immediately safe
from recapture.

These are **tactical gates, not overall strength scores**. A false result does
not by itself identify the faulty layer. It narrows the investigation to search
horizon, move ordering, quiescence, evaluation, or a combination of them.

The benchmark also checks `state_ok`, because tactical probing temporarily
makes and undoes moves. A tactical diagnostic must not corrupt the board state
used by the next search.

## Why no hard-coded best-move list yet?

A single engine's output cannot validate itself. For positions without an
independent solution, the framework should first establish an objective
property or obtain an external/reference solution. Only then should a specific
best move be promoted into a regression assertion.

This keeps the V0.9.14 suite useful for diagnosing the existing engine rather
than silently teaching the test suite to agree with it.

## Next checkpoint

After running this suite locally, classify each failure:

- **mate miss**: first inspect legal move generation, mate detection,
  quiescence, and search depth;
- **free-capture miss**: inspect evaluation/material values, capture ordering,
  and shallow search;
- **exchange-trap behavior**: compare ordinary search against SEE and inspect
  whether the search sees the opponent's recapture;
- **state failure**: stop strength work and fix search/diagnostic state
  restoration first.

Only after these classifications should we add a new search optimization or
change evaluation weights.
