# AlphaZetaChess V0.6.3 — Calibrating the Heuristic's Constants Against Real Data

## Status

**Implemented, tested, and run against real data. Real, interpretable
findings produced. Not yet applied back into `evaluate()`'s actual
constants** — see Known limitation and Next step.

## Why this, instead of more neural-network iteration

`docs/v0.6.2.md` concluded with a real, converged negative result:
three separate attempts (more network capacity, ~33x more training
data, richer hand-crafted input features) each showed the same small,
easily-exhausted improvement, and the trained network still lost to
the existing heuristic `evaluate()` by -269 Elo in a real 20-game
comparison. Rather than attempt a fourth iteration of the same
pattern, this checkpoint uses the *same* hard-won labeled data
completely differently: instead of training a black-box network to
approximate a value function from scratch, it fits new values for
`evaluate()`'s own hand-guessed constants directly, via linear
regression against real Pikafish scores.

## Design

### `engine/evaluation.py`'s new `evaluate_components()`

Decomposes a position into the same named ingredients `evaluate()`
itself combines — but as **raw, unweighted feature values** (piece
counts, balance-function outputs) rather than already-weighted scores.
Six material-count features (`material_rook`, `material_cannon`, etc.
— `material_king` is deliberately omitted, since a King is always
worth exactly 0 and isn't a meaningful regression target), plus
`pawn_crossed_river_diff`, `pst_balance`, `king_safety_balance`, and
the four existing `*_balance` functions (`mobility_balance`,
`pawn_structure_balance`, `piece_coordination_balance`,
`endgame_balance`).

**The central correctness gate**: recombining these raw values with
`evaluate()`'s *current* hand-guessed constants must reproduce
`evaluate()`'s own output exactly. `tests/
test_evaluation_components_v063.py`'s first three tests check this
directly (starting position, an asymmetric position, and with every
optional term enabled) — a decomposition that doesn't sum back to the
same total isn't a faithful decomposition of what `evaluate()`
actually computes, regardless of what else it reports. Four more
tests check individual components' correctness directly (material
counts reflect real piece counts and exclude King, crossed-river-pawn
counting, antisymmetry between colors). **7 tests, all passing.**

### `tools/calibrate_evaluation.py`

Loads (FEN, score_cp) labels, computes `evaluate_components()` for
every position, and fits an ordinary least-squares linear regression
(`np.linalg.lstsq` — closed-form, no gradient descent needed for a
linear model at 13 features) against the real Pikafish scores, plus
an intercept term (capturing any systematic side-to-move/tempo bias).
Reports every fitted coefficient next to the constant it corresponds
to in `evaluation.py` today, and compares held-out RMSE/correlation
against both the fitted model and the current hand-guessed constants
on the same split — a direct, apples-to-apples before/after
comparison, and (since it uses the identical train/val split
convention `tools/train_neural_eval.py` uses) an apples-to-apples
comparison against V0.6.2's neural network results too.

## Results (run against the real 94,872-position corpus)

```
Calibrated constants (current hand-guessed value -> fitted value):
  material_rook                  900.0 ->   1525.7
  material_cannon                450.0 ->    749.0
  material_horse                 400.0 ->    696.1
  material_elephant              200.0 ->    201.7
  material_advisor               200.0 ->    161.2
  material_pawn                  100.0 ->     96.0
  pawn_crossed_river_diff         30.0 ->     28.0
  pst_balance                      1.0 ->      9.9
  king_safety_balance              1.0 ->      8.3
  mobility_balance                 1.0 ->      4.9
  pawn_structure_balance           1.0 ->      0.2
  piece_coordination_balance       1.0 ->      0.6
  endgame_balance                  1.0 ->      4.4
  intercept (tempo bias)           n/a ->     40.2

Held-out validation RMSE: 1055.3 cp (naive baseline: 1228.0 cp)
Held-out validation correlation: 0.511

For comparison, CURRENT hand-guessed constants on the same split:
  RMSE: 1099.2 cp, correlation: 0.494
```

### The most actionable finding: relative material values

Normalizing everything to Pawn = 1 (the fitted Pawn value, 96, is
almost identical to the hand-guessed 100, so this is a fair anchor):

| Piece | Current ratio to Pawn | Fitted ratio to Pawn |
|---|---|---|
| Rook | 9.00 | **15.89** |
| Cannon | 4.50 | **7.80** |
| Horse | 4.00 | **7.25** |
| Elephant | 2.00 | 2.10 |
| Advisor | 2.00 | 1.68 |
| Pawn | 1.00 | 1.00 |

**Elephant and Advisor's relative values look roughly right already**
(within ~5-16% of their fitted values). **Rook, Cannon, and Horse —
the three "attacking" pieces — appear substantially undervalued
relative to Pawn in the current hand-guessed scale**, by a consistent
factor of roughly 1.7-1.9x across all three. This is a real, coherent
pattern (not three unrelated numbers), and a plausible one on its own
merits: these are exactly the pieces whose value comes disproportionately
from mobility and attacking potential rather than raw material weight,
which a simple fixed material count wouldn't naturally capture — and
Pikafish's actual play, distilled through these labels, apparently
weighs that more heavily than this project's hand-guessed constants
(themselves never data-validated before this checkpoint) do.

### Other findings worth noting, with appropriate caution

- **`pst_balance` and `king_safety_balance` calibrated to ~8-10x their
  current implicit weight of 1** — suggests the existing piece-square-
  table bonuses and king-safety scores (individually small numbers,
  e.g. PST bonuses in the 0-18 range, king-safety bonuses/penalties in
  the 12-40 range) may be too small in aggregate magnitude relative to
  how much position and king safety actually matter, per this data.
- **`mobility_balance` and `endgame_balance` calibrated to ~4-5x their
  current implicit weight** — similarly suggestive, though these terms
  are OFF by default in `evaluate()`, so this doesn't reflect
  real-world impact on current play, only what the data would support
  if they were weighted differently were they enabled.
- **`pawn_structure_balance` and `piece_coordination_balance` calibrated
  to near-zero (0.2 and 0.6)** — worth treating with more caution
  than the material findings: near-zero regression coefficients can
  reflect either "this term genuinely doesn't matter much" or "this
  feature has low variance across the dataset, so its coefficient is
  poorly determined by the regression" — this checkpoint didn't check
  which explanation applies, and shouldn't be read as "these
  V0.4.4/V0.4.5 heuristics are useless" without that check.
- **A real +40cp intercept (tempo bias)** — after accounting for every
  other factor, the side to move appears to have a modest inherent
  advantage beyond material/position, consistent with general
  chess/Xiangqi theory that having the move is worth something. Not
  currently modeled anywhere in `evaluate()` at all.

## Known limitation

**The overall linear model is LESS accurate at predicting Pikafish's
score than V0.6.2's neural network** (1055 cp / 0.511 correlation vs.
the network's 760 cp / 0.786) — expected, since a linear combination
of hand-crafted features has strictly less expressive power than even
a small 2-hidden-layer MLP. This is not the point of this exercise,
though: the goal isn't the most accurate possible predictor, it's
better-informed constants for the existing, already-integrated,
already fast, already interpretable heuristic `evaluate()` — where, as
`docs/v0.6.2.md`'s conclusion argued, *consistency* inside alpha-beta
search plausibly matters more than raw correlation with a strong
reference engine.

**None of these calibrated values have been applied back into
`evaluation.py` or benchmarked in real play yet.** This checkpoint
produced and validated the *analysis*, not a tested improvement — see
Next step for exactly what that would require.

**The "current constants" baseline used for comparison treats every
optional term (`mobility_balance`, `pawn_structure_balance`,
`piece_coordination_balance`, `endgame_balance`) as always-on at
weight 1** — not the same as `evaluate()`'s actual default
configuration, where all four are off. This is a fair comparison for
what the *regression* is being asked to improve on, but shouldn't be
read as "the default `evaluate()` scores 1099 cp RMSE" — the real
default configuration wasn't separately measured here.

## Next step

**Test the material-value finding specifically** — the most confident,
coherent result, and the easiest to test in isolation without
touching the PST/king-safety/mobility scaling questions at the same
time: update `MATERIAL_VALUES` (or add an alternate, opt-in constant
set) with the fitted Rook/Cannon/Horse values, keep Elephant/Advisor/
Pawn as they are (already close to their fitted values), and run a
real `tools/compare_engines.py` comparison against the current
constants — the actual test of whether this data-informed adjustment
helps real play, the same way every other evaluation-term change in
this project has been validated.

**Investigate the near-zero pawn-structure/piece-coordination
coefficients** before concluding anything about them — check each
feature's actual variance/prevalence across the real corpus first
(the caution flagged in Results above).

**Consider adding the tempo/intercept term** as a new, tested,
optional `evaluate()` component (`use_tempo_bonus`, following this
project's own established pattern for every other optional term) —
the +40cp finding is plausible and consistent with general theory, but
like every other term in this project, deserves its own dedicated
test and a real strength comparison before being trusted, not just
adopted from one regression's output.

## Addendum (2026-09-06): wired the material-value finding into the engine for real testing

Acted on the "Next step" above — rather than leave the material-value
finding as analysis-only, made it directly testable.

**`evaluate()` gained an optional `material_values` parameter** (a
dict, same shape as the module-level `MATERIAL_VALUES`): `None`
(default) reproduces every prior version's exact behavior; passing an
override dict replaces the material lookup table entirely. Threaded
through `_piece_score` (evaluate()'s only internal caller of
`MATERIAL_VALUES`) and `SearchEngine`'s own new `material_values`
constructor parameter, which flows into `_evaluate()` alongside the
existing `eval_fn` override — the same pattern V0.6.2's pluggable
evaluator already established.

**`CALIBRATED_MATERIAL_VALUES`** (a new module-level constant in
`evaluation.py`): a copy of `MATERIAL_VALUES` with only Rook (900 →
1500), Cannon (450 → 750), and Horse (400 → 700) updated — rounded
from the exact fitted 1525.7/749.0/696.1 to the nearest 50 for a
plausible, testable constant, not because the extra precision was
shown to matter. Elephant/Advisor/Pawn deliberately left unchanged,
isolating the single most confident finding from the more speculative
PST/king-safety-scaling and near-zero pawn-structure/piece-coordination
findings the same analysis produced (see the original findings above).

**`tools/compare_engines.py`** gained `--a/b-use-calibrated-material`,
mirroring the existing `--use-opening-book`/`--use-neural-eval`
pattern exactly — both sides otherwise identical, only the material
table differs, giving a clean, isolated strength comparison.

**4 new tests**: default `material_values=None` preserves existing
behavior exactly; the calibrated table changes a position's score by
precisely the expected Rook-value delta (600 = 1500 - 900) with every
other term held constant; `SearchEngine` correctly threads the
override through to `_evaluate()`; and `CALIBRATED_MATERIAL_VALUES`
itself is verified to leave Elephant/Advisor/Pawn/King untouched.
Combined test total: **195/195 green**.

**Not yet run at real scale**: a comparison game was started in this
session but didn't complete within the per-command time budget (real
depth-2 games take 1-3+ minutes here, the same constraint every prior
real comparison in this project has run into). The mechanism itself is
confirmed correct and tested; the actual strength verdict needs a real
run — see Next step.
