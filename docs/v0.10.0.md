# V0.10.0 — Search Correctness and Horizon Cost

## Scope

This checkpoint follows the strength-oriented review of the current project. It fixes
search correctness edge cases first, strengthens objective tactical regression checks,
then takes a measured, behavior-preserving performance improvement. It does not claim
that these changes alone make the engine stronger overall.

## Search correctness

### Repetition

`Board.position_history` includes search-only null moves, so it cannot safely serve as
the actual-game repetition record. `Board.repetition_history` now tracks only the
initial position and positions reached through real moves; null moves do not add
repetition occurrences. `board_from_fen()` initializes both histories consistently.

Alpha-beta and quiescence check for repetition before accepting a TT score. A repeated
position with legal moves scores as a draw (0), and the repetition result is not stored
as a position-only TT value. As in `Rule.game_result()`, checkmate/stalemate takes
precedence over repetition. A root with no legal moves is scored as a loss. MCTS treats
repetition leaves as draws and does not search from an already-repeated root.

### Quiescence check evasions and TT separation

The quiescence ply cap no longer causes a position where the side to move is in check
to be statically evaluated. Check evasions continue to be searched until the side is no
longer in check; repeated positions terminate as draws. This avoids stand-pat evaluation
of an illegal-to-ignore check while retaining the cap on ordinary capture sequences.

Quiescence TT keys include the quiescence ply. The amount of remaining quiescence search
depends on that ply, so scores searched with different remaining budgets must not reuse
one another's entries. The separate key also prevents quiescence entries from colliding
with ordinary alpha-beta entries for the same board hash.

## Tactical regression coverage

The existing objective tactical fixtures now check the engine's behavior, not just the
fixture geometry:

- select a legal immediate mate when one exists;
- select an objectively safe capture in the free-capture position;
- avoid the capture that permits the opponent's immediate recapture.

The tests independently enumerate the property being checked instead of asserting an
unverified engine-preferred move. Existing diagnostics additionally cover board-state
restoration and search through depth 4.

## Horizon performance

At depth zero, when quiescence is enabled, `_negamax()` previously generated all legal
moves and then immediately called quiescence, which generated legal moves again. It now
delegates directly to quiescence; quiescence remains responsible for terminal-position
detection. When quiescence is disabled, the prior depth-zero terminal check is preserved.

Single-run iterative-deepening measurements on the checked reference positions:

| Position | Depth | Before | After | Nodes before/after | Score/move |
|---|---:|---:|---:|---:|---|
| initial | 3 | 4.798s | 2.735s | 5,115 / 5,115 | same |
| early_development | 3 | 6.063s | 3.666s | 5,512 / 5,512 | same |
| central_development | 3 | 3.193s | 1.953s | 4,485 / 4,485 | same |

These are local, single-run timings and are sensitive to machine load. The consistent
roughly 39–43% reduction at depth 3 is evidence for this optimization on the tested
positions, not a general throughput guarantee. The depth 2 results were noisier.

## Depth-4 vs. depth-3 strength check

Ran 20 alternating-color games with opening randomization disabled. Depth 4 played Red
in 10 games and Black in 10. The result was 10 wins, 10 losses, no draws: 50% score and
estimated Elo difference 0 for depth 4. The game records are in
`data/v0.10_depth4_vs_depth3.jsonl`.

This does not establish parity: a rough 95% interval for the score rate is 30–70%
(approximately -148 to +148 Elo). Every game used the same initial position and
deterministic search, so opening coverage is particularly limited. A multi-opening,
color-balanced match is needed before drawing a strength conclusion.
