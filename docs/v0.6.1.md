# AlphaZetaChess V0.6.1 — Monte Carlo Tree Search Skeleton

## Status

**Implemented and correctness-tested.** This is the search *mechanism*
only — no policy/value neural network yet (see Design). Confirmed
directionally sound against a real opponent (RandomEngine); **not**
yet shown to reliably win outright within a practical move limit at
the simulation budgets tested here (see Known limitation).

## Why this, and why now

`docs/v0.5-real-data-checkpoint-3.md` closed out the V0.5 line's three
open comparisons (opening book: null result; endgame heuristic: null
result at both depth=2 and depth=3; depth=3 vs depth=2: real +88.7 Elo
win) and recommended moving to V0.6 rather than continuing to grind
out more depth=3 self-play games for diminishing certainty on two
already-answered questions. `engine/base.py`'s own `ChessEngine`
docstring has said "future MCTSEngine / NeuralEngine / HybridEngine"
since it was written; this is the first of those three to actually
exist.

## Design

Full design rationale is in `engine/mcts.py`'s own module docstring
(read that first, it's the source of truth) — summary here:

- **Search skeleton first, evaluation function second** — same split
  V0.3 (Negamax/Alpha-Beta skeleton, material-only eval) used before
  V0.4's five checkpoints enriched evaluation without touching search
  again. `MCTSEngine` uses the *existing* `evaluate()` function
  (V0.4.x/V0.5.3, whichever optional terms are configured) as its leaf
  value estimator, and **uniform** move priors (`1/num_legal_moves`)
  in place of a policy network. Both are exactly the two things a
  future V0.6.2 (trained value + policy network) would replace,
  without touching the tree-search logic (selection, expansion,
  backup) around them.
- **PUCT selection** (the AlphaZero formula), same as AlphaZero-family
  engines use once they add a real network — the formula's shape
  doesn't change when the priors go from uniform to learned, only the
  `prior` values fed into it.
- **Leaf evaluation via `evaluate()`, not random rollout to terminal.**
  A deliberate choice with a real side benefit beyond speed: each
  simulation's *depth* is bounded by the current size of the tree
  (selection only walks already-expanded nodes; expansion adds exactly
  one new level per simulation), so there's no risk of a single
  simulation recursing arbitrarily deep the way rollout-to-terminal
  can, and no `max_rollout_depth` safety valve is needed.
- **Terminal handling**: no legal moves is *always* a certain loss
  (`terminal_value = -1.0`) for the side to move, matching Xiangqi's
  own rule that stalemate is a loss, not a draw (see `core/rule.py`'s
  docstring) — checkmate and stalemate don't need to be distinguished
  for MCTS's value backup.
- **The one thing most worth getting right, and testing directly**:
  every `_MCTSNode`'s own `visit_count`/`value_sum` is from the
  perspective of whichever color is to move *at that node*. A child's
  average is therefore from the *opponent's* perspective relative to
  its parent, and `_select_child` must **negate** it before comparing
  children — using it unnegated would select for what's good for the
  opponent. This is the single most error-prone part of any
  minimax/negamax/MCTS implementation to get backwards, and gets a
  dedicated, deliberately isolated unit test rather than relying only
  on end-to-end play to catch it indirectly (see Correctness gates).

## Correctness gates (`tests/test_mcts_v061.py`, 12 tests)

1-3. `_squash` (the tanh value-bounding helper): zero maps to zero,
strictly monotonic and bounded within (-1, 1), antisymmetric.

4-5. `_MCTSNode.expanded` correctly reflects whether `children` has
been set.

6. **The sign-convention test.** Two children with equal visit counts
(so PUCT's exploration term ties) but opposite average values —
`_select_child` must pick the child whose *negated* average favors the
parent, not the one with the larger raw average. A naive, unnegated
implementation would fail this test by picking the wrong child.

7. `_select_child` favors giving an entirely unvisited child a look
when a visited sibling is exactly neutral (Q=0 for both, but the
unvisited child's exploration term should dominate) — the core PUCT
exploration behavior working as intended.

8. `_expand_and_evaluate` marks a real checkmate position (constructed
via the same forced-mate fixture pattern used across the V0.3.x-V0.5.x
suite, then advanced one move via `SearchEngine`) as `terminal_value =
-1.0` exactly.

9. `_expand_and_evaluate` on a normal (non-terminal) position creates
exactly one child per legal move, with priors summing to 1.0, and
returns a value within `[-1, 1]`.

10. `choose_move` from the starting position returns a genuinely legal
move (cross-checked against `Rule.generate_legal_moves`) and correctly
reports `nodes_evaluated`/repurposed `depth` (= simulation count).

11. `choose_move` returns `best_move=None` when there are no legal
moves at all (mirrors `SearchEngine`'s own convention for this case).

12. **The cross-validation test, and the strongest evidence this
implementation is actually correct, not just internally consistent**:
on the forced-mate fixture, `MCTSEngine(simulations=300)` finds the
*exact same* mating move `SearchEngine(depth=2)` (an independently
implemented, already-trusted alpha-beta oracle) finds — rather than
hand-verifying the winning square myself, letting two independently
implemented search algorithms agree is much stronger evidence than
either one's self-consistency alone.

Combined with every other targeted test file: **142/142 green.**

## Smoke test (this session)

```python
board = Board()
result = MCTSEngine(simulations=100).choose_move(board, Color.RED)
# -> legal move, 0.31s
```

**MCTSEngine vs RandomEngine, 6 games, simulations=150, max-moves=150:**
```
6/6 draws (move limit) -- 0 decisive results either way.
```
This looked concerning at first glance — a working search engine
should crush a random-move opponent, and V0.2's own history used
exactly that comparison as its first strength proof for `SearchEngine`.
Investigated directly rather than either dismissing it or assuming a
bug:

```
MCTSEngine(simulations=300) as Red vs RandomEngine as Black,
tracking material every 10 plies:
  ply 10: Red 4800 / Black 4400
  ply 20: Red 4700 / Black 4400
  ply 30: Red 4150 / Black 4000
  ply 40: Red 4150 / Black 3600
  ply 50: Red 4150 / Black 3600
  ply 60: Red 4150 / Black 3600
```
**MCTSEngine reliably builds a real, growing material advantage against
RandomEngine** — the mechanism is directionally sound, not broken.
What it does *not* reliably do at this simulation budget is *convert*
that advantage into checkmate within a 150-move cap — an expected
characteristic of vanilla MCTS without a policy/value network (which
needs many more simulations per move than alpha-beta needs plies to
reliably find precise mating sequences), not evidence against the
implementation's correctness, which the unit tests above (especially
#12, the direct alpha-beta cross-validation) already establish
independently of this smoke test.

## Known limitation

**Simulation budgets in the 100-800 range don't reliably produce
decisive game outcomes within a 150-move limit**, even against a
non-adversarial (random) opponent that a properly-tuned SearchEngine
handles easily. This is very likely a *simulation-budget* limitation
rather than a *correctness* limitation (see the material-gain evidence
above and the mate-in-one cross-validation test), but that's a
hypothesis this checkpoint didn't have time to confirm — a proper win-
rate benchmark at a much higher simulation count (thousands per move,
typical for vanilla, no-policy-network MCTS) is the natural next
empirical step, at real computational cost.

No CLI wiring (`tools/compare_engines.py`, `tools/benchmark.py`) added
yet for `MCTSEngine` specifically — this checkpoint's smoke tests used
ad hoc scripts importing `run_match` directly. Adding proper CLI
support once there's a specific comparison worth running repeatedly
(e.g. "how many simulations does MCTSEngine need to match
SearchEngine(depth=2)?") is a natural, well-scoped next increment.

## Next step

Two independent directions, neither blocking the other:

**Tune/benchmark the existing skeleton**: find the simulation count
where `MCTSEngine` reliably beats `RandomEngine` decisively (not just
materially), and where it starts competing with `SearchEngine` at
various depths — this needs real computational budget (a local run,
not this sandbox) and CLI support to run repeatably:
```bash
# (not yet supported -- natural V0.6.1-followup CLI addition)
python tools/compare_engines.py --a-engine mcts --a-simulations 1000 --b-engine random --games 20
```

**Build the actual policy/value network (V0.6.2)**: the two spots this
checkpoint deliberately left as placeholders --
`_expand_and_evaluate`'s call to `evaluate()` (replace with a learned
value head) and its uniform `1/num_legal_moves` priors (replace with a
learned policy head) — are exactly where a network plugs in, without
touching `_simulate`/`_select_child`'s tree-search logic at all. This
needs training data and infrastructure that doesn't exist yet (a much
bigger undertaking than any single V0.5.x/V0.6.1 checkpoint) — a
reasonable moment to pause and think through what that infrastructure
needs to look like before writing any of it, rather than rushing a
first attempt.
