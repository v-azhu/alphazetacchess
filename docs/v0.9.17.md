# V0.9.17 — Root Candidate Diagnostic

## Goal

V0.9.13–V0.9.16 progressively isolated the earlier search-score instability:

- Null Move reduced node count without changing tested decisions.
- TT and PVS A/B tests produced identical best moves and scores on the tested suite.
- Quiescence Search materially affected shallow scores and, on some positions, shallow root decisions.

V0.9.17 does not modify the engine. It exposes the relationship between static evaluation and searched root-candidate score.

## Method

For each selected position and depth:

1. Generate all legal root moves.
2. Evaluate every root move statically using the engine's current evaluation.
3. Select the top N static candidates.
4. Independently search each selected root move with a full alpha-beta window.
5. Always include the normal engine's root choice, even if it is outside the static top N.
6. Report static score, searched score, and search-minus-static delta.

The diagnostic keeps TT, PVS, Quiescence, and History enabled, with Null Move disabled.

The per-candidate diagnostic search deliberately uses a full window, so candidate comparison is not itself a root-PVS experiment.

## User Results

### tactical_exchange — depths 2–4

The engine selected the same move at all three depths except that its score changed:

| Depth | Engine move | Score |
| --- | --- | ---: |
| 2 | (1,2)->(3,3) | 0 |
| 3 | (4,2)->(4,6) | 190 |
| 4 | (4,2)->(4,6) | 0 |

The candidate diagnostic shows why the depth-3 decision changes:

- d2: (1,2)->(3,3) static 120, search 0; (4,2)->(4,6) static 110, search 0.
- d3: (4,2)->(4,6) static 110, search +190, while (1,2)->(3,3) falls to +20.
- d4: (4,2)->(4,6) remains the best searched candidate at 0; (1,2)->(3,3) falls to -70.

This is evidence that search discovers a tactical or positional consequence for (4,2)->(4,6) at depth 3 that static evaluation does not see. At depth 4, another ply removes that advantage from the score. The best move itself remains (4,2)->(4,6).

### initial — depths 3–4

At depth 3 the two horse-development moves have static/search score +100 and are selected. The two cannon captures of the opposing rooks have static score +600 but searched score -60.

At depth 4:

- the horse-development moves score 0;
- the cannon captures fall further to -160;
- the same horse move remains the engine choice.

This is a useful sanity check: static evaluation strongly values the rook capture because material gain is visible immediately, while deeper search rejects it. That is normal evidence of search correcting a shallow material attraction, not evidence that static evaluation itself must rank the move correctly after tactics.

### open_position — depths 3–4

The same general pattern appears:

- horse development is selected by the engine at both depths;
- the cannon captures have static score +600 but searched score -60 at d3 and -160 at d4;
- the engine's selected horse move scores +100 at d3 and 0 at d4.

Again, search overrides an apparently attractive immediate capture after seeing the opponent's reply.

### Current interpretation

The V0.9.17 output does **not** currently point to a simple static-evaluation defect.

The stronger finding is:

> Static evaluation and searched evaluation are behaving differently for concrete tactical reasons, and the remaining score instability is concentrated in what deeper search discovers after the root move.

The initial/open positions provide a healthy example of search rejecting a superficially valuable rook capture. The tactical position provides a more interesting example where a candidate gains +80 over static evaluation at d3 and then loses that search advantage at d4.

This shifts the next investigation from “which global evaluation component is broken?” toward “what concrete reply/path causes the score to change?”

## Important Diagnostic Caveat

The current root-candidate tool reuses one diagnostic SearchEngine across the selected root moves at a given depth. Its TT entries are position-keyed and therefore should remain semantically valid, but this makes the output less clean for forensic analysis than a completely fresh engine per candidate.

Consequently, the results above are sufficient to guide the investigation, but before drawing a strong conclusion from exact candidate scores, the next PV tracer should use a fresh search context for each root move or explicitly disable TT.

## Next step

The next diagnostic should be a **PV / principal-reply tracer** for a small number of suspicious root moves, especially:

- tactical_exchange: (4,2)->(4,6) at depths 3 and 4;
- tactical_exchange: (1,2)->(3,3) at depths 3 and 4;
- initial: (1,2)->(1,9) and its mirrored counterpart;
- open_position: (1,2)->(1,9) and its mirrored counterpart.

The tracer should expose the principal reply sequence and the evaluation at the leaf/QS boundary. That will let us distinguish a genuine horizon effect from an evaluation component changing the score.

No engine optimization should be added until a concrete search path identifies an actionable issue.

## Interpretation

The important signal is not simply whether search-minus-static is large. Large deltas are normal because search discovers tactics and positional consequences.

Look for:

- a high-static move with a sharply negative search delta;
- a modest-static move with a sharply positive search delta;
- candidate rankings changing substantially between depths;
- the engine's selected move being absent from the static top group;
- tactical fixtures where a clearly forced move is not recovered.

These patterns help distinguish evaluation mis-ranking, tactical horizon effects, Quiescence effects, and ordinary deeper-search correction.

## Limitation

The diagnostic searches selected root moves independently. It is a diagnostic view, not a replacement implementation of SearchEngine._search_fixed_depth. Node counts and exact timings should not be interpreted as a performance benchmark.

The current tool does not reconstruct a complete PV. A dedicated PV tracer is the proposed next diagnostic.
