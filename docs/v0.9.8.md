# V0.9.8 — Stale-Doc Sweep, `--engine random`, and the Baseline Finding It Exposed

## Status

**IMPLEMENTED and tested** (319/319 full suite green). Started as a deliberate sweep
for stale "flagged but never done" notes across all 48 files in `docs/`, following
V0.9.7's suggestion that such a sweep would likely turn up more small, concrete wins.
It did -- and one of them turned out to expose a genuinely significant engine finding,
not just a documentation cleanup.

## Stale items found

A keyword sweep (`not done`, `not implemented`, `TODO`, `not attempted`, `not wired`,
`deferred`, `follow-up`, ...) across every doc turned up three items that were stale
*as claims*, not merely as unfinished work:

1. **`docs/v0.7.2.md`'s scope boundary** still says time-based UCCI controls
   (`usemillisec`/`time`/`opptime`/`movetime`) "are not implemented yet" -- V0.7.3
   implemented all of them (`protocol/search_limits.py`). Accurate when written,
   misleading now.
2. **`docs/v0.6.1.md`'s next-step example** shows
   `compare_engines.py --a-engine mcts --b-engine random` annotated
   "(not yet supported -- natural V0.6.1-followup CLI addition)". V0.9.2 added
   `--{prefix}-engine`, but only with `search`/`mcts` choices -- so the `random` half
   of that example was *still* unsupported, two full minor versions after the note was
   written. This is the actionable one.
3. `docs/v0.6.2.md`'s "not wired into `SearchEngine`/`MCTSEngine`" note about the value
   network -- checked and still accurate (`eval_fn` exists as a hook, but nothing
   wires a trained value network in by default), so left alone.

## What this builds: `--{a,b}-engine random`

`RandomEngine` has existed since V0.1 and is the baseline this project's own "Engine
Benchmark" section in `docs/roadmap.md` measures against -- but it was never reachable
from `tools/compare_engines.py`. Added as a third `--{prefix}-engine` choice. It
ignores every other flag on its side, by construction rather than by policy: there is
no search, evaluation, or ordering to configure.

## The finding this immediately exposed

Running the exact command `docs/v0.6.1.md` had been recommending since V0.6.1, now
that it actually works:

**Uniform-prior MCTS (200 sims) vs. RandomEngine** (10 games,
`data/v0.9.8_mcts_uniform_vs_random.jsonl`):

```
MCTS wins:   0
Random wins: 0
Draws:      10   (every single game hit the 150-move limit)
```

**Heuristic-prior MCTS (200 sims) vs. RandomEngine** (10 games,
`data/v0.9.8_mcts_heuristic_vs_random.jsonl`):

```
MCTS wins:   9
Random wins: 1
Draws:       0
Score rate: 90%, estimated Elo ~+382
```

**Sanity check that the harness itself is sound** (6 games, not saved): `SearchEngine`
at depth 2 vs. RandomEngine goes **6-0**, all decisive, 44-88 moves. So the 0-0-10
above is a real property of uniform-prior MCTS, not a broken comparison or a
move-limit artifact affecting everything equally.

### Why this matters more than it first looks

**Uniform-prior MCTS could not beat a player making uniformly random moves.** Not
"beat it narrowly" -- it failed to convert a single game in ten, hitting the move limit
every time. It presumably accumulates material (its leaf evaluation is the same
`evaluate()` `SearchEngine` uses) but cannot convert an advantage into a finished win
within 150 moves. That is a far more damning baseline result than V0.9.2's
already-decisive "MCTS loses badly to SearchEngine" finding, and it had gone unmeasured
for three minor versions purely because the CLI couldn't express the comparison.

It also **retroactively strengthens V0.9.5's promotion of `use_heuristic_priors`**
considerably. That decision rested on a 96-game equal-time comparison showing 65.6%
(p=0.0022) -- real, but a modest-sounding edge. Against the random baseline the same
change is the difference between *never winning* and *winning 90%*. The
`docs/v0.9.3.md` framing of heuristic priors as "a real, measurable lever on MCTS's
own internal strength" turns out to have understated it: on this baseline it is closer
to the difference between a functioning engine and a non-functioning one.

### Honest caveats

- n=10 per configuration. The *contrast* (0/10 vs. 9/10) is stark enough that its
  direction isn't in doubt, but the precise rates aren't pinned down, and the ~+382
  Elo figure inherits the same near-extreme-score instability `docs/v0.9.2.md` already
  flagged for its own ~-570 figure. Treat it as "decisively better," not as a number.
- This does not change any standing recommendation. `SearchEngine` remains the engine
  to prefer for real play (V0.9.2's large gap is untouched by any of this);
  `use_heuristic_priors` was already promoted to `MCTSEngine`'s default in V0.9.5, so
  the *current* default configuration is the one that wins 9/10 here, not the one that
  wins 0/10. Nothing needs to change as a result of this finding -- it explains and
  reinforces decisions already made.
