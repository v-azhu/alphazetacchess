# V0.3.3 — Negamax / PVS

## Goal

Refactor the V0.3.2 Alpha-Beta search (separate maximizing/minimizing
branches, tracked relative to `root_color`) into a single Negamax
recursion, then layer Principal Variation Search (PVS) on top of it,
while preserving V0.3.2's search result on every tested position.

## Design

### Negamax

Xiangqi is a two-player zero-sum game, so a position's value to the
side to move is always the negation of its value to the opponent:
`value(node, color) == -value(node, opponent)`. This lets the old
`_minimax`/`_alphabeta` maximizing/minimizing pair collapse into a
single `_negamax(board, depth, alpha, beta, current_color, root_depth,
use_pruning)` that always returns the score from `current_color`'s own
point of view; the caller negates it and negates/swaps the alpha-beta
window on each recursive call.

A side effect: because every node's score is now naturally expressed
from the mover's own point of view, the transposition table key no
longer needs `root_color` (see `docs/v0.3.2.md`, which had flagged
this as a known limitation) — `board.zobrist_hash` alone identifies
the position, and TT entries become reusable across searches
regardless of which color initiated the search.

`use_pruning=False` keeps a plain, exhaustive Negamax path (still
exact, just without Alpha-Beta cutoffs) as a correctness baseline,
mirroring V0.3.2's `use_alpha_beta=False` minimax path.

### Principal Variation Search (PVS)

At every node (including the root), the first move (already the
best-ordered one, via root ordering and/or the TT-suggested move) is
searched with the full `(alpha, beta)` window. Every subsequent move
is first probed with a cheap null window `(alpha, alpha+1)`: if the
probe fails low (score <= alpha), the move is confirmed worse than the
current best and the cheap result is kept; only if the probe suggests
the move might actually be better is it re-searched with the full
window for an exact value. This prunes more aggressively when move
ordering is already good, without changing the final result.

PVS is automatically disabled whenever `use_alpha_beta=False`, since a
null-window probe is meaningless without pruning.

## Scope

V0.3.3 deliberately does NOT introduce:

- quiescence search
- null-move pruning
- history heuristic / killer moves
- late move reductions

Those remain later V0.3.x / V0.4 items so each optimization stays
independently measurable.

## Acceptance Criteria

1. Existing tests remain green.
2. Negamax (no pruning) computes the same score as V0.3.2's plain
   minimax on tested positions (Negamax is a restructuring, not a
   different search).
3. Negamax + Alpha-Beta (no PVS) computes the same score/move as
   V0.3.2's Alpha-Beta on tested positions.
4. PVS computes the same score/move as Negamax + Alpha-Beta without
   PVS, on every tested position (`test_pvs_matches_plain_alpha_beta_*`).
5. A constructed forced-mate position is still solved correctly end to
   end: the search finds the mating move, and replaying it satisfies
   `Rule.is_checkmate` (`test_negamax_terminal_scoring_matches_checkmate_detection`).
6. Benchmark PVS vs non-PVS Negamax (nodes, time) at depth 2 and 3 and
   record results here before marking complete.
7. No change to Xiangqi rules or evaluation semantics.

## Measured Results (2026-08-29)

All runs: iterative deepening on, TT on, Alpha-Beta on; only `use_pvs`
toggled. Same three reference positions as the V0.3.1 benchmark.

| Position | Depth | No PVS | PVS | Same score/move |
|---|---|---|---|---|
| initial | 2 | 3.05s / 973 nodes | 3.05s / 982 nodes | yes |
| early_development | 2 | 2.33s / 671 nodes | 2.38s / 685 nodes | yes |
| central_development | 2 | 0.60s / 171 nodes | 0.61s / 173 nodes | yes |
| initial | 3 | 6.56s / 2769 nodes | 6.76s / 2782 nodes | yes |
| early_development | 3 | 16.15s / 5317 nodes | 15.34s / 4812 nodes | yes |
| central_development | 3 | 13.78s / 5223 nodes | 13.36s / 5082 nodes | yes |

**Honest reading:** at depth 2, PVS is a small net loss (slightly more
nodes/time) — the null-window probe's own overhead isn't paid back by
extra pruning when so little tree remains below it. At depth 3, PVS
starts to pay off on two of the three positions (up to ~9.5% fewer
nodes on `early_development`), but is still roughly break-even on
`initial`. This matches the qualitative expectation already encoded in
`test_pvs_benefit_grows_with_depth` (PVS's relative benefit should not
shrink as depth grows) without over-claiming a large win at these
still-shallow depths. PVS is being kept on by default because (a) it
never changes correctness, (b) its worst-case overhead measured here
is small (~3% at depth 2), and (c) its benefit is expected to compound
further once quiescence search (V0.3.4) makes deeper searches
practical and move ordering has more tree left to prune.

## Known Limitation

PVS's benefit at the currently-practical depths (2-3) is small and
sometimes slightly negative. This is expected and documented rather
than hidden; it is not a regression against V0.3.2, since correctness
(criteria 2-5 above) is fully preserved on every tested position.

## Next Step

V0.3.4: Quiescence search (tactical move set, capture search, check
extensions, horizon-effect tests, performance/strength benchmark) —
this is the next lever expected to make deeper search both affordable
and worthwhile, which should also let PVS's benefit show up more
clearly.
