# V0.9.6 — Self-Play Policy Distillation: Infrastructure, and a Negative Generation-0 Result

## Status

**IMPLEMENTED, tested, and given a first real training run** (319/319 full suite
green). Picked as the direct follow-through on `docs/v0.9.4.md`'s "Round 2" conclusion:
two rounds of training a policy network to imitate Pikafish's *independent* move
preference both failed to beat V0.9.3's heuristic priors, and the more promising
untried direction identified there was training toward `MCTSEngine`'s *own* search
result instead -- a fundamentally different signal, real AlphaZero-style self-play
distillation rather than external-engine imitation. Unlike the Pikafish pipeline, this
needs no external engine or user-local setup at all: `MCTSEngine` already *is* the
label source, so this entire round -- infrastructure, data generation, training, and
real strength comparisons -- was completed in one session without the usual
user-in-the-loop labeling step.

## What this builds

**`MCTSEngine.search_root(board, color, stop_event=None)`** (`engine/mcts.py`):
`choose_move` is refactored to build on this new method, which returns the raw root
`_MCTSNode` (plus `legal_moves` and `completed_simulations`) instead of just a
`SearchResult` -- exposing the full move -> visit-count distribution at the root, not
just the single most-visited move. `choose_move`'s own public behavior is completely
unchanged by this refactor (verified by the full suite staying green with zero changes
needed to `choose_move`'s own existing tests). `root_visit_distribution` is a thin
convenience wrapper returning `{move: visit_count}`.

**`tools/generate_mcts_policy_labels.py`**: plays `MCTSEngine` against itself and
records, at every position, the search's own most-visited root move as a policy label
-- `{fen, score_cp, best_move}`, the *exact same* format
`tools/label_positions_with_pikafish.py` produces, so `tools/train_policy_network.py`
needed zero changes to consume this data. `score_cp` comes from the root's own value
estimate (un-squashed back through `atanh`, matching `engine/mcts.py`'s
tanh-squashing convention), included only for schema compatibility -- the policy
target doesn't depend on it. Random-opening plies (matching `self_play.py`'s own
game-diversity convention) still record the search's *real* choice as the label even
on a ply where a random move gets played instead, rather than misrepresenting the
random move as the search's preference.

6 new tests (`tests/test_mcts_search_root_v096.py`), including a same-call
cross-check against `choose_move`'s own decision and a verified (not assumed)
off-by-one in visit-count accounting (the first simulation expands the root itself
without visiting a specific child, so child visits sum to
`completed_simulations - 1`, not `completed_simulations` exactly).

## Generation-0 data and training

Generated **5,263 real self-play labels** (65 games, 200 simulations/move, `data/mcts_
policy_labels.jsonl`) -- already exceeding the first Pikafish round's 4,106-example
scale, in a fraction of the wall-clock time that round needed, since no external
process or user-local setup was in the loop. Verified clean (all records parse, no
skipped/illegal `best_move`s). 1,036 distinct target classes, comparable diversity to
the Pikafish rounds' 819-1,408.

Trained `PolicyMLP` on this data with `tools/train_policy_network.py`'s existing
defaults (`lr=0.01`), via several checkpoint-resumed bounded training chunks (a sandbox
execution-time workaround, not a methodology change, same approach `docs/v0.9.4.md`'s
two rounds already used). **Validation accuracy plateaued at 28.90%** -- clearly lower
than either Pikafish round (43.92%/47.1%). Confirmed real overfitting before stopping:
training accuracy reached 90.75% while validation accuracy had been flat around 27-28%
for 150+ epochs. This lower ceiling is not surprising in retrospect: a 200-simulation
MCTS search (even with V0.9.5's heuristic priors active during data generation -- see
below) is a much noisier "expert" than Pikafish, so the labels themselves carry less
learnable signal per example than the Pikafish rounds' labels did.

## Real strength results

Using the same `tools/compare_engines.py --{prefix}-policy-network` flag V0.9.4 added:

**Self-play-distilled policy vs. uniform priors** (20 games, `data/v0.9.6_selfplay_
policy_vs_uniform.jsonl`): 45.0% (9-11), 95% CI [23.2%, 66.8%] -- roughly even, similar
to both Pikafish rounds' results against the same baseline.

**Self-play-distilled policy vs. V0.9.3's heuristic priors** (19 games, `data/v0.9.6_
selfplay_policy_vs_heuristic_priors.jsonl`): **15.8% (3-16)**, 95% CI [-0.6%, 32.2%] --
clearly losing, the same qualitative pattern both Pikafish rounds showed against this
baseline (24.0% and 0/19 respectively).

## A telling detail: the label source and the losing baseline are the same search

`tools/generate_mcts_policy_labels.py` constructs `MCTSEngine(simulations=
args.simulations)` with no override -- since V0.9.5, that means `use_heuristic_priors=
True` by default, so **the self-play data was generated by the exact search
configuration (heuristic-prior MCTS) that the resulting trained network then lost to**.
This makes the result more interpretable, not less: distilling a search's own
conclusions into a small, fast classifier is inherently lossy -- with only ~5,263
examples over 1,036 classes, the approximation (28.9% top-1 accuracy) is too crude to
preserve the quality of the very signal it was trained to imitate. This is the expected
shape of a true generation-0 bootstrap: real AlphaZero-style training needs many
generations of self-play (each network's improved priors feeding into the next
generation's search, at a much larger scale than one 65-game round) before a distilled
network exceeds the search that trained it -- a single round was never likely to clear
that bar, and this result is the concrete confirmation rather than an assumption.

## Conclusion across three rounds

Three attempts now, two different training signals (external-engine imitation via
Pikafish, self-distillation via `MCTSEngine`'s own search), all three losing clearly to
V0.9.3's heuristic priors:

| Round | Signal | Examples | Val accuracy | vs. uniform | vs. heuristic priors |
|---|---|---|---|---|---|
| V0.9.4 round 1 | Pikafish imitation | 4,106 | 47.1% | 50.0% | 24.0% |
| V0.9.4 round 2 | Pikafish imitation | 16,213 | 43.9% | 50.0% | 0.0% |
| V0.9.6 gen 0 | Self-distillation | 5,263 | 28.9% | 45.0% | 15.8% |

**Recommendation: stop incremental investment in the policy-network direction for
now.** Three rounds across two genuinely different approaches have not produced a
network that beats the one approach that *has* worked (V0.9.3's heuristic priors,
promoted to `MCTSEngine`'s default in V0.9.5). Continuing would require either (a) a
much larger scale of self-play (multiple generations, far more than 65 games per
round) -- a real, multi-session undertaking, not an incremental next step, or (b) a
different architecture/approach entirely. Neither is a natural next increment; this is
a deliberate stopping point for the thread, not an unfinished one. `MCTSEngine`'s
`policy_fn` parameter (V0.9.4) and `search_root`/`root_visit_distribution` (this
checkpoint) remain available infrastructure for whoever picks a larger-scale attempt
back up later -- nothing here needs to be rebuilt, only run at a much larger scale.

## Scope boundary

No multi-generation bootstrap loop (train on generation N's self-play, generate
generation N+1's self-play with the trained network's priors, repeat) -- this
checkpoint is a single generation-0 round, deliberately, to get a first real
data point before committing to the much larger effort a real bootstrap loop would
need. `PolicyMLP`'s architecture and training loop are unchanged from V0.9.4 -- this
checkpoint is entirely about the data source, not the network or training method.
