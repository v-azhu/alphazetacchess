# V0.5 — Second Real Data Checkpoint (2026-09-05)

## What this is

Supersedes `docs/v0.5-real-data-checkpoint.md`'s 12-game corpus. The
user ran several real self-play/comparison batches locally (where a
real background process is practical, unlike this session's sandbox)
and pushed the results: **63 real games** now in `data/selfplay.jsonl`
(up from 12), all depth=2. This is the first checkpoint where the
numbers are large enough to say something more than "too small to
tell" about at least one of V0.5's open questions.

## Corpus composition

```
63 total games:
  38 games: plain self-play, both sides identical config
            (depth=2, no optional eval terms, random opening) --
            RESULT: 40 draws / 12 RED wins / 11 BLACK wins overall
            (across all 63 games; this is the corpus's main bulk).
  25 games: tools/compare_engines.py, use_endgame_heuristics ON vs OFF
            (14 with ON as Red, 11 with ON as Black -- colors were
            alternated as designed).
```

## Opening book: rebuilt, now real and substantial

`tools/build_opening_book.py --input data/selfplay.jsonl --output
data/opening_book.json` against the full 63-game corpus produces
**1057 unique positions, 1121 position-move entries** (the version
committed alongside the data had gone stale at 689 positions --
apparently built against an intermediate, smaller version of the
corpus partway through the local collection process; rebuilt fresh
from the final 63-game file as part of this checkpoint).

Sanity-checked end to end, not just "the file exists":
```python
book = load_book("data/opening_book.json")
engine = SearchEngine(depth=2, use_opening_book=True, opening_book=book, opening_book_min_games=3)
engine.choose_move(Board(), Color.RED)
# -> SearchResult(best_move=(1,0)->(2,2), score=None, nodes_evaluated=0, depth=0, from_book=True)
```
`from_book=True` confirms the book is actually consulted and actually
returns a move — this is the first time in the project this has been
verified against a real, non-trivial book rather than a hand-built
2-3-entry test fixture. Still off by default (`use_opening_book=False`)
-- book *quality* (does it actually improve play, or just reproduce
whatever the shallow self-play engine happened to try first) is a
separate, still-open question from "does the mechanism work."

## Endgame heuristic: real signal now, and it's a null result

`tools/analyze_endgame.py` against the full 63-game corpus:
```
Reached endgame phase: 30/63 games
Average endgame onset ply: 66.1
Positions with a Rook/Cannon edge at onset: 16 (tied: 14)
  Favored side won 8/16 (50%), lost 1, drew 7
  NOTE: sample too small to draw real conclusions...
```
16 is close to (just under) the 20-decided-position threshold the tool
treats as reasonable, and the result is a flat 50% — no signal, in
either direction, from the "material edge at endgame onset" analysis.

More directly: isolating the 25 `use_endgame_heuristics` on-vs-off
comparison games specifically (computed manually against the raw
records, cross-checking `tools/compare_engines.py`'s own Elo-diff
formula):
```
25 games: ON  3 wins  /  OFF  3 wins  /  19 draws
ON score rate: 50.0%
Estimated Elo difference (ON - OFF): +0
```
**This is a real, if still modest-sized, null result**: across 25
real games, turning `use_endgame_heuristics` on made no measurable
difference. Two honest readings, and this doc doesn't pick one:

1. The heuristic's magnitude (+40/-40) might genuinely be too small to
   matter at depth=2, where search itself doesn't reach deep enough
   into a true 車炮 imbalance to exploit or be hurt by a fixed
   material nudge either way.
2. Depth=2 self-play is extremely draw-heavy (19/25 = 76% draws in
   this specific comparison slice, and 40/63 = 63% overall) — a format
   this drawish has limited statistical power to detect a real but
   modest effect even if one exists, regardless of sample size, unless
   the sample gets substantially larger or search goes deeper.

Either way, the previous checkpoint's small-sample 75% "favored side
won 3/4" number is now understood to have been noise, exactly as that
checkpoint's own caveat warned it might be — a good example of why the
"sample too small to trust" note exists and is worth taking literally
rather than as boilerplate.

**`use_endgame_heuristics` stays off by default.** Not because it was
shown to hurt (it wasn't — score rate is exactly 50%), but because
this checkpoint found no evidence it helps either, and the project's
established default posture (see `docs/v0.4.4.md`'s and `docs/v0.4.5.md`'s
own reasoning for their optional terms) is "on by default only once
measured to help," not "on by default until measured to hurt."

## What this checkpoint does NOT establish

- Whether `use_endgame_heuristics` would show a different result at
  depth=3+ (where search can actually act on the material nudge more
  meaningfully) — untested.
- Opening book *quality* — a 1057-position book existing and being
  consultable is a mechanism fact, not a strength claim. No
  `compare_engines.py` run with `use_opening_book` on one side vs. off
  on the other has been done yet.
- Whether depth=3 beats depth=2 (a separate open `tools/compare_engines.py`
  question from `docs/v0.5.4.md`, still untouched by any run so far).
- The draw rate itself (63%) is worth independent attention: it may
  indicate depth=2 self-play without any optional eval terms just
  isn't decisive enough to be a good source of training/comparison
  signal, independent of any specific evaluation term's effect. Worth
  keeping in mind if future comparisons keep coming back "no
  detectable difference."

above:** `tools/compare_engines.py` currently has no `--a-use-opening-book`
/ `--b-use-opening-book` flag — V0.5.4 was built before this checkpoint's
book became substantial enough to be worth comparing against. Adding
that flag is a small, natural next increment now that there's an
actual reason to want it.
