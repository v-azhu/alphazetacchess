# V0.6.4 — Combined Calibrated Weights (Material + PST + King Safety)

## Status

**IMPLEMENTED and tested** (287/287 full suite green). Prepared for the user to run
the real strength comparison -- this doc's own "Script to run" section is the actual
deliverable, following the same "I build and verify the mechanism, the user runs the
real multi-game comparison" division of labor V0.6.3's and V0.8.3's real-game results
both used.

## Why

`docs/v0.6.3.md`'s second addendum found `CALIBRATED_MATERIAL_VALUES` alone leans
*negative* in real play (~-53 Elo over 120 games) despite being a better statistical fit
to Pikafish's static evaluation, and raised two untested hypotheses for why. This
checkpoint builds the infrastructure to test the first one: the same V0.6.3 regression
also fit `pst_balance` and `king_safety_balance` to roughly 9.9x and 8.3x their current
implicit weight of 1 (`docs/v0.6.3.md`'s Results section), but that finding was
deliberately *not* applied alongside the material change, to isolate the most confident
finding from the more speculative ones. If the material table now being
"more accurate in isolation" is actually *inconsistent* with the rest of `evaluate()`'s
un-recalibrated weighting, applying all three calibrated findings together, rather than
material alone, should change the picture.

## Design

`evaluate()` gains `pst_weight=1`/`king_safety_weight=1` (both default 1, exactly
reproducing every prior version's behavior -- the same "None/1/False means unchanged"
convention every optional term in this file has used since V0.4.3). Required splitting
`_piece_score` (previously combined material + PST into one return value) into
`_piece_score` (material + crossed-river bonus only) and a new `_pst_component`, so
`pst_weight` can scale PST independently without touching material at all -- purely a
refactor, verified behavior-preserving by the full suite staying green with no test
changes needed before `pst_weight`/`king_safety_weight` were even added.
`evaluate_components()` was already structured around raw, unweighted values (uses
`_pst_lookup` directly, not `_piece_score`), so it needed no changes at all.

`CALIBRATED_PST_WEIGHT = 10` and `CALIBRATED_KING_SAFETY_WEIGHT = 8` (rounded from the
exact fitted 9.9/8.3 to the nearest integer, same rounding rationale
`CALIBRATED_MATERIAL_VALUES` already used: "a plausible, testable constant, not because
the extra precision was shown to matter"). `SearchEngine` threads both through to
`_evaluate()` identically to how `material_values` already does.

`tools/compare_engines.py --{prefix}-use-calibrated-weights` turns on all three
findings together (material + PST weight + king-safety weight) for one side -- this is
the actual point, not three separate flags, since testing them combined is exactly what
V0.6.3's isolated-material result didn't do. Implies
`--{prefix}-use-calibrated-material` (redundant if both are set, not an error). Ignored,
with an explicit warning, on an `--{prefix}-engine mcts` side, same as every other
`SearchEngine`-only flag (`MCTSEngine` has no `pst_weight`/`king_safety_weight`
parameters -- out of scope here, see Scope boundary).

## Correctness

6 new tests (`tests/test_pst_king_safety_weights_v064.py`), following the exact pattern
`tests/test_evaluation_components_v063.py`'s own `material_values` tests already
established: default weights (1) preserve existing behavior exactly, a weight change
produces precisely the expected delta computed from `evaluate_components()`'s raw
value (not re-derived by hand), all three calibrated findings combine additively and
independently (`material_delta + pst_delta + king_safety_delta`, no cross-term
surprises), `SearchEngine` threads the override through to `_evaluate()`, and the V0.6.3
correctness gate (raw components recombined with the constants in force must reproduce
`evaluate()`'s own output exactly) still holds for a non-default weighting, not just
weight=1 -- confirming `evaluate_components()`'s values really are the raw, unweighted
ingredients they claim to be, for any weighting, not only the default one. Full suite:
**287/287 green.**

## Script to run

Two commands, testing the two things worth distinguishing: does *combining* all three
calibrated findings change V0.6.3's negative result, and does it matter at a greater
search depth (`docs/v0.6.3.md`'s second, still-untested hypothesis -- shallow search may
not see far enough ahead to justify more aggressive valuations):

```powershell
# Combined calibrated weights vs. default, depth 2 (matches V0.6.3's own depth exactly,
# so this result is directly comparable to the existing -53 Elo material-alone finding)
python tools/compare_engines.py --a-use-calibrated-weights --a-depth 2 --b-depth 2 --games 100 --output data/v0.6.4_combined_weights_compare.jsonl

# Same comparison at depth 3, testing the depth hypothesis at the same time
python tools/compare_engines.py --a-use-calibrated-weights --a-depth 3 --b-depth 3 --games 100 --output data/v0.6.4_combined_weights_depth3_compare.jsonl
```

Same guidance as the V0.6.3 100-game run this is directly following up on: safe to
interrupt and resume (each completed game is appended immediately, not batched). Safe
to run multiple processes in parallel for speed, but each parallel process should write
to its *own* `--output` file rather than sharing one -- `append_record` opens the file
fresh per record with no file-locking, so two processes writing to the same file at the
same moment can interleave mid-write and corrupt a line on Windows in particular. Merge
the resulting files by concatenation (or just hand each one to whoever is analyzing the
result) rather than trying to write them all to one shared path. At depth 2 these games
run at roughly the same speed as V0.6.3's own 100-game run (~40-45s/game observed
there); depth 3 will be noticeably slower per game.

## Real-game result (2026-09-11): a clear reversal — combined calibration wins

User ran both commands from the "Script to run" section above, 100 games each.

**Depth 2** (`data/v0.6.4_combined_weights_compare.jsonl`, directly comparable to
V0.6.3's own depth-2, material-alone result), all 100 records verified clean:

```
Calibrated weights: 57 wins
Default:            43 wins
Draws:               0
Calibrated score rate: 57.0%
95% CI: [47.3%, 66.7%]
Estimated Elo diff: +49
p = 0.162 vs. a 50% null (not significant alone)
```

**Depth 3** (`data/v0.6.4_combined_weights_depth3_compare.jsonl`), all 100 records
verified clean:

```
Calibrated weights: 60 wins
Default:            37 wins
Draws:               3
Calibrated score rate: 61.5%
95% CI: [52.0%, 71.0%]
Estimated Elo diff: +81
p = 0.021 vs. a 50% null (significant at the conventional 0.05 level)
```

**Combining both as independent confirmatory tests (Fisher's method): p ≈ 0.023.**

### This reverses V0.6.3's material-alone finding, and confirms both untested hypotheses at once

This is the first clearly *positive* result from any evaluation-tuning checkpoint in
this project's history -- V0.6.2's neural eval was -269 Elo, V0.6.3's material alone was
~-53 Elo, and this is +49 to +81 Elo depending on depth. The reversal is the whole
point: **applying material calibration *together with* the PST/king-safety scaling the
same regression found, rather than material in isolation, turns a losing change into a
winning one.** That's a direct confirmation of this doc's hypothesis (a) -- the isolated
material table genuinely was inconsistent with the rest of `evaluate()`'s
un-recalibrated weighting, and combining all three findings resolves that
inconsistency rather than compounding it.

The depth-2-vs-depth-3 gap (directionally positive but not significant alone at depth
2; significant at depth 3) is also informative, though not as cleanly isolated as a
dedicated depth-only test would be -- it's consistent with (though doesn't in isolation
prove) `docs/v0.6.3.md`'s second, depth-shallowness hypothesis: a deeper search may be
better positioned to actually exploit the more nuanced positional signal the stronger
PST/king-safety weighting provides. Both of V0.6.3's untested hypotheses end up
pointing the same direction here rather than being mutually exclusive: the combined
weighting is more internally consistent (hypothesis a) *and* that consistency pays off
more clearly with more search depth to use it (hypothesis b).

### Recommendation, not yet acted on

Given a statistically significant positive result at depth 3 and a directionally
consistent (if not independently significant) one at depth 2, combined p≈0.023, this is
meaningfully stronger evidence than V0.6.3's own "100+ games is the natural way to
settle this" bar asked for, and the first evaluation change in this project with a real
case for promotion to the *default*, not just an available opt-in flag. **This has
deliberately not been done in this session** -- changing `SearchEngine`'s actual default
arguments (as opposed to `tools/compare_engines.py`'s opt-in flags) affects every
existing default-constructed `SearchEngine` everywhere, including `UCCIEngine`, and is a
more consequential decision than adding another available-but-off option was. Flagging
it clearly as the recommended next action rather than making it unilaterally: promote
`CALIBRATED_MATERIAL_VALUES`/`CALIBRATED_PST_WEIGHT`/`CALIBRATED_KING_SAFETY_WEIGHT` to
`SearchEngine`'s actual constructor defaults (with the current hand-guessed
`MATERIAL_VALUES`/weight-1 behavior remaining available via explicit override for
comparison), which would need its own doc entry and its own before/after real-game
confirmation that nothing regressed in the process.

## Scope boundary

`MCTSEngine` does not get `pst_weight`/`king_safety_weight` parameters in this
checkpoint -- it currently hardcodes `use_piece_square_tables=True`/
`use_king_safety=True` with no weight concept at all, matching how it never got
`material_values` either (V0.6.3 was scoped to `SearchEngine` only, and this checkpoint
follows that same boundary).
