# AlphaZetaChess V0.9.10 — Search 2.0 foundation

## Status

IMPLEMENTED — History Heuristic integration.

## Why this change

The V0.9.9 work increased practical search speed substantially, but simply
raising the nominal depth is not expected to close the large playing-strength
gap with mature Chinese-chess engines. The next stage therefore focuses on
making each searched node more valuable through modern alpha-beta search
techniques.

## Implemented in V0.9.10

### History Heuristic

`SearchEngine` now maintains a search-local history table for quiet moves.
Quiet moves that produce a beta cutoff receive a depth-weighted reward;
quiet moves searched before the successful cutoff move receive a penalty.
The resulting history score participates in non-root move ordering.

The implementation uses a gravity-style bounded update so repeated evidence
converges instead of growing without limit.

History is cleared at the start of each root search, preserving the existing
search-local behavior of killer moves and preventing unrelated games from
contaminating move ordering.

### Compatibility

`use_history=True` is the new default. The option can be disabled with
`use_history=False` for A/B comparisons. History changes move ordering only;
it does not intentionally alter the evaluation function or game rules.

## Intentionally not included yet

The following changes are deliberately separated into later commits so that
strength and performance can be measured independently:

1. Static Exchange Evaluation (SEE)
2. Null Move Pruning
3. Late Move Reduction (LMR)
4. Aspiration Windows
5. Futility/Razoring
6. Check extensions
7. Additional history tables / continuation history

## Web UI

No UI-specific switch is required for this first step. The Web UI already
uses `SearchEngine`, so the default engine search automatically benefits from
History Heuristic after pulling this commit. A later UI pass will expose
search diagnostics such as depth, selective depth, nodes, NPS and TT hit rate
when those metrics are available from the search layer.

## Verification plan

The next local verification should run the complete pytest suite and then
compare the same benchmark positions with `use_history=False` and
`use_history=True`. Strength conclusions should come from fixed-time engine
matches rather than from a single game or nominal depth alone.
