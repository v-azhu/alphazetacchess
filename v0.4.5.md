# AlphaZetaChess V0.4.5 — Piece Coordination

## Status

**Implemented, tested, cheap. `use_piece_coordination` defaults to
`False`** (same reasoning as every other V0.4.x term).

This completes V0.4's original scope from `docs/roadmap.md`: mobility
(V0.4.3), piece-square tables (V0.4.1), coordination (V0.4.5), king
safety (V0.4.2), pawn structure (V0.4.4) are all now implemented,
tested, and independently toggleable. Endgame/opening knowledge was not
part of this pass — see "What's left" below.

## Design

Two classical, well-known Xiangqi coordination patterns, both about
Rooks and Cannons sharing a file:

```python
DOUBLED_ROOKS_BONUS = 15
ROOK_CANNON_BATTERY_BONUS = 10
```

- **Doubled Rooks (双车):** two friendly Rooks on the same file support
  each other and can combine firepower along it.
- **Rook-Cannon Battery (车炮连环):** a friendly Rook and Cannon sharing
  a file form a combined threat — a Cannon needs a screen piece to
  capture, and any piece landing between them (including future
  repositioning) can create one, while the Rook independently backs up
  the same file regardless.

Both bonuses can stack on the same file (e.g. two Rooks + a Cannon on
one file scores both).

### Deliberately out of scope for this first version

- **Clear line of sight between the two pieces is NOT required.** "Same
  file" is treated as sufficient — both pieces already exert
  independent pressure along that file. Requiring an unobstructed path
  (a "real, immediately usable" battery right now) is a natural
  refinement for later, not a correctness requirement for a first,
  intentionally simple version.
- **Horse-Cannon coordination** (e.g. a Cannon using a friendly Horse as
  a screen) — a real pattern, but requires reasoning about a specific
  screen relationship rather than simple file-sharing, so left for a
  later, more targeted addition if this first version's signal proves
  useful.
- **Same-rank coordination** — only file-sharing is checked, matching
  how Rooks/Cannons more commonly coordinate vertically along a file
  toward the opponent's camp; a rank-based variant could be added
  symmetrically later.

### API

`evaluate(board, perspective_color, ..., use_piece_coordination=False)`
— independent of the other four V0.4.x terms
(`use_piece_square_tables`/`use_king_safety`/`use_mobility`/
`use_pawn_structure`); all five stack additively and can be toggled in
any combination. `SearchEngine` gained a matching
`use_piece_coordination` constructor flag, threaded through all four
internal `evaluate()` call sites, following the exact pattern
established for the other four terms.

## Correctness gates (`tests/test_piece_coordination_v045.py`, 11 tests)

1. A single Rook alone scores zero.
2. Two Rooks on the same file score the Doubled Rooks bonus.
3. Two Rooks on different files score zero.
4. A Rook and Cannon on the same file (even far apart) score the
   Battery bonus.
5. Doubled Rooks and a Battery can stack on the same file.
6. Horse/Elephant sharing a file with a Rook do NOT count (only
   Rook/Cannon combinations count, per the scope boundary above).
7. An enemy piece on the same file does not count.
8. Symmetric position → `piece_coordination_balance(RED) ==
   -piece_coordination_balance(BLACK)`.
9. `use_piece_coordination=False` (explicit) exactly reproduces the
   V0.4.4 baseline evaluation.
10. Toggling the term on changes the score by exactly the expected
    amount in a constructed position.
11. `SearchEngine`-level wiring check (direct `_quiescence` call,
    same technique used for every other V0.4.x wiring test).

Combined with all other V0.4.x targeted test files: **46/46 green,
0.35s.**

## What's left from V0.4's original list

`docs/roadmap.md`'s V0.4 scope was: "Mobility, piece-square tables,
coordination, king safety, pawn structure, endgame knowledge and
opening knowledge." The first five are now all implemented. Endgame and
opening knowledge are qualitatively different from the other five (they
aren't simple additive scoring terms — endgame knowledge typically means
piece-count-dependent evaluation switches or tablebase-style lookups,
and opening knowledge means a move-selection book, not a position
scorer) and are reasonable candidates to either become their own
V0.4.6+ sub-versions or be folded into V0.5's self-play scope, since
opening books in particular are often built FROM self-play data. Left
as an open decision rather than assumed.

## Next step: the web UI now exposes all five toggles

Rather than editing `web/server.py` by hand to try combinations, the web
UI's "New Game" panel now has checkboxes for all five evaluation terms
(three off-by-default: Mobility, Pawn Structure, Piece Coordination; two
on-by-default: Piece-Square Tables, King Safety), so any combination can
be tried directly from the browser. See `docs/ui.md` for details. This
was the actual point of doing V0.4.3-4.5 before touching endgame/opening
knowledge or V0.5 — there's now something real to sit down and play
against.
